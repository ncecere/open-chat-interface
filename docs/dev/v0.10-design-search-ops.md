# v0.10 design: search fallback, clearer project search, shared operations UI

Three ROADMAP "Now — v0.10" rows: **Slow search providers**, **Clearer
project search** and **One place for operations pages**. No database
migration: the new settings live in the existing `instance_setting` JSON, and
the new reply data in the existing message `parts`.

## Slow search providers

**What fails over.** A provider timeout, a network failure and, new in v0.10,
an HTTP 5xx are *transient* (`services/search/http.ts`): retried once (as in
v0.9) and then passed to the fallback provider. 401/403 (key), 429 (quota or
rate limit), other 4xx and invalid responses are the administrator's to fix,
so they fail at once and never reach the fallback. A search the caller
stopped (reply stopped, tool time limit) neither retries nor falls back.

**Time budget.** The `web_search` tool call is cut off at 30 s, so the whole
search, fallback included, still ends within `SEARCH_TOTAL_TIMEOUT_MS`
(25 s). Without a fallback nothing changes (15 s per attempt). With one, each
attempt at the first provider gets 8 s (`SEARCH_PRIMARY_ATTEMPT_WITH_FALLBACK_MS`)
and both together at most 17 s, so the fallback always has at least 8 s; it
gets up to 15 s per attempt from what remains and may itself retry once if
2 s or more are left. `searchWithFallback` in `services/search/index.ts`.

**Settings.** `search` gains `fallbackProvider`, `fallbackBaseUrl` and
`encryptedFallbackApiKey` (absent in older settings = no fallback). The
admin API returns `fallbackProvider`, `fallbackBaseUrl` and
`hasFallbackCredential`, never the key; the PATCH takes `fallbackProvider`,
`fallbackBaseUrl` and write-only `fallbackApiKey`. The same rules as the
primary: only what the chosen provider needs is stored, and switching the
fallback provider drops its key. The PATCH rejects (422) a hosted provider as
its own fallback and a SearXNG fallback at the primary's address, checked on
the merged result. A fallback missing its key or address is ignored at run
time (`fallbackSearchProblem`), and the setup checklist's web search detail
says why, without marking search unavailable. The settings audit diff
redacts `fallbackApiKey`/`encryptedFallbackApiKey` by name.

**Recording who answered.** `searchWeb` now returns `{ results, provider,
fallback }` (provider by display name). The `web_search` tool result carries
`provider` and `fallback: true` when the fallback answered; the tool step
summary then ends "· via Brave Search (fallback)". The pre-search
`data-search-grounding` part carries `provider` and `fallback`; the grounding
details show it. When both fail, the error is "<first error> The fallback
provider failed too: <second error>", each naming its provider.

**Test search** takes an optional `fallback` target and tests it separately
(in parallel, own retry budget, no fallback), so a failing primary does not
hide the fallback's result. The saved fallback key is used only when the
fallback provider on the page is the saved one. The `search.test` audit
entry adds `fallbackProvider` and `fallbackOk`.

**Observability.** Logs (`slot: primary|fallback`, provider, attempt,
duration, error message, "Web search falling back to the second provider")
never contain the query or a key. New metrics: `oci_web_searches_total
{provider, slot, outcome}` and `oci_web_search_duration_seconds{provider,
slot}`, counted for conversation searches only (not Test search).

**Tests.** `web-search-fallback.live.test.ts`: real database and admin API,
real HTTP to stub servers (two SearXNG stubs; Brave's fixed endpoint
redirected to a third stub so its key travels in the real header), covering
encryption/redaction, 5xx and unreachable fallback, both failing, no fallback
on 401, SearXNG-as-fallback, same-service refusal, incomplete fallback, and
Test search of both. Unit: timing budget, retry of 5xx, no fallback on
401/429, abort, availability rules.

## Clearer project search

**(a) Passages used.** The `data-project-search` part keeps its shape and
adds, per file, `excerpts: [{ id, first, last, heading?, snippet }]`:
`id` is `<attachmentId>:<first>-<last>`, `snippet` the first 200 characters
of the passage on one line (`PROJECT_EXCERPT_MAX_CHARS`, ellipsis when cut,
never splitting a surrogate pair), at most 24 per reply
(`PROJECT_EXCERPTS_MAX`, the first in file order; every passage is still
counted). This reverses the v0.8 rule "names and counts only, never passage
text" deliberately: the roadmap asks to show the passages, the text is the
person's own file, the part is still excluded from share links (allowlist in
`share-links.ts`), is not indexed by conversation search (text parts only)
and is bounded (about 5 KB). Replies stored earlier have no excerpts and
render as before, without the toggle.

Headings are not stored at index time. `passageHeadings` reads at most
4,000 characters before each passage (one query) and takes the first
Markdown-style heading inside the passage, else the last one before it.
Files without such lines (most PDFs and Word documents) get none. Failure
means no headings, never a failed reply.

The web note keeps its one-line summary and adds a **Show passages used**
toggle (`aria-expanded`/`aria-controls`) listing, per file, "Passage(s) n–m ·
heading" and the snippet.

**(b) Leaving files out.** `POST /api/chat` accepts optional
`excludedProjectFileIds` (at most 20, the per-project file limit). Before the
turn is claimed, `assertExcludableProjectFiles` requires the conversation to
be in a project and every id to be a file of that project owned by the
person (a file deleted since the composer listed it still passes); otherwise
422 and nothing is stored. Excluded files take no part in the turn at all,
whole or searched (simpler and more predictable than excluding only from
search). The part gains `excluded: [{ name }]`; with exclusions and no
searched passages the part is `{ mode: 'search', files: [], excluded }`, so
the reply always says what it did not look at.

Exclusions apply to one message. They are not stored, so regenerating a reply
and the continuation after a tool approval use every file (noted in the
user docs). The composer's **Files** control appears in a conversation (not
on the landing page) whose project has at least one indexed file, when the
role has projects; it lists all ready files with checkboxes (default all),
and the session sends the unticked ids with the next message and resets.

## One place for operations pages

`components/admin/operations/`:

- `destination.tsx`: `DestinationDraft`, `destinationDraftFrom`,
  `destinationChanges` (only changed fields; secret only when typed),
  `DestinationSelect`, `S3BucketFields` (bucket, region, endpoint, prefix,
  access key, write-only secret, path style) and `DestinationTest`.
- `schedule.tsx`: `formatHourUtc`, `HourField`, `IntervalField`,
  `RetentionField`.
- `runs.tsx`: `RunStatusIcon`, `RunNowControl`, `RunHistory` (status, when,
  trigger, page-specific badges, size/count summary or error, extra lines,
  object key) and `formatRunTime`.

Backups and Compliance keep their ids, labels, texts, exports
(`backupChanges`, `complianceChanges`, `filesSummary`, query keys) and
behaviour; their existing tests pass unchanged. The run history stays a
list rather than becoming a table with duration and actions, since that
would change the pages; the component is where to add them later. Component
tests: `admin-operations.test.tsx`.

## Deferred

- Leaving files out of the first message of a new conversation (landing page)
  and remembering exclusions for regeneration.
- A duration column and per-run actions in the operations run history.
- Per-provider health history for web search beyond the metrics.
