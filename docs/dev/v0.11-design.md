# v0.11 design: always on

Status: **in progress** on branch `v0.11/always-on`. Written before the work
started, so it records intent and the decisions still open. Sections gain "As built" notes as
items ship, as in `v0.9-design.md`.

## Goal

A large deployment (tens of thousands of people, tens of millions of messages,
several API replicas, a highly available PostgreSQL cluster such as Patroni
with three to five nodes) upgrades OCI from the previous minor release with
**no downtime**, keeps working through a database failover, and rebuilds
search or vector indexes without a gap. Each of these is **tested in CI**, not
promised in documentation.

"No downtime" means, during an upgrade from release N−1 to N:

- every request that worked before the upgrade keeps working, apart from
  requests that are safe to retry and are retried by the client;
- a reply being written when a replica is replaced finishes, or resumes on
  another replica, instead of being cut short;
- no step takes a lock that blocks reads or writes for longer than a few
  seconds;
- search, project search and meaning-based search keep answering while
  anything they depend on is rebuilt.

Non-goals for v0.11: multiple regions, multiple tenants in one deployment,
replacing PostgreSQL, and making any new service mandatory. OCI keeps one
stack: PostgreSQL, Redis and S3-compatible storage, with optional additions.

## Where OCI starts

Verified against the code at v0.9.1:

- **Migrations** run once, under a transaction-scoped advisory lock, all in
  one transaction (`packages/db/src/migrator.ts`). Replicas started with
  `RUN_MIGRATIONS=false` refuse to serve until the newest bundled migration
  is recorded. Because everything runs in one transaction, an index cannot be
  built `CONCURRENTLY`: v0.7's message search index blocked writes to
  `message` for as long as it took to build, and v0.9's audit numbering takes
  time proportional to the audit log. There are no lock or statement timeouts.
- **Compatibility**: releases add tables and nullable columns and remove
  columns over two releases (`docs/dev/database.md`), so release N−1 normally
  runs against release N's schema. This is a convention; nothing tests it.
- **Data model**: messages are rows, not one document per conversation, so
  migrations rarely need to rewrite stored conversations.
- **Background jobs** run in-process on every API replica
  (`services/jobs/index.ts`), each guarded by a PostgreSQL advisory lock, on
  fixed intervals. Indexing, embedding, imports, compaction, retention,
  webhooks and backups are all jobs.
- **Redis** carries durable reply streams (resume after a disconnect), the
  per-person concurrency slots and rate limits. Rate limits fall back to
  in-process counters when Redis is unavailable, which is per replica.
- **Settings** are cached per replica for 30 seconds.
- **Database connections** use postgres.js with prepared statements off
  (`prepare: false`). Session-mode pooling or direct connections are required
  because jobs and migrations hold advisory locks.
- **Embeddings** live in one runtime-created pgvector table
  (`project_file_embedding`), re-created when the model's dimensions change,
  which drops every stored vector until the background job re-embeds them.
  Searches are filtered to one person's project and use an exact scan (no
  approximate index).
- **Shutdown**: on SIGTERM the API stops its jobs and closes the HTTP server,
  which waits for open connections without a limit or a readiness change. A
  reply still being written on that replica ends when the process does.
- **Backups**: scheduled `pg_dump`, which suits small and medium databases,
  not a multi-hundred-gigabyte cluster.

## Design

### 1. Migrations in three phases

After [GitLab's database development model](https://docs.gitlab.com/development/database/),
which separates regular, post-deployment and
[batched background migrations](https://docs.gitlab.com/development/database/batched_background_migrations/).

| Phase | Runs | Contains | Must be |
| --- | --- | --- | --- |
| **Pre-deploy** | The `migrate` job, before replicas are replaced (as today) | New tables, nullable columns, constraints `NOT VALID`, new indexes on new or small tables | Transactional and fast: seconds, never proportional to data |
| **Post-deploy** | The `migrate --post` job, after every replica runs release N | `CREATE INDEX CONCURRENTLY`, `VALIDATE CONSTRAINT`, dropping what release N no longer reads | Non-transactional, one statement per step, idempotent, resumable |
| **Background** | The job runner, while OCI serves | Backfills and rewrites of existing rows, in batches | Idempotent per batch, throttled, resumable after any failure |

**Files.** Pre-deploy migrations stay in `packages/db/drizzle` with Drizzle's
journal. Post-deploy steps live in `packages/db/post/NNNN_name.sql` with their
own journal table (`oci_post_migration`: name, started, finished, attempts,
error). Background migrations are TypeScript definitions in
`packages/db/src/background/` registered by name.

**Background migration state** (`background_migration` table): name, target
table, cursor (the last primary key processed), batch size, pause between
batches, status (`pending`, `running`, `paused`, `finished`, `failed`),
attempts, last error, started and finished times. One worker claims a
migration with a lease, as the compaction queue does. Each batch updates rows
and advances the cursor **in one transaction**, so a crash or failover never
loses or repeats work beyond one batch, and the batch body is idempotent in
case it does.

**Throttling.** Batches pause when the database is under pressure:
replication lag above a threshold (read from `pg_stat_replication` on the
primary), long-running transactions, or request latency above a target.
Defaults are conservative; operators can pause, resume and change the batch
size on System health.

**Finalisation.** A release can declare that it needs earlier background
migrations to be finished. The preflight (section 6) and the migrator both
refuse to apply release N's pre-deploy migrations until they are, with a
message naming them. This is how a later release can rely on a backfill
without blocking its own upgrade on it.

**Code during the gap.** Between pre-deploy and the end of the background
phase, release N runs on a schema whose new indexes or backfilled columns may
be incomplete. Features that depend on them check a readiness flag (a
finished post-deploy step or background migration) and fall back, for
example keyword search without the new index's speed-up, or the old column
until the backfill finishes.

**As built** (`packages/db/src/post-migrator.ts`, `release-manifest.ts`,
`sql-analysis.ts`, `src/background/`; `apps/api/src/services/migrations/`;
migration 0039; `docs/dev/database.md`, "Three kinds of migration"):

- **Post-deploy** steps are one statement per file in `packages/db/post`,
  ordered by `post/journal.json` (tag and release). `migrate --post` (API
  image `node dist/migrate.js --post`, `pnpm db:migrate:post`, Compose
  `migrate-post`) refuses until the release's newest pre-deploy migration is
  recorded, holds a session advisory lock, and runs each step outside a
  transaction with the pre-deploy `lock_timeout` and retry/backoff and its own
  `statement_timeout` (`POST_MIGRATION_STATEMENT_TIMEOUT_MS`, four hours).
  `oci_post_migration` records started before and finished after each step;
  unfinished steps rerun. Before an index step it drops an INVALID index of
  that name (`pg_index.indisvalid`) concurrently. Reproduced first: an
  interrupted `CREATE INDEX CONCURRENTLY IF NOT EXISTS` leaves an INVALID
  index, and rerunning the statement succeeds without building it. A session
  lost mid-step (terminated, failover) is reported and resumed, with nothing
  more sent on the dead connection.
- **Automatic post-deploy is explicit by default.** There is no sound signal
  in the database that every replica runs release N (releases before v0.11
  record nothing about themselves), so with several replicas it stays an
  operator step. `RUN_POST_MIGRATIONS` (default: `RUN_MIGRATIONS`) lets a
  single instance, which migrates itself at startup, apply it from a job.
- **Background migrations** are TypeScript definitions registered in
  `src/background/index.ts`, scheduled by `migrate --post` (not `migrate`: once
  every replica runs N, N writes new rows correctly, so a keyset scan from the
  start covers every row that needs it). The job `migrations.background` (30 s
  ticks, 25 s budget) claims one with a lease (`for update skip locked`, two
  minutes, renewed per batch); each batch locks the row, checks the lease and
  status, runs, and advances the cursor in one transaction. Throttles:
  standby replay lag (`pg_stat_replication`, needs `pg_monitor`) and the
  oldest transaction in the database; request latency is not used (it is per
  replica). Failures back off and mark the migration `failed` after five in a
  row. System health shows progress (UUID cursor position, or rows against
  `reltuples`); administrators pause, resume and set batch size and pause,
  audited; auditors read. Gauges `oci_background_migration_*`. v0.11 has no
  real backfill to ship: the test-only `oci-test.rewrite-messages-in-place`
  (enabled by `OCI_TEST_BACKGROUND_MIGRATIONS`) rewrites messages in place for
  the tests and the upgrade test. A batch that throws or is cancelled
  mid-statement, a dead lease holder and a taken-over lease were each checked
  to lose and repeat no row (a counter that is not idempotent on purpose).
  Terminating a batch's backend makes postgres.js 3.4.9 throw an uncaught
  TypeError (a query written to the closed socket of a transaction); that is
  for the failover work (section 3).
- **Finalisation**: `packages/db/releases.json` names each minor release's
  first migration and its `requires`; the migrator checks them under its lock
  before applying a release's migrations and fails with
  `UnfinishedRequirementsError` naming each item and its state (reproduced
  first: without it the migration applied). New databases are never refused.
  The linter checks the manifest names real migrations, steps and
  definitions. `isPostStepDone` / `isBackgroundMigrationDone` (readiness.ts)
  cache true forever and false for 30 s.
- **First real use**: `0001_message_created_at_index` and
  `0002_message_error_created_at_index` (partial, `status = 'error'`; with
  only the first, the usage page's error count got slower, 43 to 60 ms, as
  the planner read a third of the table through it). Scale harness `small`
  (500,000 messages, 905 MB): the overview's counts 46 / 46 / 138 ms to
  1.0 / 1.4 / 22 ms (index-only scans), `GET /api/admin/overview` median
  126 ms to 22 ms, the usage error count 43 ms to 1.6 ms; builds 381 ms and
  136 ms; the first index is 11 MB (estimated 11 MB).
- **Upgrade test**: after replacing replicas it runs `migrate --post` and
  waits for background migrations under load. From v0.10.2: post-deploy 1.5 s
  (index builds 134 ms and 67 ms on 300,000 messages), the test migration
  300,342 rows in 301 batches over 25 s across both TO restarts, no failed
  request outside the FROM stop windows, p99 142 ms, no lock waits.

### 2. Lock-safe steps

Every migration step runs with `SET LOCAL lock_timeout = '3s'` and
`statement_timeout` sized to the step (seconds for pre-deploy DDL), plus
`idle_in_transaction_session_timeout` on migration sessions. A step that
times out waiting for a lock is retried with backoff (up to ten attempts over
a few minutes) and then fails clearly, instead of queuing every other query
behind it. The lint rule in section 4 keeps pre-deploy steps fast enough for
these timeouts.

**As built** (`packages/db/src/migration-safety.ts`, `migrator.ts`): each
attempt sets `lock_timeout` (`MIGRATION_LOCK_TIMEOUT_MS`, 3 s),
`statement_timeout` (`MIGRATION_STATEMENT_TIMEOUT_MS`, 15 minutes, per
statement) and `idle_in_transaction_session_timeout` (10 s) right after
`BEGIN`. A lock timeout (55P03) rolls the whole attempt back, advisory lock
included, and retries: 10 attempts, 1 s doubling to 30 s with jitter, about
three minutes. The final error names the table, the lock mode and the blocking
session's pid, state, application and query. `pnpm db:migrate` uses the same
path. Reproduced first: a reader queued behind a blocked `ALTER TABLE` waited
without limit and the migration never gave up.

### 3. Failover safety

On Patroni (or any primary/replica cluster behind a virtual IP, HAProxy or a
pooler) a failover drops every connection to the old primary. Advisory
locks, open transactions and prepared state are lost. With asynchronous
replication, the last moments of committed work can be lost too.

- **Requests**: postgres.js reconnects. Read requests and idempotent writes
  that fail with a connection error are retried once within the request.
  Non-idempotent writes return a retryable error, and the web app retries the
  operations it knows are safe.
- **Jobs**: a job that loses its lock connection stops its current batch at
  the next check and releases nothing it does not hold. The next tick
  re-acquires the lock on the new primary. Job bodies are already written to
  be re-run safely; the failover drill proves it.
- **Pre-deploy migrations**: transactional, so a failover rolls the attempt
  back and a rerun starts cleanly.
- **Post-deploy steps**: a concurrent index build interrupted by a failover
  leaves an `INVALID` index; the runner drops and rebuilds it on the next
  attempt.
- **Background migrations**: the cursor commits with each batch; a batch lost
  to asynchronous replication is redone, and batches are idempotent.
- **Reply streams** are in Redis, not PostgreSQL, so a database failover does
  not interrupt one being written. Its final save is retried.

**Tests.** Pull-request CI terminates every backend connection
(`pg_terminate_backend`) during a migration, a background batch, a job and a
reply, and checks each recovers. A scheduled workflow runs a real
three-node Patroni cluster with etcd and HAProxy, promotes a replica during
an upgrade and a backfill under load, and checks the success criteria above.

**As built** (`lib/db-connection.ts`, `middleware/read-retry.ts`,
`services/jobs/lock.ts`, `services/chat/run-save.ts`, `persist-turn.ts`,
`docs/dev/failover.md`): a lost connection is one of `57P01`-`57P03`, class
`08`, `25006`, socket errors or postgres.js's `CONNECTION_CLOSED`/`ENDED`
(through Drizzle's `cause`), or an unexpected `500` while the pool lost a
connection. Reads are run again once within the request (after 250 ms); other
methods are never repeated and answer `500` with `"retryable": true` and
`X-OCI-Retryable: database-connection` (`503` stays reserved for draining).
A turn's opening transaction is retried for 10 s (a lost commit is recognised
by the reply's lineage); the final save, thread touch and usage settlement
for 30 s, continued totals only while still `streaming`. A job's lock
connection is checked every 5 s and at each `jobMayContinue()` between
batches; a lost lock stops the job after its batch, is recorded as cut short
and is not unlocked, and the next tick re-acquires. Imports requeue (without
using an attempt) on a lost connection, lock or shutdown. Readiness tolerates
30 s of database outage before `503`, so a failover does not empty every
Service at once. Reproduced first: a job ran two more batches beside the
replica that took its lock; the final save and a new message failed; reads
answered `500`. postgres.js 3.4.9 threw an uncaught `TypeError` when a
transaction's backend was terminated (porsager/postgres#1154) and, after a few
such failures, stopped serving; the pinned patch fixes four defects in its
close path (`patches/README.md`). The migration case already passed. PR CI:
`failover-*.live.test.ts`, `postgres-transaction-failover.live.test.ts`. The
drill (`tools/failover-drill`, weekly): Spilo x3, etcd, HAProxy, two `web`
replicas and a worker; `patronictl failover` took 2.4 to 2.6 s, HAProxy
routed to the new primary after 3.0 to 3.2 s; with one and two failovers,
588 and 1,173 requests failed none, 90 and 180 replies all completed, imports
of 5,000 and 8,000 conversations completed with none failed, and jobs
resumed. A slow failover (12.8 s without a primary) left 8 of 635 requests
failed, all retryable. Post-deploy and background migrations join the drill
when section 1 ships.

### 4. Migration linter

A CI step parses every new migration (with a PostgreSQL parser, not regular
expressions) and fails on:

- `CREATE INDEX` without `CONCURRENTLY` on an existing table (pre-deploy may
  index tables created in the same release);
- table rewrites: `ALTER COLUMN TYPE` that changes storage, `ADD COLUMN` with
  a volatile default, `SET NOT NULL` without an existing validated check;
- `ADD CONSTRAINT` without `NOT VALID` on an existing table;
- `UPDATE` or `DELETE` in a migration (data changes belong in background
  migrations);
- `DROP COLUMN` or `DROP TABLE` in pre-deploy (post-deploy only, and only for
  what the previous release no longer reads: checked against the previous
  release's Drizzle schema);
- `LOCK TABLE`, and any statement in post-deploy that cannot run outside a
  transaction safely.

An exception needs an inline `-- oci:lint-allow <rule>: <reason>` comment,
which reviewers see in the diff.

**As built** (`scripts/lint-migrations.mjs`, `pnpm lint:migrations`, a CI
step): parses with `libpg-query` (MIT, WebAssembly), replays migrations in
journal order to know which tables exist, and adds `dynamic-sql` (`EXECUTE` in
`DO` blocks), `REINDEX`, and journal/file mismatch checks. `now()` and
`CURRENT_TIMESTAMP` defaults are flagged although they do not rewrite (they
are stable), because every existing row gets the migration's time: allow them
with a reason. The 38 existing violations (15 non-concurrent indexes, 11 data
changes, among them v0.7's message search index and v0.9's audit numbering)
are grandfathered in `scripts/lint-migrations/baseline.json`; CI never writes
it.

### 5. Rolling-upgrade tests

For every pull request that touches migrations, and for every release:

1. Start PostgreSQL with a database seeded by the **previous release**, at a
   modest scale (enough rows that a missing `CONCURRENTLY` shows).
2. Start the previous release's published image and a steady synthetic load
   (sign-in, sidebar, open conversation, send a message to a stub model,
   search).
3. Run the new pre-deploy migrations while that load continues. No request
   may fail with a server error; latency stays under a bound.
4. Run the previous release's API smoke tests against the new schema.
5. Replace replicas with the new release one at a time, run post-deploy steps
   and background migrations, and check the load still succeeds throughout.

Supported upgrade paths are published per release. The default promise is
"from the previous minor, with no downtime". Skipping a minor is supported
with a maintenance window unless the release notes say otherwise.

**As built** (`tools/upgrade-test`, `.github/workflows/upgrade-test.yml`,
`docs/dev/rolling-upgrades.md`): FROM is the newest published release older
than the source; 300,000 messages are seeded with SQL generated from
`information_schema`, so the seed follows the schema. Under load it runs TO's
migrations, a 52-step smoke suite against FROM on the new schema, replaces API
replicas and web proxies one at a time, restarts TO replicas, and runs the
smoke suite against TO. Five injected unsafe migrations (`--inject index`,
`drop-column`, `rename-column`, `rewrite`, `lock`) make it fail; v0.9.2,
v0.10.0, v0.10.1 and v0.10.2 to the branch pass. Runs on pull requests that
touch migrations, on tags, and on demand (10 to 15 minutes). Replicas of
releases before draining (item 13) cannot drain, so the replies they cut are
reported, and must be recovered by TO; TO replicas are checked strictly.
Post-deploy and background phases join the test when section 1 ships.

### 6. Upgrade preflight

`node dist/scripts/upgrade-check.js` in the API image, and **System health →
Upgrades** in administration, report:

- the running release and schema, and the target's pre-deploy, post-deploy
  and background migrations;
- estimated work: rows and sizes of the tables each step touches (from
  `pg_class` and `pg_total_relation_size`), indexes to build and the disk
  they need (OCI cannot read free disk space through SQL, so it states what
  is needed);
- unfinished background migrations the target requires;
- whether this upgrade can be rolling, or needs a window, and why.

**As built** (`apps/api/src/services/migrations/preflight.ts`,
`scripts/upgrade-check.ts`, `GET /api/admin/migrations/upgrade`, System
health, Upgrades): every pending pre-deploy statement and post-deploy step is
parsed with libpg-query (now a dependency of `@oci/db`) for the tables it
touches (including inside `DO` blocks) and a cost class (catalog, scan,
rewrite, index, concurrent index, data, lock). A non-catalog pre-deploy
statement on an existing table over 10,000 rows or 64 MB makes the verdict
`window`, as does a schema more than one minor behind; unfinished required
work or migrations newer than the image make it `blocked`; otherwise
`rolling`, or `current`. Index sizes are estimated from `pg_stats` widths and
`reltuples` (a partial index from the planner's row estimate for its
predicate), other kinds as 30 % of the table; the report asks for twice the
estimate free. Exit codes 0 (rolling, current), 2 (window), 3 (blocked).

### 7. Search and vector rebuilds without a gap

**Generations.** Each embeddings configuration (model and dimensions) is a
**generation** with its own table, `project_file_embedding_g<n>`. Changing the
model creates generation n+1 and embeds into it in the background while
searches keep using generation n. When n+1 covers every indexed passage (or an
administrator forces the switch), searches move to it atomically. Generation
n is dropped after a grace period. Embedding cost for the new model is shown
before the change is saved.

**Approximate indexes.** When a generation table grows past a threshold, an
HNSW index is built `CONCURRENTLY` (a post-deploy-style step run by the job
runner). Because every search is filtered to one person's project, the exact
scan stays correct and is often fast; the harness (section 10) decides the
threshold, and whether pgvector's iterative index scans are needed for
filtered queries.

**Full-text indexes** built for new search features use the same pattern: the
new index builds concurrently in the background, and the feature switches to
it when it is valid.

**Measured** (scale harness, `medium`: 437,000 passages, 390,000 embeddings
at 1,536 dimensions): an exact scan of the largest project takes 18 to 20 ms;
a scan of every embedding with no project filter takes 1.9 s. Every search is
scoped to one project, so no approximate index is needed yet. The slow part of
project chat was keyword ranking (a CTE recalculated per hit; fixed, 1,491 ms
to 46 ms). Generations (above) are still needed for model changes without a
gap.

**As built** (migration 0041, `apps/api/src/services/vector-store/`,
`services/embeddings/generations.ts`, `rebuild.ts`, `status.ts`;
`docs/dev/database.md`, "Embedding generations"): `embedding_generation`
records each configuration (`filling`, `current`, `retired`, `cancelled`,
`dropped`; at most one current and one filling) and
`embedding_generation_failure` the backoff per file and generation.
Reproduced first: with the model changed to one of other dimensions through
the admin API, a paraphrased question found nothing until every passage was
embedded again (`embedding-model-change.live.test.ts`, failing on the
previous code). Now:

- **Generation 1 keeps the name `project_file_embedding`.** It is adopted
  from the saved setting the first time v0.11 needs it, without copying or
  renaming: v0.10 replicas still running during the upgrade read, write and
  re-create that table by name, and a rename would have them build an empty
  copy and embed everything again. The `embeddings` setting keeps v0.10's
  shape and always describes the current generation (written by the switch
  in its transaction), so v0.10 embeds into and searches generation 1 as
  v0.11 does; the model being filled lives only in its generation row. Later
  generations are `project_file_embedding_g<n>` (a check ties the name to the
  id). Switching away from generation 1 and dropping its table wait until
  every v0.11 post-deploy step is finished (`migrate --post`, the operator's
  statement that no v0.10 replica runs); the admin page says so. A v0.10
  replica whose administrator changes the model mid-upgrade re-creates
  generation 1's table at another size; v0.11 then leaves it alone (no
  drop-and-recreate tug of war), searches keyword-only and System health
  says why.
- **Fill**: the job `embeddings.rebuild` (60 s, 45 s budget, worker and `all`
  replicas) embeds what the filling generation lacks in passage-key order,
  one request per file, pausing `EMBEDDING_REBUILD_PAUSE_MS` (250) after every
  64 passages and stopping under the background migrations' pressure checks.
  Not a background migration: those commit a batch with its cursor in one
  transaction, and this batch waits on a provider. Resumable by the
  anti-join; a crash re-embeds only the request in flight (tested by
  abandoning a fill mid-write). Uploads embed into both generations; the
  current generation's job is unchanged.
- **Switch**: when nothing is missing (or an administrator forces it, with
  the coverage shown), one transaction retires the current generation
  (`drop_after` = now + `EMBEDDING_GENERATION_GRACE_MINUTES`, a day), makes
  the filling one current and writes the setting. Each search reads the
  current generation as it starts and embeds the question with that
  generation's model; a test running 24 searches through a switch saw every
  one answer by meaning, from both generations. The job drops retired tables
  after the grace period and cancelled ones at once; a configuration chosen
  again before its table is dropped is reused.
- **Deletes** need no outbox in PostgreSQL: every generation table has a
  foreign key to its passage with `ON DELETE CASCADE`, so file, project and
  account deletion, trash purge, retention and legal hold release remove
  vectors from every generation in the deleting transaction, whichever
  release deletes.
- **Cost before saving**: the page shows passages × average tokens (sampled,
  four characters a token) × the price entered; the estimate is audited with
  the change. Switch (`embeddings.generation.switch`, manual or automatic),
  cancel and drop are audited.
- **Measured** (`small`, about 62,000 passages; `docs/dev/scale-harness.md`):
  the fill ran at 4,975 passages a minute; the vector search statement stayed
  at 9.7 ms median during it (10.5 before); uploads took 136 ms instead of
  82 ms while written to two generations; the current generation's embedding
  job slowed from 213 to 74 passages per busy second, sharing the provider
  and the API process with the fill.
- **Full-text indexes** need no new mechanism: a post-deploy step builds the
  new index concurrently, the feature checks `isPostStepDone` and keeps its
  old query until then, and the next release drops the old index.
- No approximate index: not needed at the measured scale.

### 8. Vector store interface, and optional Qdrant

Searches and writes go through a `VectorStore` interface: upsert passages,
delete by passage, file, project or person, search with a **mandatory**
person-and-project filter, report health, and create, fill, switch and drop
generations. `PgvectorStore` is the default and the only store in the first
step.

**Qdrant as an optional store.** A deployment with very many passages, or one
that wants vector search load off the database cluster, could configure
Qdrant. The rules that keep it from becoming the problem it is elsewhere:

- **PostgreSQL stays the source of truth** for passages, files and
  permissions. Qdrant holds vectors and the minimal payload needed to filter
  (person, project, file, passage id), never message or file text.
- **Rebuildable**: losing or upgrading Qdrant never loses data. Vectors are
  also kept compactly in PostgreSQL (`halfvec` or float16 `bytea`, an
  operator option), so a rebuild copies instead of re-embedding. Without that
  option a rebuild re-embeds, at the model's cost.
- **Blue/green collections**: each generation is a Qdrant collection behind an
  alias, so a Qdrant upgrade or model change fills a new collection and moves
  the alias. Nothing is migrated in place.
- **Deletes are delivered reliably**: an outbox table in PostgreSQL records
  every vector delete in the same transaction as the source change (file
  removed, retention, trash purge, account deletion, legal hold release). A
  job delivers it to Qdrant with retries, and System health shows the
  backlog. Compliance documentation states the delay.
- **Isolation**: every query carries the person and project filter, enforced
  in the store, never by the caller; Qdrant's multitenancy guidance (payload
  indexes on the tenant fields) applies.
- **Backups** do not need to include Qdrant, because it is rebuildable.

Whether Qdrant ships in v0.11 depends on the harness: if pgvector meets the
latency targets at the measured scale, v0.11 ships the interface and

**As built** (`apps/api/src/services/vector-store/`): `VectorStore`

### 9. Read-only maintenance mode

An administrator setting (and an environment variable for emergencies) puts
the instance in read-only mode: reading, searching, exporting and signing in
work; sending, editing, uploading and settings changes return
`503 Service Unavailable` with `Retry-After`, and the web app shows why and
disables the composer. A scheduled broadcast announces it beforehand. Jobs
that write pause, apart from those the operator chooses to keep running.

**Note from item 13:** the bundled proxy takes a replica that answers `503`
out of rotation for 10 s, so read-only mode must refuse writes with another
status (for example `423 Locked` or a `409` with a stable code), or every
replica would leave rotation at once.

**As built** (`middleware/read-only.ts`, `services/maintenance/read-only.ts`,
`routes/maintenance.ts`, `routes/admin/maintenance.ts`,
`packages/shared/src/schemas/maintenance.ts`; web `lib/read-only.ts`,
`components/layout/read-only-banner.tsx`, `components/admin/maintenance-mode.tsx`;
`docs/admin/maintenance.md`; no migration, the `maintenance` instance setting):
on when `OCI_READ_ONLY=true` (wins; System health says the environment holds
it and cannot turn it off), when an administrator switches it on (reason,
optional expected end, who and when kept), or inside a scheduled window
(start and end; it ends by itself). Writes are refused with **`423 Locked`**,
error code `READ_ONLY`, `details.readOnly` (the status), `Retry-After` in
seconds when the end is known and `X-OCI-Read-Only` naming the source: not
`503` (the proxy's passive check, and draining), not `500` (`retryable`
failover), not `409` (per-resource conflicts the web app handles per
resource); `423` is a client-side refusal no proxy or error budget counts
against the server. The guard is the first middleware of `/api` and refuses
every method other than GET, HEAD and OPTIONS before anything else (no body
read, no rate limit spent) unless an explicit allowlist matches: Better
Auth's `sign-in/*`, `sign-out` and the SAML posts (`sso/saml2/*`, so
just-in-time provisioning still works), invitation validation, the
first-sign-in policy step (`me/onboarding/*`), signing out other devices and
an administrator revoking someone's sessions, Stop on a reply in progress,
dismissing an announcement, the switch itself (`PUT /api/admin/maintenance`,
administrators only), and a manual backup or compliance export while that job
is kept running. Session refresh happens on GET. If the setting cannot be
read the guard lets the request through (it would meet the database anyway).
`read-only-allowlist.unit.test.ts` enumerates every write the router
registers, Better Auth's endpoints behind `/api/auth/*` expanded from
`auth.api` (168 writes, 47 of them Better Auth's), asserts each refused one
answers 423 with the code and `Retry-After`, keeps the allowed set as an
inline snapshot (20 routes), and fails on an allowlist entry that matches no
route. **Jobs**: the runner asks a
pause hook (`setJobPauseCheck`) before taking a job's lock and in
`jobMayContinue()`, so a paused job does not start (tick, kick or Run now) and
one running stops after its batch (an import is requeued as on a shutdown).
Kept running by default: `backups.run`, `compliance.export`, `webhooks.deliver`
(the switch's own audit event reaches the SIEM) and
`chat.recover-interrupted-replies`; the administrator ticks others or unticks
these. **Replies** admitted before the switch finish: the guard sits in front
of the routes, and a reply's saves are not requests. **Window**: saving one
with *Announce it now* creates an ordinary broadcast (warning, dismissable)
shown from now until the window starts, updated (and shown again) when the
window changes and deleted when it is cancelled; the read-only banner takes
over at the start. Audited as `maintenance.read_only.update` (changes,
before/after, source, reason, end, window, jobs). System health: a
**Read-only mode** check and the `oci_read_only` gauge. **Web**: a store
outside React Query (`useSyncExternalStore`) kept current by the banner
(polls `GET /api/maintenance`, public, every 30 s and on focus) and by any
423 the API client or the chat transport receives, so a write that raced the
switch shows the explanation and flips the page at once; the composer
(field, send, attach), Edit, Retry and Fork are disabled with the reason;
administration's `canEdit` is false while read-only (every `EditOnly`,
`EditableFieldset` and Save row), apart from the Maintenance section on
System health; personal Settings show the banner and a refused save shows
the explanation. Tests: the allowlist unit test; `read-only.live.test.ts`
(two instances, own module graphs, real routes, PostgreSQL and Redis: on from
A refuses on B at once with `Retry-After`, only the switch is allowed back, B
turns it off and A accepts writes; audit rows; a window announced, then 423
`schedule` on both at its start with `Retry-After` to its end and writes back
at its end; jobs paused, kept, chosen, and a running job stopped after its
batch when the switch on B reaches A); `read-only-reply.live.test.ts` (a
reply streaming when it is switched on finishes and is saved `complete`, the
next turn is refused before anything is stored, Stop still works); web
`read-only-mode.test.tsx`.

### 11. Connection pooling and read routing

Two pools:

- **Application pool**, safe behind a transaction-mode pooler such as
  PgBouncer: no session state, no prepared statements (already off), no
  session advisory locks.
- **Control pool**, a few direct or session-mode connections per replica, for
  migrations, advisory locks, `LISTEN` and jobs.

Every current use of session state moves to the control pool or is replaced.
Optionally, `READ_DATABASE_URL` sends heavy reads that tolerate a second of
staleness (search, admin reports and usage, exports) to replicas. A person's
own writes are never read back through it.

**As built** (`apps/api/src/db/{index,control,read,routing,replicas}.ts`,
`packages/db/src/client.ts` `createControlClient`; `docs/OPERATIONS.md`,
"Connection pooling"): `DATABASE_URL` is the application pool
(`DATABASE_POOL_MAX`, 10); `CONTROL_DATABASE_URL` (default `DATABASE_URL`)
serves short-lived control connections. The audit found five uses of session
state, all moved: a job's session advisory lock (one control connection per
running job), the worker's `LISTEN` (one per worker/`all` replica; `NOTIFY`
stays on the application pool, delivered at commit), `migrate --post` (session
lock and session `statement_timeout`/`lock_timeout`/`idle_in_transaction`),
pre-deploy migrations (transaction-scoped, so already safe; moved for clarity)
and `pg_dump`. Everything else was already transaction-scoped:
`pg_advisory_xact_lock` (quota, memory, embeddings storage, rollup fold),
`set_config(..., true)` (background batches, connectors), no temporary tables,
prepared statements off. Reproduced first against PgBouncer 1.25 in
transaction mode (`edoburu/pgbouncer`, MIT, pinned by digest; pool of two):
a second replica took a job the first held (the lock re-entered on the same
pooled server connection), an advisory lock stayed on a pooled connection,
a worker's `LISTEN` heard nothing in 10 s, and `migrate --post` left
`statement_timeout = 4h`, `lock_timeout = 3s` and
`idle_in_transaction_session_timeout = 10s` on a pooled connection. The live
test (`pgbouncer.live.test.ts`, starts PgBouncer itself in Docker, CI-able)
now passes: requests (thread routes, a transaction with `SET LOCAL` and an
xact lock), job locks with leases checked between busy batches, `LISTEN`,
post-deploy steps, background migration batches and the rollup fold, all
through PgBouncer, then every pooled server connection inspected for locks,
settings and channels. Not the whole suite: tests that open their own
sessions for locks or `LISTEN` would need a second URL each.
**Read routing**: `onReadReplica(work)` runs `work` with the shared `db` answering
from the replica (an `AsyncLocalStorage` scope behind a proxy, so services need
no new parameter); only `GET /api/admin/overview` and `GET
/api/admin/usage/*` use it (search and exports were left out: a person's own
search and export read what they just wrote; audit search shows an admin's own
change). The replica is used only while it has replayed the primary's WAL
position sampled `READ_DATABASE_MAX_LAG_MS` (1 s) earlier (sampled every 250 ms
while routed reads happen, stopped after a minute idle); behind, unreachable
or unchecked means the primary; a read failing there with a connection error
or a recovery conflict (40001) is run again on the primary. A write inside the
scope would fail on a real replica (25006) and be rerun on the primary: the
reports call `getDefaultOrganizationId`, which inserts the organization on an
instance that has none (never after `migrate` seeds it).

### 12. Kubernetes Helm chart

A first-party chart with: a pre-upgrade migration job and a post-upgrade
post-deploy job (Helm hooks), API and web deployments with rolling updates,
readiness and liveness probes, pod disruption budgets, a `preStop` drain
(section 13), optional horizontal autoscaling on OCI's metrics, a separate
worker deployment (section 14), and values for external PostgreSQL, Redis and
S3. The chart is tested in CI on a local Kubernetes (kind).

**As built** (`deploy/helm/open-chat-interface`, `deploy/helm/dev`,
`.github/workflows/helm.yml`; docs/OPERATIONS.md, "Kubernetes with Helm"):
released with the application (`release:check` ties `version`/`appVersion` to
the packages). Deployments `api` (`OCI_ROLE=web` with the worker, else `all`),
`worker` and `web`; no bundled PostgreSQL or Redis. Configuration is inline
environment and the runtime Secret arrives by `envFrom` (`existingSecret`;
`secrets.values` only for evaluation, rendered as a pre-install hook because
the pre-install migration needs it before any release resource exists, and
nothing is generated, since `helm template` users would get new keys).
`/api` stays behind the web pods' Caddy (the client-address boundary): the
API gets a headless Service so Caddy balances across pod IPs and its passive
check takes one draining pod out (with a ClusterIP upstream one `503` would
have taken out the whole API for 10 s), and a default ingress-only
NetworkPolicy admits only web pods and scrapers to the API. Hooks: `migrate`
(pre-install/upgrade, weight 0) and `migrate --post` (post-install/upgrade),
kept for their logs; the post hook's init container (Node in the API image,
no kubectl) waits until the API and worker rollouts are complete and **no pod
of them is still terminating**, with a token projected into that container
only and a Role (get the two Deployments, list Pods) that exists only during
the hook, so post-deploy steps never run beside release N-1 even without
`helm upgrade --wait` (Deployment status excludes terminating pods, so a
rollout looks complete while N-1 replicas are still draining; observed on
kind). The chart refuses `maxUnavailable` other than 0 and a grace period not
above drain plus `preStop`. Images allow read-only root filesystems with
emptyDir `/tmp`, attachments, and Caddy's `/data` and `/config`; the caddy
binary's `cap_net_bind_service` file capability makes `exec` fail under
`drop: [ALL]` with `no_new_privs`, so the web container keeps
`NET_BIND_SERVICE` in its bounding set (allowed by `restricted`, not
granted). kind (amd64 and arm64 in CI; arm64 locally, Kubernetes 1.37, the
namespace enforcing `restricted`): install in 10 s, `helm test`, the API
unreachable from other pods; `helm upgrade` to a new tag under load (two
requests every 50 ms through the web Service), both hooks, every Deployment
replaced: 3,156 requests, none failed; another run with an extra API rollout
restart, 3,460, none failed.

**arm64 images** (roadmap): `publish-containers.yml` builds each
architecture natively (`ubuntu-24.04`, `ubuntu-24.04-arm`) and pushes it by
digest, then joins them into one index pushed by digest only (the digest of
`imagetools create --dry-run`'s output; the registry refuses a mismatch), so
the existing verify-then-alias flow is unchanged; `ghcr-release.mjs` now
requires exactly linux/amd64 and linux/arm64 and checks each image's config
and labels. Both Dockerfiles build unchanged on arm64: the API has no native
addon at runtime (libpg-query is WebAssembly, PDF fonts are files,
`postgresql17-client` is in Alpine for both). Smoke-tested natively on arm64
and emulated on amd64: migrate, `migrate --post`, `all` and `worker` roles,
`/metrics`, and `/api/health/ready` 200 through Caddy, all with read-only root
filesystems.

## Further scale work

Beyond the roadmap items so far, in rough order of how much they matter for
"always on" at scale:

13. **Draining replies on shutdown.** Today a replica that stops ends the
    replies it is writing. On SIGTERM a replica should report not-ready at
    once, stop accepting new turns, let replies in progress finish (up to a
    configurable limit inside the pod's termination grace period), and, past
    the limit, save what it has with a resumable state so the person can
    continue. Without this, every rolling upgrade cuts off some replies.

    **As built:** on SIGTERM `/api/health/ready` answers 503, new turns are
    refused with 503, `Retry-After: 1` and `Connection: close` before anything
    is read (the web app retries twice), other requests are served with
    `Connection: close`, jobs start nothing new, and replies get
    `SHUTDOWN_DRAIN_TIMEOUT_MS` (25 s) before each is saved as interrupted
    (stored `cancelled` with a message), its stream ended and its usage
    settled; then the replica exits 0. Runs heartbeat in Redis (5 s) and
    PostgreSQL (10 s); a run silent in both for 20 s is recovered by a
    resuming reader, a new message or a job every 15 s. The bundled Caddy
    leaves a replica on a 503 or a 1 s dial failure and refreshes DNS every
    2 s. Upgrade test: restarts exit 0 in 0.6 to 3.9 s with no reply cut
    (before: killed at 30 s, three replies left streaming).
14. **A separate worker role.** `OCI_ROLE=web|worker|all` (default `all`).
    Embedding, imports, document rendering, compliance exports, backups and
    background migrations run on workers that scale separately and cannot
    take CPU from requests.

    **As built** (`lib/role.ts`, `worker-app.ts`, `services/jobs/requests.ts`,
    `services/jobs/workers.ts`): every job runs on `worker` and `all`, none on
    `web` (no job needs to run per web replica). Request-path work stays on
    `web`: replies, indexing an uploaded project file (its response reports
    the index), rendering a downloaded document (in-request, in a worker
    thread; nothing queues it), and recovering a stale reply when a reader or
    a new message finds it. Work requests used to start inline (an import, a
    webhook delivery, a summary, a new file's embedding) is queued as before
    and announced with `NOTIFY oci_job_requests`; workers `LISTEN` (and listen
    again after reconnecting) and run the job under its lock, once more if
    asked again meanwhile; the tick is the fallback. Run now, manual backups
    and manual compliance exports go the same way, and answer `409` when no
    worker is alive. A worker serves only `/api/health/{live,ready}` and
    `/metrics`, and on `SIGTERM` lets jobs finish the batch in hand within
    `SHUTDOWN_DRAIN_TIMEOUT_MS` (`all` keeps five seconds). Every replica
    heartbeats in Redis every 15 s; System health shows a Background workers
    check (error when no `worker`/`all` replica beat within 60 s, falling back
    to the 15-second sweep's job runs without Redis) and a Replicas list, and
    `web` replicas log a warning. Compose: an optional `worker` service
    (profile `worker`, with `OCI_API_ROLE=web`). The drill runs two `web`
    replicas and one worker.
15. **Provider capacity.** At this size the model provider's rate limits, not
    OCI, are the bottleneck. Shared limits per provider and model (requests
    and tokens per minute, concurrent streams) across replicas in Redis; a
    fair queue with a visible position instead of failures; retries with
    backoff on 429s; optional priority by role.

    **As built** (`services/limits/capacity/`, `services/providers/retry.ts`,
    `services/chat/capacity-wait.ts`; `docs/admin/models-providers.md`,
    "Provider capacity"; `docs/OPERATIONS.md`, "Provider capacity"): limits
    per provider and per model (requests and tokens per minute, replies at
    once) live in the instance setting `providerCapacity` (no migration);
    none set means nothing changes and no Redis key is written. Requests and
    tokens are token buckets refilled over a minute (as providers meter them;
    O(1) per check, and a token estimate can be settled afterwards, so the
    bucket may go below zero); replies at once are leases that lapse 30 s
    after their last renewal (every 10 s), so a crashed replica frees its
    slots. One queue per provider in Redis (`oci:capacity:{<provider>}:`,
    every change one Lua script timed by Redis's `TIME`), ordered by
    start-time fair queuing: a person's waiting turns are spaced 10 s apart
    (one person's many tabs take every other place at most), role priority
    moves a turn a minute ahead or behind (never a strict class, so nobody
    waits for ever). Admission walks the queue from the head: a turn blocked
    only by its own model's limit is passed over, one blocked by the provider
    stops the walk. A replica polls all its waiting turns in one script per
    provider four times a second; any replica's walk admits any turn, and a
    ticket lives only 10 s past its owner's last poll. The wait happens after
    the turn is stored and its stream begun, so the place (`data-capacity`,
    updated in place: position, estimate from admissions in the last minute)
    is replayed to a reader who reconnects anywhere; Stop (local or another
    replica's, through the Redis cancel flag) leaves the queue and releases
    the quota reservation (the model was never called); past the maximum
    wait (120 s, 5 to 1,800) the reply fails with "*model* is busy". A tool
    loop's later steps, retries and the context-overflow retry never queue
    again (re-queuing a reply people are reading, after its first steps were
    paid for, behind newcomers would be worse than letting it finish) but
    each is debited as a request, so newcomers wait longer instead. Draining:
    nothing is refused at the door (the turn is stored before it queues), so
    a draining replica hands its waiting turns back at once: the reply is
    saved `cancelled` with a reason, its tag is kept two minutes under
    `handoff:<prompt>`, the web app regenerates it (twice at most), the next
    replica takes the tag (its old place), and the empty reply is deleted in
    the regenerate transaction instead of becoming a second reply. Retries:
    every reply's provider requests, limits or not, are retried on 429, 408,
    409, 5xx or an "overloaded" first stream event, before the first output
    only (the stream is peeked up to its first content event), after
    Retry-After/retry-after-ms or 1, 2, 4 s with jitter, at most three
    retries within 60 s; this replaces the AI SDK's own two retries
    (`maxRetries: 0`), which honour Retry-After but cannot tell the limiter or
    retry an error event. A 429 on a limited model or provider pauses its
    admissions for the time asked (2 s if unsaid, 60 s at most): the
    provider's own signal, cheaper and more exact than lowering a rate
    estimate, and it lets admitted replies retry before newcomers meet the
    same refusal. Without Redis each replica enforces the whole limit with
    the same algorithm in memory (a store that fails mid-wait moves its
    waiters there, keeping order). Metrics `oci_provider_queue_*`,
    `oci_provider_throttled_total`, `oci_provider_retries_total`; System
    health has a Provider capacity check; the Providers tab edits limits and
    the queue's settings and shows each provider's queue now. Reproduced
    first: ten turns at once to a stub provider allowing two streams (429,
    `Retry-After: 1`) failed eight on the previous code; with the limit set,
    ten of ten completed, the provider refused none and never saw more than
    two at once. Two people (one with six turns, one with two, one stream):
    the second person's turns started second and fourth. Two replicas
    sharing Redis held one limit and admitted in queue order across them; a
    replica that died holding the slot freed it when its lease lapsed. Load
    (limiter only, two replicas, live Redis, eight streams, 193 turns of
    200 to 400 ms from 20 people, one sending 60 at once): 24.3 turns a
    second (91 % of the eight streams), never more than eight at once, the
    light senders' wait p50 1.8 s / p95 3.6 s against the heavy sender's
    6.6 s / 7.6 s, 1.5 ms per store call.
16. **Redis high availability.** With several replicas Redis is effectively
    required (reply streams, concurrency slots, shared rate limits). Support
    Sentinel and Redis Cluster, state what degrades when Redis is unavailable,
    and test a Redis failover.

    **As built** (`lib/redis.ts`, `services/chat-streams.ts`,
    `chat-stream-replay.ts`, `lib/redis-requirement.ts`, `db/replicas.ts`;
    `docs/OPERATIONS.md`, "Redis"; `docs/dev/failover.md`, "Redis"): one
    factory builds the only Redis client (`REDIS_URL`, `REDIS_SENTINELS` +
    `REDIS_SENTINEL_NAME`, `REDIS_CLUSTER_NODES`; auth and TLS for nodes and
    sentinels); `sharedRedis()` keeps its signature (a Cluster is typed as
    `Redis`; `sharedRedisClient()` has the real type). Commands never queue
    (`enableOfflineQueue: false`), are bounded (`REDIS_COMMAND_TIMEOUT_MS`,
    2 s) and are never resent after a reconnect; the client reconnects in the
    background and follows `+switch-master`, and callers fall back while it is
    away. A reply's capture keeps frames Redis could not take (30 s) and
    stores each at its own sequence number, so a lost answer is not doubled
    and events a promoted replica lacked are stored again; readers ride out
    an outage for 30 s; a resume waits 5 s for a reconnecting client.
    **Cluster**: a run's keys share its hash tag and the thread pointer has
    its own; publishing an admitted run and finalizing one run in two steps
    there. Tags are added on Cluster only, so key names on one server and
    Sentinel are unchanged and a rolling upgrade keeps replies resumable;
    replica heartbeats (new in v0.11) moved to `oci:{replicas}:…`.
    **Redis is required for more than one replica** (the open question:
    yes): without it each replica keeps a named connection open and counts
    the distinct `oci:<role>:<id>` `application_name`s in `pg_stat_activity`;
    with more than one, System health's Redis row is an error and each
    replica logs a warning (after 30 s, then every ten minutes). Without
    Redis: replies are not resumable, caps and rate limits count per replica,
    replicas are not listed; worker requests are unaffected (PostgreSQL
    `NOTIFY`). Reproduced first (`redis-reconnect.integration.test.ts`): a
    connection closed by the server mid-reply ended its reader with "Live
    replay is no longer available" after 31 of 84 frames, and Redis was not
    used for 30 s. Tests: that one (now every frame), a Sentinel failover in
    Docker (`SIGKILL` of the primary: promoted after 2.4 s, the client on it
    after 3.2 s, all 304 frames replayed once, 348 rate-limit checks with no
    failure), a three-primary Cluster (every operation; `CROSSSLOT` without
    the tags), and `failover-drill --redis` (two failovers: promoted after
    2.8 s and 3.3 s, the API on the new primary after 3.8 s and 3.7 s;
    1,439 requests, none failed; 210 replies stored complete; 70 partly read
    and resumed, 67 to the end and 3 answered `204` for a reply finished or
    never resumable; no process exited). Its first run found a reader that
    stopped short when PostgreSQL said the reply was finished while its tail
    waited for Redis; fixed.
17. **Backups at scale.** `pg_dump` takes hours and loads the primary on a
    large cluster. For clusters with their own backup (pgBackRest, WAL-G,
    point-in-time recovery), OCI's backups become "attachments and
    verification only", and the documentation covers recovery objectives and
    restore drills.
18. **Usage rollups.** Budgets and the Usage pages read usage events directly.
    A daily (and hourly) rollup maintained by a job keeps them fast at
    millions of events, with the raw events kept for their retention period.

    **Measured:** at `medium` the admin overview and usage pages take about
    2.7 s (p95) and grow linearly; at `large` they would take 10 to 15 s, so
    this comes before item 19. The overview also counts messages by day, and
    `message.created_at` has no index.

    **As built** (migration 0040, `packages/db/src/usage-rollups.ts`, the
    background migration `0.11.usage-rollups`,
    `apps/api/src/services/usage-report/source.ts`; `docs/dev/database.md`,
    "Usage rollups"): hourly, not daily, because report ranges start at any
    instant and days are local (display zone, budget zones); a daily table on
    top did not pay off. `usage_rollup_hour` (UTC hour, person or null for
    deleted accounts, model; report and budget amounts) and
    `usage_rollup_model_hour` (hour, model). Maintained by **statement
    triggers** on `usage_event` that append differences to
    `usage_rollup_change` in the writer's transaction (so the previous
    release during an upgrade, retention and the account-deletion `SET NULL`
    are covered), folded every 30 s by `usage.fold-rollups`. Not in the
    settlement transaction: a shared per-hour, per-model row made a
    reservation and settlement 7 times slower under 32 concurrent clients
    (17.4 ms against 2.5 ms; the triggers measured within noise of none).
    Readers are exact at any moment: one statement adds the rollups, the
    unfolded log and the events of the partial first hour (and of hours a
    local midnight falls inside, for half-hour zones). Rollups mirror the
    events, pruned by the same retention, holding only an account id that
    becomes null with the event's. The backfill marks events
    (`usage_event.in_rollup`, which every write also sets) so the triggers
    add them; until it finishes every reader uses the events. A live test
    compares both paths on generated data (deleted accounts, five models,
    pending and unknown usage, seven zones including +05:45 and Lord Howe,
    rolling, daily, weekly and monthly budgets, before and after folding,
    retention with a legal hold, a backfill through concurrent changes).
    Measured at `medium`: the Spend tab 777 ms to 39 ms (median; 90 days
    1.6 s to 43 ms), a heavy user's budget check 2.3 ms to 0.24 ms, backfill
    of 1 M events 293 s. The Overview tab is still 537 ms: its activity
    counts scan `message`, which is next. Release 0.12 is not made to require
    the backfill (nothing depends on it yet); the release that drops the
    fallback must name it in `releases.json`.
19. **Batched retention.** Conversation retention already works in batches
    of 500, but usage-event and audit-log pruning delete everything due in one
    statement per run. Deleting those in batches with pauses avoids long
    transactions and vacuum spikes; partitioning the largest append-only
    tables follows if the harness shows a need.
20. **Cross-replica cache invalidation.** Settings changes reach other
    replicas within 30 seconds. Publish invalidations over Redis so changes
    such as turning a feature off apply at once everywhere.

    **As built** (`services/cache-bus/index.ts`; `services/settings.ts`,
    `services/connectors/tools.ts`, `services/webhooks/endpoints.ts`;
    docs/OPERATIONS.md, "Settings changes and other replicas"): one channel
    per instance, `oci:cache-invalidate:<organization id>`; every replica
    (every role: a worker reads the read-only switch) opens one dedicated
    subscriber connection through the Redis client factory (one server,
    Sentinel, Cluster; classic pub/sub, which Cluster delivers on every
    node) and publishes on the shared command connection after the change is
    committed, ignoring its own messages. The audit of in-process caches:
    **settings** (one cache for every key: features, roles' features and
    tools, auth policy and session lifetime, branding, rate limits, provider
    capacity limits, read-only mode, retention, storage and its S3 driver,
    which follows the setting, search, SMTP, embeddings, reranking, backups,
    compliance) published by `updateSetting` and by `settingsChanged` (the
    embeddings switch, which writes the setting in its own transaction); the
    **connector catalogue** (10 s) and **webhook endpoints** (15 s), published
    by their existing invalidate functions. Not cached, nothing to do: the
    model catalogue, role access, SSO providers. Left alone: readiness flags
    (finished is permanent), the organization id, the `pg_dump` version, and
    Better Auth's signed session cookie cache (five minutes, in the browser,
    the authentication area). A read that overlapped an invalidation does not
    cache what it read (a generation counter), so it cannot keep the old
    value for the whole TTL. The TTLs stay as the fallback: without Redis, or
    while a subscription is away, changes arrive on expiry as before; a
    subscriber that subscribes again after being away clears everything,
    since pub/sub keeps nothing. System health's **Cache invalidation** check
    and the `oci_cache_invalidation_listening` gauge say whether the replica
    answering hears the others. Reproduced first
    (`cache-invalidation.live.test.ts`, two instances as separate module
    graphs sharing PostgreSQL and Redis): a feature changed on A was still
    read as before on B 2 s later, and so were webhook endpoints; with the bus
    B reads the change within milliseconds (feature switches, rate limits,
    webhook endpoints); with Redis unreachable B stays stale until the 30 s
    expiry and then reads it.
21. **Long conversations in the browser.** A conversation loads its whole
    history. Load the latest part first and the rest on scroll, and virtualise
    very long transcripts.

    **As built** (`services/chat/history-page.ts`, `routes/chat.ts`;
    web `lib/chat-history.ts`, `hooks/use-history-pages.ts`,
    `hooks/use-windowed-rows.ts`, `components/chat/message-list.tsx`;
    `docs/dev/browser-performance.md`, "Long conversations"):
    `GET /api/chat/:threadId/messages` answers in pages when given `limit`
    (default 100, at most 500), `before`, `after` or `around` (one of the last
    three), adding `page: { olderCursor, newerCursor, total, targetFound? }`;
    without them it returns the whole conversation as before, for v0.10
    clients, the share dialog and anything needing all of it (exports and
    share links read their own paths, unchanged). Pages are windows of the
    active path in `listConversation`'s order (position, created_at, id); a
    cursor is the id of the message at a page's edge, compared in SQL as a row
    value against the stored row (full timestamp precision), so it stays put
    as messages arrive; a cursor naming no message of the conversation is
    `422`. `replies` (the switcher's alternatives) come with any page that
    reaches the latest message. `around` gives about half before and the rest
    from the message, or the latest page with `targetFound: false` for a
    message not on the active path. Branches are separate conversations, so
    another branch's cursor is refused. A v0.11 web against a v0.10 API gets
    the whole conversation back (the parameters are ignored) and treats it as
    one page; recovery joins a refreshed latest page to what is loaded.
    The web keeps only the live part (latest page and everything since) in
    the AI SDK's state; earlier pages and a search result's window (an
    "island" above a gap, filled from either side) are held apart, so send
    detection, retries and recovery are unchanged. Earlier pages load when
    the reader nears the top (and from a **Load earlier messages** button,
    announced politely); the first message in sight keeps its place.
    Windowing is hand-rolled (no dependency): above 150 rows only rows within
    a view's height (at least 800 px) of the view are rendered, the rest are
    spacers of measured or estimated height; scroll anchoring is turned off
    then and a row above the view that changes height moves the view by as
    much. The opened search result, the focused row and the gap are always
    rendered. Trade-off: find in page sees only rendered rows; conversation
    search covers everything (`docs/user/conversations.md`). Reproduced first
    on a 2,000-message fixture: v0.10 transferred 1.05 MB, drew 143,894 DOM
    elements and held 138 MB of heap; v0.11 53 KB, 7,743 and 22 MB, ready in
    135 ms instead of 448 ms (474 ms against 1,776 ms with CPU ×4), and 792
    elements and 25 MB at the first message after loading every page. A
    `--gate` on the new runner fails v0.10 and passes v0.11. A partial index
    `message (thread_id, position, created_at, id) where superseded_at is
    null` would make the keyset scans index-only; not added (no migrations in
    this item), the existing `(thread_id, position)` index serves them.

    Also: a reply's search before answering (the Search toggle with a model
    not offered the web search tool) and links its tool calls returned are
    steps of its one work block ("Searched the web · 5 sources", "Sources ·
    2 links"; summary "Searched the web · thought"), replacing the separate
    "Searched the web" panel and "Search Grounding Details".
22. **Sign-in storms.** A term's first morning signs in thousands of people
    through single sign-on within minutes. The harness covers it; session
    creation and just-in-time provisioning are profiled and rate limited per
    identity provider rather than per address.

    **Measured:** Better Auth's own limiter is on in production: three
    sign-ins per address every 10 seconds, per replica. A campus behind one
    NAT would hit it before OCI's own limit. This item covers it.

    **As built** (`middleware/auth-rate-limit.ts`,
    `services/limits/rate-limit.ts`, `auth/index.ts`, `lib/threadpool.ts`;
    docs/OPERATIONS.md, "Sign-in limits"): Better Auth's limiter is off
    (`rateLimit.enabled: false`); OCI's, in Redis (fixed one-minute windows,
    per-process fallback without Redis), are the only ones, checked in order
    and stopping at the first refusal: an address ceiling (every limited
    request, 10 x the address allowance), the identity provider's budget for
    SSO callbacks (`RATE_LIMIT_AUTH_SSO_PROVIDER_PER_MINUTE`, 3,000), failed
    sign-ins per account (`RATE_LIMIT_AUTH_PER_MINUTE` / Roles & access, 10),
    password and email changes per session (same), then failed sign-ins and
    failed SSO callbacks per address (`RATE_LIMIT_AUTH_ADDRESS_PER_MINUTE`,
    300). Failures are counted on arrival and refunded on success (a 2xx
    sign-in; an SSO callback redirecting without `error=`), so a burst is
    bounded and successes cost nothing; a locked account's retries stop
    counting against its address. Sign-up, reset and verification requests
    count every request per account and per address. `auth.rate_limited`
    keeps its shape, with scopes `account`, `session`, `ip`, `ip-ceiling`,
    `provider` (and the provider). Reproduced first
    (`sign-in-storm.live.test.ts`, NODE_ENV=production): 50 people from one
    address in ten seconds, 3 signed in, 7 refused by Better Auth and 40 by
    OCI's per-address limit; now 50 of 50, while the eleventh wrong password
    for one account from the same address is refused. `sso-storm.live.test.ts`
    runs the real SSO plugin against the harness's stub OpenID Connect
    provider (`tools/scale/stub/oidc.mjs`): 20 people provisioned from one
    address, failed callbacks limited per address, a flooded provider refused
    while another signs people in. Harness (`run.sh --storm-only`, every user
    behind 4 addresses, `docs/dev/scale-harness.md`): before, 72 of 1,107
    password and 72 of 1,107 SSO sign-ins succeeded at 20/s; after, all, with
    p95 87 ms and 28 ms. Hot spots: statements are about 0.5 ms (password)
    and 1 ms (SSO) per sign-in; scrypt queued in libuv's four-thread pool at
    60/s (p95 3.7 s), fixed by sizing the pool per CPU (p95 71 ms); SSO
    provisioning rewrote the role on every sign-in (now only when changed).
    Also found: Better Auth's five-minute session cookie cache answered
    getSession from a signed cookie, and the API authorizes from it, so a
    demoted administrator, a ban or an ended session took up to five minutes
    to apply; the cache is off (`session-revocation.live.test.ts`, about 2 ms
    more per request in the test, one session read joined to its person).
23. **Encryption key rotation.** `ENCRYPTION_KEY` protects provider keys,
    connector credentials and backup credentials. Support a new key alongside
    the old one, re-encrypt in the background, then retire the old key, with
    no downtime.

    **As built** (`lib/crypto.ts`, `services/encryption/rotation.ts`,
    `packages/db/src/background/reencrypt-secrets.ts`; docs/OPERATIONS.md,
    "Rotating ENCRYPTION_KEY"; docs/dev/database.md, "Encrypted secrets"): no
    migration. Every caller was found: `provider.encrypted_api_key`,
    `connector` (shared header value, OAuth client secret),
    `connector_account` (tokens, pending authorization),
    `webhook_endpoint.encrypted_secret`, and `encrypted…` fields in instance
    settings (storage, backups and compliance S3 secrets, web search keys,
    SMTP password). SSO client secrets are stored by Better Auth in
    `sso_provider.oidc_config` and were never encrypted with this key.
    Format: `oci:v1:<key id>:base64(iv | tag | ciphertext)`, the key id 12
    hex characters of HMAC-SHA256(key, a constant); a value without the
    prefix (all before v0.11) is tried with `ENCRYPTION_KEY` then each of
    `ENCRYPTION_KEYS_PREVIOUS` (GCM rejects a wrong key), so old data needs
    nothing. An unknown key id, a damaged value or no key that fits fails
    with a `SecretDecryptionError` naming what to configure. **Upgrade
    gate**: v0.10 reads only the old format, so v0.11 writes it (under the
    current key) until every 0.11 post-deploy step is finished, the
    generation-1 gate (`previousReleaseGone()`), checked at start-up and
    every 30 s on every replica. Re-encryption: five background migrations,
    `0.11.reencrypt-*`, one per table (rows locked, values not already under
    the current key rewritten, idempotent; the codec is registered by the
    API because the keys are in its environment), scheduled by
    `migrate --post` (moving pre-0.11 values to the new format) and, after a
    key change, by the `encryption.rotation` job, which restarts finished
    ones while their table holds values not under the current key (counted
    in SQL by key id). System health has an **Encryption keys** check
    ("Previous keys still in use: N values"; an error when a value needs an
    unconfigured key; says when `ENCRYPTION_KEYS_PREVIOUS` can go).
    `encryption-rotation.live.test.ts` fills every location the v0.10 way,
    checks the gate, runs `migrate --post`, rotates with a batch failing
    half-way through 600 values (the first batch committed with its cursor,
    nothing of the second, resumed to the end), removes the old key and then
    makes a model call to a stub that checks the key, uses a person's
    connector token and the shared credential, and signs an S3 request with
    the backup credential. The upgrade test re-enters the provider key while
    v0.10 still serves (stored in the old format; v0.10's chats keep working)
    and checks every secret is versioned after `migrate --post`.

## Open questions

- Which latency and throughput targets define "meets the scale"? Proposed:
  p95 under 300 ms for sidebar and conversation opening, reply start under
  1 s added by OCI, search under 1 s at the `large` profile.
- Is Redis formally required for more than one replica? Proposed: yes, from
  v0.11.
- Should background migrations be controllable from System health by any
  administrator, or only through the command line?
- Which Qdrant versions to support, and whether its gRPC or HTTP API is used.
- Where the scheduled Patroni drill and harness run (a self-hosted runner is
  likely, since hosted runners are small).
