# v0.10 design: artifacts, summaries and PDF scripts

Four v0.10 items from the roadmap ("Now — v0.10"): a resizable artifact
panel, resuming very long artifact streams after a reload, reporting failed
summaries, and PDF export in every script. Decisions and what was built; the
v0.9 background is in [v0.9-design.md](v0.9-design.md) (Artifacts, Long
conversations, File output).

## Resizable artifact panel

| Question | Decision |
| --- | --- |
| Where | Only the docked panel (from 1024px). The phone/narrow dialog, share links and full screen are unchanged and render no handle. |
| Handle | A focusable `role="separator"` on the panel's left edge (8px hit area, a grip that shows on hover, focus and drag), `aria-orientation="vertical"`, `aria-controls` the panel, `aria-valuenow/min/max` in CSS pixels of the panel's width and `aria-valuetext` ("480 pixels wide"), named "Resize artifact panel". |
| Pointer | Pointer events with pointer capture, so a drag over the preview's sandboxed frame keeps reaching the handle. Moving left widens. The width is stored when the drag ends (a click without movement stores nothing). |
| Keyboard | Left/Up widen and Right/Down narrow by 32px (Shift: 128px), Home is the minimum, End the maximum, Enter restores the default. Double-click also restores it. Escape still closes the panel. |
| Limits | At least 22rem (352px), at most 70% of the window. A stored width is clamped to the current window on every render and window resize, so a smaller window never loses the conversation. |
| Default | Unchanged until the person resizes: CSS `w-[45%]`, `min-w-[22rem]`, `max-w-[56rem]` of the layout. The separator's value is then the measured width (ResizeObserver). Once resized, the width is an inline style and `max-w-[56rem]` no longer applies (70% of the window does). The full-screen placeholder keeps the same width. |
| Memory | `localStorage["oci.artifacts.panelWidth"]`, a number of pixels, per browser (not synced to the account: it depends on the screen). Restoring the default removes the key. Unreadable or blocked storage falls back to the default. |

Built in `components/artifacts/panel-resize.tsx` (pure clamping and key
mapping, the hook and the handle) and `artifact-panel.tsx`. Tests: unit
(`artifacts.test.tsx`, "resizing the docked panel": ARIA, keys, drag,
double-click, storage, absent in full screen and on phones) and e2e
(`tests/e2e/artifact-panel-resize.spec.ts`: drag by 120px, keys, reload keeps
the width, full screen has no handle, double-click resets; on the phone
project it checks the dialog has no handle).

## Long artifact streams after a reload

**The defect.** Redis keeps each reply's SSE frames in a stream trimmed to
about 10,000 entries (`XADD MAXLEN ~`). An artifact tool call streams its
input as one `tool-input-delta` per token, so a long artifact passes 10,000
events. A reload replays from the first stored event; once the head was
trimmed, the replay sees a sequence gap and answers "Live replay is no longer
available". Reproduced by `chat-stream-replay.integration.test.ts`, "fails
without a snapshot once the oldest events are trimmed (the v0.9 defect)",
with the limit lowered to 40 events.

| Question | Decision |
| --- | --- |
| What is saved | A compact snapshot of the whole stream so far, not only the artifact's input: every frame, with consecutive text, reasoning and tool-input deltas of one part merged into one delta, and a tool call's input deltas dropped once its `tool-input-available` (the full input) arrived. Replaying it gives the AI SDK client the same message as replaying every event, including the text and steps before the artifact, which the trimmed head also lost. The draft of an artifact still being written is therefore one `tool-input-delta` with all its input so far (`chat-stream-snapshot.ts`). |
| Where | Redis, beside the run: `oci:chat-stream:run:<id>:snapshot`, `{ sequence, frames }`, with the run's TTL, written by a Lua script only while the run's metadata exists. Not PostgreSQL: the replay itself lives in Redis (no Redis, no resume), a draft table would rewrite up to 512 KiB per artifact every few seconds for nothing, and **no migration** is needed (pre-deploy safe: older API processes ignore the key). |
| How often | Every `maxEvents / 4` events (2,500 in production), counted, not timed. Redis's approximate trimming never keeps fewer than `maxEvents` entries, so the newest snapshot always reaches the oldest kept event and a replay can always continue from it. Replies under 2,500 events never write one. Each write is the whole snapshot (it grows with the reply); a 512 KiB artifact is about 50 writes over its stream. |
| Resume | The replay reads from the start as before. If the first kept event is not number 1 (trimmed), it reads the snapshot once; if the snapshot reaches the first kept event it sends the snapshot's frames, then continues from the event after the snapshot, skipping kept events it already covers. A missing, malformed or too-old snapshot is the same friendly failure as before. A reader that falls more than the limit behind while tailing still fails (unchanged; the limit is generous for a live reader). |
| Client | Nothing changes: the SDK's reconnect consumes ordinary frames. The artifact card and panel show the draft at once and continue live. |

`ChatStreamStore` takes `{ maxEvents }` (tests only) and `append(runId,
frame, snapshot?)` now returns the sequence number. Tests:
`chat-stream-snapshot.unit.test.ts` (merging, reused part ids, providerMetadata,
dropped tool input, unreadable frames, stored-snapshot validation) and four
integration tests through the real AI SDK transport (the defect, a reload
mid-artifact that receives the draft as one delta then live deltas and ends
with the same message as a full replay, a finished long reply, and a stale or
malformed snapshot).

## Failed summaries are reported

| Question | Decision |
| --- | --- |
| What is reported | Only manual requests ("Summarise earlier messages now"). Automatic summaries are never reported, as asked: the person did not ask, and the conversation carries on regardless. |
| Categories | `allowance` (spent when the request ran), `model_error` (the provider failed or refused, including a model gone or too small), `nothing_to_summarise` (by the time it ran), `timeout` (an abort or timeout anywhere in the error, its causes or a retry's attempts: the summary call's 120 s limit). |
| Storage | Migration `0037_compaction_failure`: `conversation_compaction_failure`, one row per thread (reason, the request's instructions, failed_at), cascading with the thread and owner. The queue row is deleted when work ends, so it cannot carry the report. Additive and re-runnable (pre-deploy safe). |
| When it is written | Model errors and timeouts at the first failed attempt; the existing retries (1, 5, 30 minutes) still run, and a later success removes the report. Nothing to summarise when the run finds nothing. A spent allowance: a manual request is now reported and dropped at once instead of waiting silently for up to a day (automatic ones still wait). |
| When it goes | Any later successful summary of the thread (automatic or manual), a new manual request (so Retry clears it immediately), or `DELETE /api/threads/:id/compaction/failure` (dismiss; idempotent; returns the state). |
| API | `GET /api/threads/:id/compaction` adds `failure: { reason, instructions, failedAt } \| null` (also in the 202 of `POST /compact`). The web client treats a missing field as null. |
| UI | `CompactionFailureNotice` under the conversation: a quiet `role="status"` line, "The summary you asked for could not be made." and the reason, with **Retry** (same instructions; not offered for nothing to summarise) and **Dismiss**; a failed Retry or Dismiss shows the API's message (`role="alert"`). The state is read as before: polled while pending (3 s, two minutes) and after each reply. |

Tests: live (`chat-compaction.live.test.ts`, "failed summaries are reported":
model error with instructions then Retry, automatic never reported, timeout,
nothing to summarise, allowance, dismiss by owner only, cleared by a later
automatic success, error classification) and web unit (`compaction.test.tsx`).
The legal-hold path inventory lists the new deletion (exempt: a notice).

## PDF export in every script

**Before:** the PDF standard fonts, Windows-1252 only; everything else "?".

| Question | Decision |
| --- | --- |
| When fonts load | Only for a document with text Windows-1252 cannot draw (beyond the existing ASCII stand-ins such as "→"). Such a document uses embedded fonts for all its text; every other document is byte-for-byte the v0.9 output (standard fonts, nothing embedded). Fonts are read lazily, one slice at a time, when a character needs it; pdfkit embeds only the glyphs used. |
| Fonts | Noto, under the SIL Open Font License 1.1, from Fontsource's npm packages (pinned, integrity-checked by the lockfile, offline after install, no network at test or run time): Noto Sans (Latin, Latin Extended, Vietnamese, Greek, Cyrillic, Devanagari; 400/700, upright/italic), Noto Sans Arabic and Hebrew (400/700), the Arabic package's symbols and maths slices (arrows, box drawing, shapes), and Noto Sans SC, JP and KR (400 only; bold is a 0.035em outline). |
| Subset strategy | Fontsource ships each family as slices: per script, and for CJK about 120 frequency-ordered subsets of a few hundred characters (Google Fonts' slicing). `unicode.json` gives each slice's characters; a character's slice is found by range, then confirmed with fontkit (`hasGlyphForCodePoint`: Noto Sans SC's ranges list Hangul it lacks). WOFF, not WOFF2: fontkit cannot copy compound glyphs out of WOFF2's transformed glyph table (`RangeError` while subsetting). |
| Fallback per run | Each character takes the first family that has it: Noto Sans, Arabic, Hebrew, the document's CJK family, the other CJK families, symbols. The CJK preference is per document: Japanese if it has kana, Korean if it has Hangul, otherwise Chinese (simplified forms; the SC font also covers traditional characters). Combining marks stay with their base character's font. Consecutive characters with one font are drawn together, so fontkit shapes them. Code keeps Courier for Windows-1252 characters. |
| Shaping | pdfkit lays text out with fontkit, which applies OpenType shaping (Arabic joining forms, ligatures, mark positioning, Devanagari conjuncts) and reverses right-to-left scripts into visual order. That is enough for Arabic; no other shaping library is needed. A harfbuzz (WASM) build was not needed and would add megabytes. |
| Bidi | pdfkit has no bidirectional algorithm and wraps left to right, so right-to-left text could not use its wrapping. Documents that need the embedded fonts are laid out by `pdf-text.ts`: line breaking (spaces, hyphens, between CJK characters with simple kinsoku rules, overlong words split between characters), the Unicode Bidirectional Algorithm from `bidi-js` (MIT, 170 KB, pure JS) for embedding levels per paragraph, rule L2 per line, then each run drawn at its position on a common baseline. A right-to-left run of Arabic or Hebrew goes to fontkit in logical order (it reverses it); other runs at an odd level go in visual order with brackets mirrored. Paragraphs take the direction of their first strong character and align to that side; table columns keep their alignment (default: the cell's start side). |
| Emoji | No colour emoji: pdfkit cannot embed COLR/CBDT fonts, and a monochrome emoji font was not worth the size. Each emoji code point prints as U+FFFD; skin-tone modifiers, variation selectors and joiners are dropped (a ZWJ sequence prints one U+FFFD per component). Characters no font has also print as U+FFFD. |
| Image size | The packages install 205 MB (every weight, WOFF and WOFF2) in development. The API image keeps 10.3 MB: `apps/api/scripts/prune-pdf-fonts.mjs` runs after the build and deletes every file not in `PDF_FONT_FACES` (`pdf-font-faces.ts`, the same list the generator reads). The packages are `optionalDependencies`; without them, documents fall back to the standard fonts as before. |
| Licences | `OFL-1.1` added to the licence-check allowlist; `THIRD_PARTY_NOTICES.md` (repository root, copied to `/licenses/` in the API image) lists the fonts and their copyright lines; each package keeps its LICENSE in the image. |
| Limits | No italic for CJK, Arabic or Hebrew; list markers stay on the left in right-to-left lists; one CJK preference per document; no vertical text. Performance: about 110,000 mixed CJK/RTL characters lay out in ~1.2 s in the worker. |

Tests: `documents-pdf-scripts.unit.test.ts` renders English, Greek, Cyrillic,
Chinese (simplified and traditional), Japanese, Korean, Arabic, Hebrew and
emoji and checks, from the PDF itself (`pdf-inspect.ts` inflates the content
streams and reads each embedded font's ToUnicode map): no glyph drawn with
code 0 (`.notdef`, which pdfkit's subsets always keep at 0), which font each
script used, the CJK family per document, Arabic shaping (three distinct
positional forms, none the isolated one), right-to-left order with numbers,
brackets and Latin words, and wrapping from the right; PDF.js (unpdf) for the
text. Also tables, code, links, every block type, a long CJK document over
pages, Windows-1252 documents embedding nothing, the font book's fallback
when a slice file is missing, and (`documents-pdf-fallback.unit.test.ts`) the
fallback without the font packages.

## Not done (deferred)

- Resizing the panel by the person's account rather than per browser.
- Snapshots for a tailing reader that falls more than the limit behind (it
  already has the prefix; it would need a reset protocol the SDK lacks).
- Colour emoji in PDFs, italic for CJK/Arabic/Hebrew, right-to-left list
  markers, per-paragraph CJK preference.
