# v0.10 design: finish and harden

Status: **in progress**. Decisions and as-built notes for the v0.10 items
(ROADMAP.md, "Now — v0.10"), one section per item, in the style of
`v0.9-design.md`.

## Legal hold covers everything

| Question | Decision |
| --- | --- |
| Deleting a held person's project | **Refused** (409, *Deleting projects and project files is paused…*), like "delete forever". |
| Deleting a held person's project file | Refused, for the same reason. |
| Usage-event pruning | Skips held people's events. |
| Other deletion paths | Audited one by one; each either checks the hold or is listed as exempt with a reason, in a test that fails when a new deletion is added unclassified. |

### Refuse, or hide and keep?

Held conversations behave in two ways: moving to the trash works (the trash
is a place the person can see, restore from, and that a hold keeps), and
permanent deletion is refused. The question for a project is which of the
two its deletion is. Projects have no trash: deleting one destroys its files
at once (the conversations are detached and kept). So it is a permanent
deletion, and refusing it is the consistent choice.

The alternative, removing the project from view but keeping its row and files
until the hold lifts, would need a soft-delete state for projects and their
files that exists only under hold: a `deleted_at` on `project`, every project
query filtering it, the project search index and storage accounting taught to
ignore such files, and a job that destroys them when the hold lifts. That is a
project trash in all but name, with no way for the person to see or restore
it, built for a rare state. It also hides from the person that the data is
still there, which the hold message for conversations deliberately does not.
Refusing says plainly what is happening, costs one check, and matches the
existing message's promise ("Permanent deletion is paused for this account").

The same reasoning refuses deleting a project file (also outright, by design)
and deleting memory notes (no trash either; the `forget` tool and undoing a
saved note included). A chat file deleted on its own already goes to the
trash, so it still works and its purge waits for the hold.

### Every deletion path

`apps/api/src/__tests__/unit/legal-hold-paths.unit.test.ts` scans the API's
source for every row deletion (`db/tx.delete(…)`, `delete from`) and stored
object deletion (`driver.delete`), and requires each to be listed with how it
treats a hold. `apps/api/src/__tests__/live/legal-hold-paths.live.test.ts`
runs every `checked` row against PostgreSQL twice, for a held person
(refused, skipped or kept) and for someone not held (deleted), so it proves
both that the hold is checked and that the check is about the hold.

Found and fixed by the audit, besides project deletion and usage events:

- **Opening an expired temporary chat** deleted it on the spot
  (`getOwnedThread`), without the hold check the purge job had. It is now kept
  (and stays invisible) under hold.
- **Memory deletion by the person** (one, all, `forget`, undo) was not paused.
- **Share-link pruning** removed held people's expired and revoked links,
  which record what was shared, when and how often it was read.
- **Audit retention** now also keeps deletion events about a held person's
  data whose actor is a job or an administrator (they name the owner in
  `metadata.deletion.ownerUserId`, not as actor or target).
- **Better Auth's `/admin/remove-user`** deleted accounts without our checks
  (only the legal hold trigger applied) and without an audit entry. Nothing
  uses it; it now answers 404 and accounts are deleted only through
  `DELETE /api/admin/users/:id`.

Exempt, with the reason in the test: sessions, verification tokens,
invitations and connector credentials (credentials, not records); instance
configuration; queues (webhook deliveries, summary jobs, the storage reaper's
drained rows); work that never completed (a failed upload's row or object, the
provisional reply placeholder, a released usage reservation); the import
upload (what it imports becomes conversations, which are held); objects the
storage reaper deletes (only after a checked path removed the row); and the
compliance export's own objects. Backup retention is outside the scan
(`services/backups/`), as backups are copies, not records, and are covered by
their own retention.

Not paused, and documented: editing (renaming a conversation, a project's
instructions, a memory note's text). Editing is not deletion; message edits
already create branches rather than overwriting.

As built:

- `isOnLegalHold(userId, tx)` takes an optional transaction, so the project
  and memory checks run under the locks the deletion holds; `deleteProject`
  and `deleteProjectFile` check after locking the owner and the project.
- New messages `HELD_PROJECT_DELETION_MESSAGE` and
  `HELD_MEMORY_DELETION_MESSAGE` in `services/compliance/hold-errors.ts`.
- `pruneUsageEvents` and `pruneShareLinks` add `notOnLegalHold(...)`; no
  schema change.

## Deletions in the compliance export

| Question | Decision |
| --- | --- |
| Source | Audit entries. Every deletion path writes one normalised audit entry, so the existing exactly-once audit stream carries them. No second stream. |
| What | `conversation.trash`, `conversation.restore`, `conversation.delete`, `attachment.trash`, `attachment.delete`, `project.delete`, `memory.delete`, `user.delete`. Messages and artifacts are deleted only with their conversation, and are counted on its event. |
| Fields | Who (`actorUserId`, `actorEmail`; null for a job), when (`createdAt`), and `metadata.deletion`: `type`, `id`, `ownerUserId`, `ownerEmail`, `reason`, `permanent`, plus counts and ids of what went with it. |
| Content | Never: no titles, file names, project names or memory text, whatever the export's content setting. |
| Atomicity | The entry is written in the deleting transaction. |
| Schema | No migration. |

### Why audit entries, not a second stream

The audit stream already has everything the requirement needs: a sequence
number (`audit_log.seq`), a committed-watermark read that cannot pass an
in-flight transaction, a cursor moved only after verification, cleanup of
interrupted runs, and retention that keeps unexported entries. A deletion
stream would need its own table, sequence, cursor row (the
`compliance_export_cursor_stream` check allows only `audit` and `messages`, so
a migration), manifest field and retention rule, and a reviewer would have to
re-establish exactly-once for it. Many deletions also already wrote audit
entries (`memory.delete`, `user.delete`); a second stream would have split
them across two places. And as audit entries, deletions reach webhooks and
the audit log page for free, and appear in the same order as everything else
(a downstream archive sees `compliance.hold.lift` before the purge it allows).

The cost is that the audit log grows by one entry per deleted object.
Retention and trash purges delete in batches of 500, so a large first purge
writes that many entries per batch, in the same transaction; this is the same
order of volume as sign-in events and is pruned by audit retention like them.
Memory deletion moved from one entry per retention run (v0.9) to one per note,
so every deletion event names exactly one object.

### Normalised shape

`metadata.deletion` is identical across actions so a consumer can treat every
deletion the same way (`metadata ? 'deletion'`), while `action`, `targetType`
and `targetId` stay as before. Entries that existed before v0.10 keep their
old top-level fields (`user.delete`: `email`, `role`; `memory.delete`:
`count`, `via`, `memoryId`, and its target is still the owner).

`ownerEmail` and `actorEmail` are read in the transaction from the account,
because `audit_log.actor_user_id` is `ON DELETE SET NULL`: once an account is
deleted, its own entries lose the actor id, but still say whose data it was.

Children are counted, not listed: a conversation's event carries `messages`,
`attachments`, `artifacts`; an account's carries every kind it owned. They are
identified by their parent's id, which every exported message line carries
(`threadId`), so an archive with content on can mark them deleted. A project's
event lists `fileIds` (at most 20 files per project); project files are not
in the message stream.

### Never content

Audit entries are shown to administrators and auditors, sent to webhooks
(whose payload is the metadata) and outlive what they describe. Titles and
file names are content: people name conversations after what they are about.
The roadmap left open including them "where policy allows content"; we
decided against it even with **Include conversation content** on, because the
audit log and webhooks are not covered by that setting, and an archive with
content on already has titles and file names keyed by the same ids.

### Atomicity

`recordDeletions(tx, events)` (`services/compliance/deletions.ts`) inserts the
entries, and their webhook deliveries, through the deleting transaction.
`recordAudit` writes on its own connection and swallows errors (auditing must
never break the request); for deletions that would allow a deletion without
an entry, which is exactly the gap the export must not have. So a failure to
record fails the deletion, and a rolled-back deletion leaves neither an entry
nor a queued webhook (tested with a trigger that refuses the insert). All
reads in the helper go through the transaction: a second pooled connection
taken while the transaction holds one can deadlock a small or exhausted pool
(live tests that run with a single connection found exactly that).

Bulk deletions that used one unbounded `DELETE` (trash purge, temporary chat
expiry, empty trash) now go through `services/lifecycle/destroy.ts`: select a
batch of 500 with `FOR UPDATE` (`SKIP LOCKED` for jobs), counting what each
conversation holds, delete those rows, record their events, commit, repeat.

### Schema and indexes

No migration. Events are ordinary `audit_log` rows; the export reads them by
`seq` (unique index since 0034). Audit retention's legal hold clause gains a
comparison against `metadata->'deletion'->>'ownerUserId'` inside its existing
`NOT EXISTS` over `legal_hold` (a handful of rows, probed per candidate entry,
in a daily job), so no index on `audit_log` is needed for it; adding an
expression index on a large `audit_log` would need `CREATE INDEX
CONCURRENTLY` outside a transaction, which the v0.11 migration rules call for,
for no benefit on a hot path.

### As built

- Paths and their events: `softDeleteThread`, retention (`trashLockedThread`)
  → `conversation.trash`; `restoreThread` → `conversation.restore`;
  `purgeTrashedThread`, `emptyTrash`, `purgeExpiredTrash`,
  `purgeExpiredTemporaryThreads`, `getOwnedThread` (expired temporary chat) →
  `conversation.delete`; `deleteAttachment` → `attachment.trash`;
  `deleteProjectFile`, trash purge of loose files → `attachment.delete`;
  `deleteProject` → `project.delete`; `deleteMemory`, `deleteAllMemories`,
  `forgetMemory`, undo, `applyMemoryRetention` → `memory.delete`;
  `deleteUser` → `user.delete` (now written in the deleting transaction,
  before the row goes, with counts).
- Webhooks: `enqueueWebhookEventsIn(tx, entries)` reads enabled endpoints
  through the transaction and inserts deliveries in it.
- Tests: `__tests__/live/compliance-deletions.live.test.ts` (every path's
  event, atomicity, webhooks, retention under hold, exactly-once export across
  runs and a module reload, no content even with content export on).

## Authentication rate limit

`RATE_LIMIT_AUTH_PER_MINUTE` (and **Sign-in attempts per minute** on Roles &
access) was read by `authRateLimit` in `services/limits/rate-limit.ts`, which
nothing called; only Better Auth's built-in limiter ran, per process and only
in production. Reproduced by `__tests__/live/auth-rate-limit.live.test.ts`
(the fourth wrong password from one address answered 401, not 429).

As built: `middleware/auth-rate-limit.ts`, mounted on `/api/auth/*` before
Better Auth's handler (so the limit is applied to HTTP requests only, not to
server-side `auth.api` calls such as sending an invitation's verification
email). It counts `POST` sign-in (email, SSO), sign-up, password-reset request
and completion and send-verification, and `GET` verify-email and the reset
link, per trusted client address (`lib/client-ip.ts`; the socket address
without a proxy header) and per submitted email, in Redis with the existing
per-process fallback. Without either there is nothing to count by, rather
than one shared "unknown" counter anyone could exhaust. A refusal is a 429
with `Retry-After`, a body Better Auth's client can show (`message`) and the
API's usual `error` object; the first refusal per counter per window is
audited as `auth.rate_limited` and logged. The audit map also gains
`/request-password-reset`, the current name of the endpoint `/forget-password`
used to be.

## Backups include files

Before v0.10 a backup was a `pg_dump` and `attachments.jsonl` (key, size,
SHA-256 per attachment object): a backup alone could not restore attachments.

### What is copied, and where

- Attachment files, thumbnails and the uploaded instance logo (all stored
  through the storage driver). **Artifacts are in PostgreSQL** (`artifact`,
  `artifact_version.content`), so the dump already holds them. Exports are
  temporary and not backed up.
- Destination: the backup root (the reserved `.oci-backups/` prefix in the
  attachment bucket, or the separate bucket's prefix), under
  `objects/<sha256>`, beside the per-run folders.
- **Content addressed.** The name is the SHA-256 the manifest already records,
  so a copy is shared by every backup and every attachment with that content,
  the manifest is the only index needed, and a restore needs nothing but the
  folder. Per-run copies would multiply storage by the number of backups kept.

### How

- Copying happens while the manifest is generated, a page of 200 attachments
  at a time, four objects concurrently. For each object: checksum (cached in
  `backup_object_checksum`), `HEAD objects/<sha>`; if absent, stream the source
  (`getStream` on both the local and S3 drivers) into `putStream` (multipart,
  at most one 16 MiB part in memory). Two objects with the same content in one
  page copy once.
- The stream is hashed on the way; a mismatch (or a source read error) throws
  inside the source, which aborts the multipart upload, so a wrong copy is
  never stored under a SHA-256 name. The line is written as
  `missing: true` (with `error: 'checksum mismatch'`, and the stale cached
  checksum is dropped so the next run recomputes it). A destination error
  fails the run.
- New objects are read twice on their first backup (checksum, then copy).
  Accepted: it happens once per object, and avoids a temporary key plus a
  server-side copy that cross-bucket destinations could not do.
- A failed run deletes its folder but not its copies (shared by content); the
  sweep removes them if nothing references them.

### Verification ("the restore check")

After the dump and manifest checks, the stored `attachments.jsonl` is read
back and copies are re-read from the destination and checksummed: a uniform
random sample of 32 distinct files (reservoir sampling over the streamed
manifest), or every distinct file (`verifyFiles: 'all'`). Any mismatch or
missing copy fails the run. Sampling across all referenced files, not only
those copied this run, catches copies damaged or deleted later.

### Retention: mark and sweep

After `pruneBackups` (unchanged), the sweep:

1. reads `attachments.jsonl` of every retained, succeeded run at this
   destination and prefix **that copied files** (`copied_objects IS NOT NULL`),
   collecting referenced SHA-256s in a set (about 100 bytes per distinct file;
   a million files is about 100 MB, acceptable for a daily job; a database-side
   set is the upgrade path if that ever matters);
2. lists `objects/` (ListObjectsV2 with prefix, paginated) and deletes names
   that are a SHA-256, unreferenced, and last modified more than a day ago.

Safety: it runs inside `performBackup`, which always holds the `backups.run`
job lock (scheduled via the job runner, manual via `runExclusively`). The lock
is a PostgreSQL session lock that does not fence a backup whose connection
dropped, so the one-day grace keeps the sweep from deleting a copy whose
manifest is still being written (and makes S3 clock skew irrelevant). If any
retained manifest cannot be read, nothing is deleted. Only runs that copied
files count as references, so turning copying off lets copies age out. Two
instances sharing a prefix would delete each other's copies: documented as
unsupported. The sweep never fails a backup; it is retried after the next one,
and its count is stored on the run (`swept_objects`).

### Settings and defaults

`copyFiles` (boolean) and `verifyFiles` (`sample` | `all`) in the `backups`
setting. **On for a new configuration, off for an instance that saved backup
settings before v0.10** (detected by a non-empty stored setting without
`copyFiles`). Reason: the first copy can equal all attachment storage, doubled
in the attachment bucket with the default destination; it should be an
administrator's decision with the cost in front of them, not a side effect of
an upgrade. Existing instances get a clear notice on the Backups page while
copying is off, and the upgrade notes say how to turn it on. Saving settings
stores the value explicitly from then on.

### Data model and API

Migration `0035_backup_files`: nullable `copied_objects`, `copied_bytes`,
`skipped_objects`, `skipped_bytes`, `verified_objects`, `swept_objects` on
`backup_run` (NULL = the run did not copy files). `BackupRun.files` exposes
them; the history shows copied/already backed up (counts and bytes), read
back and swept. `manifest.json` gains
`files: { copied, folder: 'objects/', verification, copied/skipped counts }`.
The `backup.run` audit entry gains copied counts and bytes.

### Restore

`apps/api/src/services/backups/restore-files.ts` (covered by tests) with a thin
CLI, `src/scripts/restore-backup-files.ts` (`pnpm --filter @oci/api
backup:restore-files`, or `node dist/scripts/restore-backup-files.js` in the
image). It needs no database: it checks `attachments.jsonl` against
`manifest.json`, then streams each `objects/<sha>` to its key in local
(`--to-local`, new `LocalStorageDriver.putStream`: temp file + rename) or S3
(`--to-s3`) storage, verifying each checksum, skipping objects already present
unless `--overwrite`, with `--dry-run`. Credentials only from `BACKUP_S3_*` /
`TARGET_S3_*` environment variables. Exit 0, 1 (some failed), 2 (usage/setup).
The docs also give the equivalent `jq` + `aws s3 cp` loop.

### Deferred

- Server-side `CopyObject` when source and destination are the same bucket
  (the *Attachment storage bucket* destination): saves transfer, not storage.
- A database-side reference set for the sweep at very large file counts.
- Metrics for copied bytes (the run history and audit entry carry them).

## S3 suites in CI

### Server choice: VersityGW

| Option | Licence | Image | Fit |
| --- | --- | --- | --- |
| MinIO from pinned source | AGPL-3.0 | none published; build ~minutes | Works, but every run (or a separate GHCR publishing workflow with write permissions) pays for a Go build of a source-only, unmaintained community distribution. |
| SeaweedFS | Apache-2.0 | `chrislusf/seaweedfs`, ~180 MB | Full object store, but needs a command (`server -s3`) and an S3 config file, so cannot be a plain service container. |
| Garage | AGPL-3.0 | `dxflrs/garage` | Needs a layout and key created through its CLI before use. |
| **VersityGW** | **Apache-2.0** | **`versity/versitygw`, ~30 MB, multi-arch, maintained (v1.8.0, Sept 2026)** | **Configured entirely by environment, so it runs as a GitHub Actions service with a health check; starts in about a second.** |

Compatibility was verified, not assumed: the three S3 suites (storage driver,
backups including the new file tests, compliance export) ran against
`versitygw:v1.8.0` pinned by digest, posix backend on a tmpfs with sidecar
metadata (no dependency on the runner kernel's tmpfs xattr support), with
`CI=true`: 30 passed, 0 skipped. That covers multipart upload and abort,
ListObjectsV2 with prefix and continuation, HeadObject, CreateBucket,
path-style addressing and object-key validation. OCI does not use presigned
URLs or S3 checksum headers (it computes SHA-256 itself). One test asserted
MinIO's error name for a `..` key; it now asserts the HTTP 400 both servers
return. The suites still pass against the MinIO fixture.

### PostgreSQL 17 client tools

`postgresql-client-17` from apt.postgresql.org for noble, the key verified
against its published fingerprint before use, only that source list updated.
The major version is pinned and asserted (`pg_dump --version` 17.x) and passed
via `BACKUP_PG_BIN_DIR`. A minor pin was rejected: PGDG keeps only current
minors in the main repository, so it would break CI at each PostgreSQL release;
the archive repository has every version but resolves `libpq5` to betas.

### No silent skips

`OCI_COVERAGE_WITHOUT_S3` and the CI echo are gone; every floor applies in CI.
With `CI` set, `liveS3Available()` throws when S3 is unreachable, and the
backup suite always requires `pg_dump`, so a broken service fails the build
instead of quietly dropping coverage. New floors cover `backups/files.ts` and
`backups/restore-files.ts`.

### CI time

Measured locally: the S3 suites take about 6 s of test time; the service
image (30 MB) pulls in a few seconds alongside the others; the client-tools
step took 3 s in a clean `ubuntu:24.04` container (allow 20–30 s on a runner
for the key fetch and apt). Estimated addition: under a minute on a 22–26
minute job, well within the 45-minute limit; no parallelisation needed.

### Decisions

**Diagram accent.** `DIAGRAM_ACCENTS` in `@oci/shared` maps each colour theme
to its **light-mode** `--accent` from `tokens.css`, because diagrams are drawn
on light paper (`#f5f5f5`) whatever the app's theme: blue `#155dfc`, violet
`#7f22fe`, emerald `#007a55` (4.8:1 or better on the paper). Neutral's accent is
near-black (light) or near-white (dark); either would vanish against the ink
`#2d3142` or the paper, so neutral keeps Diagram Design's orange `#eb6c36`,
which is also every existing default instance's current colour (no change for
them). A web unit test converts the OKLCH tokens and fails if they drift from
the map.

**`accentColor`.** Kept as an **API-only override** for diagrams: a valid hex
set with `PATCH /api/admin/settings` wins over the theme; `null` returns to the
theme. The update schema now rejects anything but `#rgb[a]`/`#rrggbb[aa]`, so a
typo is a 400 rather than a silently ignored value. Removing it would have
dropped a working API field that an instance with a house colour may use.

**Favicon from the upload.** The uploaded logo is served same-origin at
`/api/branding/logo` (PNG/JPEG/WebP, cache-busted by key), so the client
points the `<link data-brand-icon>` elements (icon ×2, apple-touch-icon) at it
and drops their `type`/`sizes`, which describe the defaults. No server-side
scaling: browsers scale icons, and the upload is at most 1 MB. A linked
external logo keeps the Turns icon, so tabs do not fetch a third-party image.

**The default mark.** `TurnsMark` inlines `mark-small.svg` (the 20–47 px
drawing) from oci-assets `logo/turns` at commit 9ce4afe; the favicons are
copied unchanged. The tile mark reads on light and dark (logo README), is never
recoloured to the accent theme, and is `aria-hidden` beside the live-text name.
When a logo is uploaded it replaces mark and name as before.

**Page titles from the path.** `pageTitleFor` names pages without touching
the router: admin pages come from `NAV_SECTIONS`, so new admin pages are named
for free; a page with a better name (a shared conversation) calls
`usePageTitle`. `DocumentBranding` is mounted beside `RouterProvider` and reads
the router's location through `useRouterState({ router })`.

### Shared components touched (kept minimal)

- `components/layout/sidebar.tsx`: the header's link/wordmark and the right
  spacer only.
- `routes/share/public-share.tsx`: the header wordmark and a `usePageTitle` call.
- `services/documents/*` (render, worker, model, four generators): one
  `creator` field threaded through; no layout change.
- `services/export.ts`: an optional `source` argument to `renderMarkdown`.

### Tests

- Web unit: `branding.test.tsx` (wordmark default/compact/logo, title per

## Slow search providers

**What fails over.** A provider timeout, a network failure and, new in v0.10,
an HTTP 5xx are *transient* (`services/search/http.ts`): retried once (as in
v0.9) and then passed to the fallback provider. 401/403 (key), 429 (quota or
rate limit), other 4xx and invalid responses are the administrator's to fix,
so they fail at once and never reach the fallback. A search the caller
stopped (reply stopped, tool time limit) neither retries nor falls back.

**Time budget.** The `web_search` tool call is cut off at 30 s, so the whole
search, fallback included, still ends within `SEARCH_TOTAL_TIMEOUT_MS`
(25 s). Without a fallback nothing changes (15 s per attempt). With one, each
attempt at the first provider gets 8 s (`SEARCH_PRIMARY_ATTEMPT_WITH_FALLBACK_MS`)
and both together at most 17 s, so the fallback always has at least 8 s; it
gets up to 15 s per attempt from what remains and may itself retry once if
2 s or more are left. `searchWithFallback` in `services/search/index.ts`.

**Settings.** `search` gains `fallbackProvider`, `fallbackBaseUrl` and
`encryptedFallbackApiKey` (absent in older settings = no fallback). The
admin API returns `fallbackProvider`, `fallbackBaseUrl` and
`hasFallbackCredential`, never the key; the PATCH takes `fallbackProvider`,
`fallbackBaseUrl` and write-only `fallbackApiKey`. The same rules as the
primary: only what the chosen provider needs is stored, and switching the
fallback provider drops its key. The PATCH rejects (422) a hosted provider as
its own fallback and a SearXNG fallback at the primary's address, checked on
the merged result. A fallback missing its key or address is ignored at run
time (`fallbackSearchProblem`), and the setup checklist's web search detail
says why, without marking search unavailable. The settings audit diff
redacts `fallbackApiKey`/`encryptedFallbackApiKey` by name.

**Recording who answered.** `searchWeb` now returns `{ results, provider,
fallback }` (provider by display name). The `web_search` tool result carries
`provider` and `fallback: true` when the fallback answered; the tool step
summary then ends "· via Brave Search (fallback)". The pre-search
`data-search-grounding` part carries `provider` and `fallback`; the grounding
details show it. When both fail, the error is "<first error> The fallback
provider failed too: <second error>", each naming its provider.

**Test search** takes an optional `fallback` target and tests it separately
(in parallel, own retry budget, no fallback), so a failing primary does not
hide the fallback's result. The saved fallback key is used only when the
fallback provider on the page is the saved one. The `search.test` audit
entry adds `fallbackProvider` and `fallbackOk`.

**Observability.** Logs (`slot: primary|fallback`, provider, attempt,
duration, error message, "Web search falling back to the second provider")
never contain the query or a key. New metrics: `oci_web_searches_total
{provider, slot, outcome}` and `oci_web_search_duration_seconds{provider,
slot}`, counted for conversation searches only (not Test search).

**Tests.** `web-search-fallback.live.test.ts`: real database and admin API,
real HTTP to stub servers (two SearXNG stubs; Brave's fixed endpoint
redirected to a third stub so its key travels in the real header), covering
encryption/redaction, 5xx and unreachable fallback, both failing, no fallback
on 401, SearXNG-as-fallback, same-service refusal, incomplete fallback, and
Test search of both. Unit: timing budget, retry of 5xx, no fallback on
401/429, abort, availability rules.

## Clearer project search

**(a) Passages used.** The `data-project-search` part keeps its shape and
adds, per file, `excerpts: [{ id, first, last, heading?, snippet }]`:
`id` is `<attachmentId>:<first>-<last>`, `snippet` the first 200 characters
of the passage on one line (`PROJECT_EXCERPT_MAX_CHARS`, ellipsis when cut,
never splitting a surrogate pair), at most 24 per reply
(`PROJECT_EXCERPTS_MAX`, the first in file order; every passage is still
counted). This reverses the v0.8 rule "names and counts only, never passage
text" deliberately: the roadmap asks to show the passages, the text is the
person's own file, the part is still excluded from share links (allowlist in
`share-links.ts`), is not indexed by conversation search (text parts only)
and is bounded (about 5 KB). Replies stored earlier have no excerpts and
render as before, without the toggle.

Headings are not stored at index time. `passageHeadings` reads at most
4,000 characters before each passage (one query) and takes the first
Markdown-style heading inside the passage, else the last one before it.
Files without such lines (most PDFs and Word documents) get none. Failure
means no headings, never a failed reply.

The web note keeps its one-line summary and adds a **Show passages used**
toggle (`aria-expanded`/`aria-controls`) listing, per file, "Passage(s) n–m ·
heading" and the snippet.

**(b) Leaving files out.** `POST /api/chat` accepts optional
`excludedProjectFileIds` (at most 20, the per-project file limit). Before the
turn is claimed, `assertExcludableProjectFiles` requires the conversation to
be in a project and every id to be a file of that project owned by the
person (a file deleted since the composer listed it still passes); otherwise
422 and nothing is stored. Excluded files take no part in the turn at all,
whole or searched (simpler and more predictable than excluding only from
search). The part gains `excluded: [{ name }]`; with exclusions and no
searched passages the part is `{ mode: 'search', files: [], excluded }`, so
the reply always says what it did not look at.

Exclusions apply to one message. They are not stored, so regenerating a reply
and the continuation after a tool approval use every file (noted in the
user docs). The composer's **Files** control appears in a conversation (not
on the landing page) whose project has at least one indexed file, when the
role has projects; it lists all ready files with checkboxes (default all),
and the session sends the unticked ids with the next message and resets.

## Long artifact streams after a reload

**The defect.** Redis keeps each reply's SSE frames in a stream trimmed to
about 10,000 entries (`XADD MAXLEN ~`). An artifact tool call streams its
input as one `tool-input-delta` per token, so a long artifact passes 10,000
events. A reload replays from the first stored event; once the head was
trimmed, the replay sees a sequence gap and answers "Live replay is no longer
available". Reproduced by `chat-stream-replay.integration.test.ts`, "fails
without a snapshot once the oldest events are trimmed (the v0.9 defect)",
with the limit lowered to 40 events.

| Question | Decision |
| --- | --- |
| What is saved | A compact snapshot of the whole stream so far, not only the artifact's input: every frame, with consecutive text, reasoning and tool-input deltas of one part merged into one delta, and a tool call's input deltas dropped once its `tool-input-available` (the full input) arrived. Replaying it gives the AI SDK client the same message as replaying every event, including the text and steps before the artifact, which the trimmed head also lost. The draft of an artifact still being written is therefore one `tool-input-delta` with all its input so far (`chat-stream-snapshot.ts`). |
| Where | Redis, beside the run: `oci:chat-stream:run:<id>:snapshot`, `{ sequence, frames }`, with the run's TTL, written by a Lua script only while the run's metadata exists. Not PostgreSQL: the replay itself lives in Redis (no Redis, no resume), a draft table would rewrite up to 512 KiB per artifact every few seconds for nothing, and **no migration** is needed (pre-deploy safe: older API processes ignore the key). |
| How often | Every `maxEvents / 4` events (2,500 in production), counted, not timed. Redis's approximate trimming never keeps fewer than `maxEvents` entries, so the newest snapshot always reaches the oldest kept event and a replay can always continue from it. Replies under 2,500 events never write one. Each write is the whole snapshot (it grows with the reply); a 512 KiB artifact is about 50 writes over its stream. |
| Resume | The replay reads from the start as before. If the first kept event is not number 1 (trimmed), it reads the snapshot once; if the snapshot reaches the first kept event it sends the snapshot's frames, then continues from the event after the snapshot, skipping kept events it already covers. A missing, malformed or too-old snapshot is the same friendly failure as before. A reader that falls more than the limit behind while tailing still fails (unchanged; the limit is generous for a live reader). |
| Client | Nothing changes: the SDK's reconnect consumes ordinary frames. The artifact card and panel show the draft at once and continue live. |

`ChatStreamStore` takes `{ maxEvents }` (tests only) and `append(runId,
frame, snapshot?)` now returns the sequence number. Tests:
`chat-stream-snapshot.unit.test.ts` (merging, reused part ids, providerMetadata,
dropped tool input, unreadable frames, stored-snapshot validation) and four
integration tests through the real AI SDK transport (the defect, a reload
mid-artifact that receives the draft as one delta then live deltas and ends
with the same message as a full replay, a finished long reply, and a stale or
malformed snapshot).

## Failed summaries are reported

| Question | Decision |
| --- | --- |
| What is reported | Only manual requests ("Summarise earlier messages now"). Automatic summaries are never reported, as asked: the person did not ask, and the conversation carries on regardless. |
| Categories | `allowance` (spent when the request ran), `model_error` (the provider failed or refused, including a model gone or too small), `nothing_to_summarise` (by the time it ran), `timeout` (an abort or timeout anywhere in the error, its causes or a retry's attempts: the summary call's 120 s limit). |
| Storage | Migration `0037_compaction_failure`: `conversation_compaction_failure`, one row per thread (reason, the request's instructions, failed_at), cascading with the thread and owner. The queue row is deleted when work ends, so it cannot carry the report. Additive and re-runnable (pre-deploy safe). |
| When it is written | Model errors and timeouts at the first failed attempt; the existing retries (1, 5, 30 minutes) still run, and a later success removes the report. Nothing to summarise when the run finds nothing. A spent allowance: a manual request is now reported and dropped at once instead of waiting silently for up to a day (automatic ones still wait). |
| When it goes | Any later successful summary of the thread (automatic or manual), a new manual request (so Retry clears it immediately), or `DELETE /api/threads/:id/compaction/failure` (dismiss; idempotent; returns the state). |

## PDF export in every script

**Before:** the PDF standard fonts, Windows-1252 only; everything else "?".

| Question | Decision |
| --- | --- |
| When fonts load | Only for a document with text Windows-1252 cannot draw (beyond the existing ASCII stand-ins such as "→"). Such a document uses embedded fonts for all its text; every other document is byte-for-byte the v0.9 output (standard fonts, nothing embedded). Fonts are read lazily, one slice at a time, when a character needs it; pdfkit embeds only the glyphs used. |
| Fonts | Noto, under the SIL Open Font License 1.1, from Fontsource's npm packages (pinned, integrity-checked by the lockfile, offline after install, no network at test or run time): Noto Sans (Latin, Latin Extended, Vietnamese, Greek, Cyrillic, Devanagari; 400/700, upright/italic), Noto Sans Arabic and Hebrew (400/700), the Arabic package's symbols and maths slices (arrows, box drawing, shapes), and Noto Sans SC, JP and KR (400 only; bold is a 0.035em outline). |
| Subset strategy | Fontsource ships each family as slices: per script, and for CJK about 120 frequency-ordered subsets of a few hundred characters (Google Fonts' slicing). `unicode.json` gives each slice's characters; a character's slice is found by range, then confirmed with fontkit (`hasGlyphForCodePoint`: Noto Sans SC's ranges list Hangul it lacks). WOFF, not WOFF2: fontkit cannot copy compound glyphs out of WOFF2's transformed glyph table (`RangeError` while subsetting). |
| Fallback per run | Each character takes the first family that has it: Noto Sans, Arabic, Hebrew, the document's CJK family, the other CJK families, symbols. The CJK preference is per document: Japanese if it has kana, Korean if it has Hangul, otherwise Chinese (simplified forms; the SC font also covers traditional characters). Combining marks stay with their base character's font. Consecutive characters with one font are drawn together, so fontkit shapes them. Code keeps Courier for Windows-1252 characters. |
| Shaping | pdfkit lays text out with fontkit, which applies OpenType shaping (Arabic joining forms, ligatures, mark positioning, Devanagari conjuncts) and reverses right-to-left scripts into visual order. That is enough for Arabic; no other shaping library is needed. A harfbuzz (WASM) build was not needed and would add megabytes. |
| Bidi | pdfkit has no bidirectional algorithm and wraps left to right, so right-to-left text could not use its wrapping. Documents that need the embedded fonts are laid out by `pdf-text.ts`: line breaking (spaces, hyphens, between CJK characters with simple kinsoku rules, overlong words split between characters), the Unicode Bidirectional Algorithm from `bidi-js` (MIT, 170 KB, pure JS) for embedding levels per paragraph, rule L2 per line, then each run drawn at its position on a common baseline. A right-to-left run of Arabic or Hebrew goes to fontkit in logical order (it reverses it); other runs at an odd level go in visual order with brackets mirrored. Paragraphs take the direction of their first strong character and align to that side; table columns keep their alignment (default: the cell's start side). |
| Emoji | No colour emoji: pdfkit cannot embed COLR/CBDT fonts, and a monochrome emoji font was not worth the size. Each emoji code point prints as U+FFFD; skin-tone modifiers, variation selectors and joiners are dropped (a ZWJ sequence prints one U+FFFD per component). Characters no font has also print as U+FFFD. |
| Image size | The packages install 205 MB (every weight, WOFF and WOFF2) in development. The API image keeps 10.3 MB: `apps/api/scripts/prune-pdf-fonts.mjs` runs after the build and deletes every file not in `PDF_FONT_FACES` (`pdf-font-faces.ts`, the same list the generator reads). The packages are `optionalDependencies`; without them, documents fall back to the standard fonts as before. |
| Licences | `OFL-1.1` added to the licence-check allowlist; `THIRD_PARTY_NOTICES.md` (repository root, copied to `/licenses/` in the API image) lists the fonts and their copyright lines; each package keeps its LICENSE in the image. |
| Limits | No italic for CJK, Arabic or Hebrew; list markers stay on the left in right-to-left lists; one CJK preference per document; no vertical text. Performance: about 110,000 mixed CJK/RTL characters lay out in ~1.2 s in the worker. |

Tests: `documents-pdf-scripts.unit.test.ts` renders English, Greek, Cyrillic,
Chinese (simplified and traditional), Japanese, Korean, Arabic, Hebrew and
emoji and checks, from the PDF itself (`pdf-inspect.ts` inflates the content
streams and reads each embedded font's ToUnicode map): no glyph drawn with
code 0 (`.notdef`, which pdfkit's subsets always keep at 0), which font each
script used, the CJK family per document, Arabic shaping (three distinct
positional forms, none the isolated one), right-to-left order with numbers,
brackets and Latin words, and wrapping from the right; PDF.js (unpdf) for the
text. Also tables, code, links, every block type, a long CJK document over
pages, Windows-1252 documents embedding nothing, the font book's fallback
when a slice file is missing, and (`documents-pdf-fallback.unit.test.ts`) the
fallback without the font packages.

## Usage kept after deletion

**Before:** deleting an account (People, or the person in Settings → Account;
both run `deleteUser`) cascaded through `user_id` to the account's usage
events, daily totals and limit refusals. Instance cost and usage reports,
scheduled reports and budget history changed after the fact.

**Now:** usage history is kept with the link to the person removed. Nothing
that identifies them (name, email, ID, a pseudonym) is copied anywhere, so no
personal data remains in those rows.

| Table | On account deletion | Why |
| --- | --- | --- |
| `usage_event` (settled, and unresolved `usage_unknown`) | **Kept**, `user_id` null | The source of every usage report (totals, daily, per model, consumers). |
| `usage_event` with `pending = true` (a quota reservation) | Deleted, by `deleteUser` in its transaction | Live state: an estimate held for a run in progress, never in reports (`pending = false` everywhere). Nothing can settle it once the owner is gone. |
| `usage_record` (daily rollup) | **Kept**, `user_id` null | The long-lived usage record ("daily totals are always kept"). |
| `quota_denial` (daily refusals per limit) | **Kept**, `user_id` null | Usage → Limits history: why a limit was changed. |
| `quota_policy_override` | Deleted (cascade) | A person's limit; nothing to apply it to. |
| `storage_usage` | Deleted (cascade) | A live counter of the files the account held, which are deleted with it. |
| `audit_log` | Unchanged (actor set null, email kept) | Compliance and audit are out of scope. |

No role or other marker is kept: usage events never carried the person's role
(reports read it from the account), and adding one only for deleted accounts
would be a new column for little benefit.

Schema: migration `0038_usage_kept_after_deletion` makes `user_id` nullable
on the three kept tables and replaces each cascading key
(`<table>_user_id_user_id_fk`) with `<table>_user_id_set_null_fk`, `ON DELETE
SET NULL`. Pre-deploy safe: the previous release always writes `user_id` and
never deletes usage itself. `DROP NOT NULL` changes only the catalog; the new
key is added `NOT VALID` and the old key is dropped last. The new key is never
validated: validation scans the table, and because the migrator applies a
release's migrations in one transaction, the other statements' locks would be
held, and writes would wait, until the scan finished. It isn't needed: the old
key guaranteed existing rows, and a `NOT VALID` key is still enforced for new
and changed rows, with its `ON DELETE SET NULL` action. The Drizzle schema names
the keys explicitly (`keptAfterDeletion` in `schema/usage.ts`).

Consumers:

| Consumer | With `user_id` null |
| --- | --- |
| Usage totals, daily, per model, idle models, denials (Usage page, scheduled reports) | Included. `usageTotals` now also leaves out pending reservations, as every other figure already did. "People" / "Active people" and "people affected" count accounts that still exist: nothing is left to tell deleted people apart. |
| Top consumers (Usage → Spend, "Heaviest use" in scheduled reports) | One **Deleted accounts** row (`deleted: true`, no user ID, email or role) ranked with the rest; it counts once in the total behind the list. |
| Quota meters and enforcement (`windowTotalsIncludingPending`), admin user detail | Per person by `user_id`, so they never see them. There is no instance-wide budget to include them in. |
| Settlement and the reservation sweep | Lock the owner first, so they never touch an ownerless event; the sweep excludes them, and `settleLockedEvent` returns for one. |
| Usage-event retention | Prunes ownerless events by age, including unresolved ones (nothing can amend them). Legal hold unchanged: a held person cannot be deleted, so their events always have an owner. |
| Storage report, audit CSV | Do not read these tables. There is no usage CSV export. |

UI and docs: the delete dialogs (`AccountDeletionText`, shared by People and
Settings → Account) say usage records are kept without anything that
identifies the person; `docs/admin/people.md`, `docs/user/settings.md`,
`docs/admin/audit-reporting.md` and `docs/OPERATIONS.md` likewise.

Tests: `usage-kept-after-deletion.live.test.ts` (an administrator's deletion
keeps events, rollups and refusals without the person and removes the
reservation, override and storage counter, with instance and per-model totals
unchanged and no identifier in the kept rows; one Deleted accounts row and
unchanged per-person meters; the scheduled report; retention and the sweep;
migration 0038 on rows written before it, re-run, and the key's behaviour),
the self-deletion case in `account-settings.live.test.ts`,
`admin-user-delete.live.test.ts`, the settlement race in
`quota-settlement.live.test.ts` (now through `deleteUser`), and web unit tests
for the dialogs and the Deleted accounts row. They failed before the change.
