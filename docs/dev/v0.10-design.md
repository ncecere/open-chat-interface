# v0.10 design: finish and harden

Status: **in progress**. Decisions and as-built notes for the v0.10 items
(ROADMAP.md, "Now — v0.10"), one section per item, in the style of
`v0.9-design.md`.

## Legal hold covers everything

| Question | Decision |
| --- | --- |
| Deleting a held person's project | **Refused** (409, *Deleting projects and project files is paused…*), like "delete forever". |
| Deleting a held person's project file | Refused, for the same reason. |
| Usage-event pruning | Skips held people's events. |
| Other deletion paths | Audited one by one; each either checks the hold or is listed as exempt with a reason, in a test that fails when a new deletion is added unclassified. |

### Refuse, or hide and keep?

Held conversations behave in two ways: moving to the trash works (the trash
is a place the person can see, restore from, and that a hold keeps), and
permanent deletion is refused. The question for a project is which of the
two its deletion is. Projects have no trash: deleting one destroys its files
at once (the conversations are detached and kept). So it is a permanent
deletion, and refusing it is the consistent choice.

The alternative, removing the project from view but keeping its row and files
until the hold lifts, would need a soft-delete state for projects and their
files that exists only under hold: a `deleted_at` on `project`, every project
query filtering it, the project search index and storage accounting taught to
ignore such files, and a job that destroys them when the hold lifts. That is a
project trash in all but name, with no way for the person to see or restore
it, built for a rare state. It also hides from the person that the data is
still there, which the hold message for conversations deliberately does not.
Refusing says plainly what is happening, costs one check, and matches the
existing message's promise ("Permanent deletion is paused for this account").

The same reasoning refuses deleting a project file (also outright, by design)
and deleting memory notes (no trash either; the `forget` tool and undoing a
saved note included). A chat file deleted on its own already goes to the
trash, so it still works and its purge waits for the hold.

### Every deletion path

`apps/api/src/__tests__/unit/legal-hold-paths.unit.test.ts` scans the API's
source for every row deletion (`db/tx.delete(…)`, `delete from`) and stored
object deletion (`driver.delete`), and requires each to be listed with how it
treats a hold. `apps/api/src/__tests__/live/legal-hold-paths.live.test.ts`
runs every `checked` row against PostgreSQL twice, for a held person
(refused, skipped or kept) and for someone not held (deleted), so it proves
both that the hold is checked and that the check is about the hold.

Found and fixed by the audit, besides project deletion and usage events:

- **Opening an expired temporary chat** deleted it on the spot
  (`getOwnedThread`), without the hold check the purge job had. It is now kept
  (and stays invisible) under hold.
- **Memory deletion by the person** (one, all, `forget`, undo) was not paused.
- **Share-link pruning** removed held people's expired and revoked links,
  which record what was shared, when and how often it was read.
- **Audit retention** now also keeps deletion events about a held person's
  data whose actor is a job or an administrator (they name the owner in
  `metadata.deletion.ownerUserId`, not as actor or target).
- **Better Auth's `/admin/remove-user`** deleted accounts without our checks
  (only the legal hold trigger applied) and without an audit entry. Nothing
  uses it; it now answers 404 and accounts are deleted only through
  `DELETE /api/admin/users/:id`.

Exempt, with the reason in the test: sessions, verification tokens,
invitations and connector credentials (credentials, not records); instance
configuration; queues (webhook deliveries, summary jobs, the storage reaper's
drained rows); work that never completed (a failed upload's row or object, the
provisional reply placeholder, a released usage reservation); the import
upload (what it imports becomes conversations, which are held); objects the
storage reaper deletes (only after a checked path removed the row); and the
compliance export's own objects. Backup retention is outside the scan
(`services/backups/`), as backups are copies, not records, and are covered by
their own retention.

Not paused, and documented: editing (renaming a conversation, a project's
instructions, a memory note's text). Editing is not deletion; message edits
already create branches rather than overwriting.

As built:

- `isOnLegalHold(userId, tx)` takes an optional transaction, so the project
  and memory checks run under the locks the deletion holds; `deleteProject`
  and `deleteProjectFile` check after locking the owner and the project.
- New messages `HELD_PROJECT_DELETION_MESSAGE` and
  `HELD_MEMORY_DELETION_MESSAGE` in `services/compliance/hold-errors.ts`.
- `pruneUsageEvents` and `pruneShareLinks` add `notOnLegalHold(...)`; no
  schema change.

## Deletions in the compliance export

| Question | Decision |
| --- | --- |
| Source | Audit entries. Every deletion path writes one normalised audit entry, so the existing exactly-once audit stream carries them. No second stream. |
| What | `conversation.trash`, `conversation.restore`, `conversation.delete`, `attachment.trash`, `attachment.delete`, `project.delete`, `memory.delete`, `user.delete`. Messages and artifacts are deleted only with their conversation, and are counted on its event. |
| Fields | Who (`actorUserId`, `actorEmail`; null for a job), when (`createdAt`), and `metadata.deletion`: `type`, `id`, `ownerUserId`, `ownerEmail`, `reason`, `permanent`, plus counts and ids of what went with it. |
| Content | Never: no titles, file names, project names or memory text, whatever the export's content setting. |
| Atomicity | The entry is written in the deleting transaction. |
| Schema | No migration. |

### Why audit entries, not a second stream

The audit stream already has everything the requirement needs: a sequence
number (`audit_log.seq`), a committed-watermark read that cannot pass an
in-flight transaction, a cursor moved only after verification, cleanup of
interrupted runs, and retention that keeps unexported entries. A deletion
stream would need its own table, sequence, cursor row (the
`compliance_export_cursor_stream` check allows only `audit` and `messages`, so
a migration), manifest field and retention rule, and a reviewer would have to
re-establish exactly-once for it. Many deletions also already wrote audit
entries (`memory.delete`, `user.delete`); a second stream would have split
them across two places. And as audit entries, deletions reach webhooks and
the audit log page for free, and appear in the same order as everything else
(a downstream archive sees `compliance.hold.lift` before the purge it allows).

The cost is that the audit log grows by one entry per deleted object.
Retention and trash purges delete in batches of 500, so a large first purge
writes that many entries per batch, in the same transaction; this is the same
order of volume as sign-in events and is pruned by audit retention like them.
Memory deletion moved from one entry per retention run (v0.9) to one per note,
so every deletion event names exactly one object.

### Normalised shape

`metadata.deletion` is identical across actions so a consumer can treat every
deletion the same way (`metadata ? 'deletion'`), while `action`, `targetType`
and `targetId` stay as before. Entries that existed before v0.10 keep their
old top-level fields (`user.delete`: `email`, `role`; `memory.delete`:
`count`, `via`, `memoryId`, and its target is still the owner).

`ownerEmail` and `actorEmail` are read in the transaction from the account,
because `audit_log.actor_user_id` is `ON DELETE SET NULL`: once an account is
deleted, its own entries lose the actor id, but still say whose data it was.

Children are counted, not listed: a conversation's event carries `messages`,
`attachments`, `artifacts`; an account's carries every kind it owned. They are
identified by their parent's id, which every exported message line carries
(`threadId`), so an archive with content on can mark them deleted. A project's
event lists `fileIds` (at most 20 files per project); project files are not
in the message stream.

### Never content

Audit entries are shown to administrators and auditors, sent to webhooks
(whose payload is the metadata) and outlive what they describe. Titles and
file names are content: people name conversations after what they are about.
The roadmap left open including them "where policy allows content"; we
decided against it even with **Include conversation content** on, because the
audit log and webhooks are not covered by that setting, and an archive with
content on already has titles and file names keyed by the same ids.

### Atomicity

`recordDeletions(tx, events)` (`services/compliance/deletions.ts`) inserts the
entries, and their webhook deliveries, through the deleting transaction.
`recordAudit` writes on its own connection and swallows errors (auditing must
never break the request); for deletions that would allow a deletion without
an entry, which is exactly the gap the export must not have. So a failure to
record fails the deletion, and a rolled-back deletion leaves neither an entry
nor a queued webhook (tested with a trigger that refuses the insert). All
reads in the helper go through the transaction: a second pooled connection
taken while the transaction holds one can deadlock a small or exhausted pool
(live tests that run with a single connection found exactly that).

Bulk deletions that used one unbounded `DELETE` (trash purge, temporary chat
expiry, empty trash) now go through `services/lifecycle/destroy.ts`: select a
batch of 500 with `FOR UPDATE` (`SKIP LOCKED` for jobs), counting what each
conversation holds, delete those rows, record their events, commit, repeat.

### Schema and indexes

No migration. Events are ordinary `audit_log` rows; the export reads them by
`seq` (unique index since 0034). Audit retention's legal hold clause gains a
comparison against `metadata->'deletion'->>'ownerUserId'` inside its existing
`NOT EXISTS` over `legal_hold` (a handful of rows, probed per candidate entry,
in a daily job), so no index on `audit_log` is needed for it; adding an
expression index on a large `audit_log` would need `CREATE INDEX
CONCURRENTLY` outside a transaction, which the v0.11 migration rules call for,
for no benefit on a hot path.

### As built

- Paths and their events: `softDeleteThread`, retention (`trashLockedThread`)
  → `conversation.trash`; `restoreThread` → `conversation.restore`;
  `purgeTrashedThread`, `emptyTrash`, `purgeExpiredTrash`,
  `purgeExpiredTemporaryThreads`, `getOwnedThread` (expired temporary chat) →
  `conversation.delete`; `deleteAttachment` → `attachment.trash`;
  `deleteProjectFile`, trash purge of loose files → `attachment.delete`;
  `deleteProject` → `project.delete`; `deleteMemory`, `deleteAllMemories`,
  `forgetMemory`, undo, `applyMemoryRetention` → `memory.delete`;
  `deleteUser` → `user.delete` (now written in the deleting transaction,
  before the row goes, with counts).
- Webhooks: `enqueueWebhookEventsIn(tx, entries)` reads enabled endpoints
  through the transaction and inserts deliveries in it.
- Tests: `__tests__/live/compliance-deletions.live.test.ts` (every path's
  event, atomicity, webhooks, retention under hold, exactly-once export across
  runs and a module reload, no content even with content export on).

## Authentication rate limit

`RATE_LIMIT_AUTH_PER_MINUTE` (and **Sign-in attempts per minute** on Roles &
access) was read by `authRateLimit` in `services/limits/rate-limit.ts`, which
nothing called; only Better Auth's built-in limiter ran, per process and only
in production. Reproduced by `__tests__/live/auth-rate-limit.live.test.ts`
(the fourth wrong password from one address answered 401, not 429).

As built: `middleware/auth-rate-limit.ts`, mounted on `/api/auth/*` before
Better Auth's handler (so the limit is applied to HTTP requests only, not to
server-side `auth.api` calls such as sending an invitation's verification
email). It counts `POST` sign-in (email, SSO), sign-up, password-reset request
and completion and send-verification, and `GET` verify-email and the reset
link, per trusted client address (`lib/client-ip.ts`; the socket address
without a proxy header) and per submitted email, in Redis with the existing
per-process fallback. Without either there is nothing to count by, rather
than one shared "unknown" counter anyone could exhaust. A refusal is a 429
with `Retry-After`, a body Better Auth's client can show (`message`) and the
API's usual `error` object; the first refusal per counter per window is
audited as `auth.rate_limited` and logged. The audit map also gains
`/request-password-reset`, the current name of the endpoint `/forget-password`
used to be.

## Backups include files

Before v0.10 a backup was a `pg_dump` and `attachments.jsonl` (key, size,
SHA-256 per attachment object): a backup alone could not restore attachments.

### What is copied, and where

- Attachment files, thumbnails and the uploaded instance logo (all stored
  through the storage driver). **Artifacts are in PostgreSQL** (`artifact`,
  `artifact_version.content`), so the dump already holds them. Exports are
  temporary and not backed up.
- Destination: the backup root (the reserved `.oci-backups/` prefix in the
  attachment bucket, or the separate bucket's prefix), under
  `objects/<sha256>`, beside the per-run folders.
- **Content addressed.** The name is the SHA-256 the manifest already records,
  so a copy is shared by every backup and every attachment with that content,
  the manifest is the only index needed, and a restore needs nothing but the
  folder. Per-run copies would multiply storage by the number of backups kept.

### How

- Copying happens while the manifest is generated, a page of 200 attachments
  at a time, four objects concurrently. For each object: checksum (cached in
  `backup_object_checksum`), `HEAD objects/<sha>`; if absent, stream the source
  (`getStream` on both the local and S3 drivers) into `putStream` (multipart,
  at most one 16 MiB part in memory). Two objects with the same content in one
  page copy once.
- The stream is hashed on the way; a mismatch (or a source read error) throws
  inside the source, which aborts the multipart upload, so a wrong copy is
  never stored under a SHA-256 name. The line is written as
  `missing: true` (with `error: 'checksum mismatch'`, and the stale cached
  checksum is dropped so the next run recomputes it). A destination error
  fails the run.
- New objects are read twice on their first backup (checksum, then copy).
  Accepted: it happens once per object, and avoids a temporary key plus a
  server-side copy that cross-bucket destinations could not do.
- A failed run deletes its folder but not its copies (shared by content); the
  sweep removes them if nothing references them.

### Verification ("the restore check")

After the dump and manifest checks, the stored `attachments.jsonl` is read
back and copies are re-read from the destination and checksummed: a uniform
random sample of 32 distinct files (reservoir sampling over the streamed
manifest), or every distinct file (`verifyFiles: 'all'`). Any mismatch or
missing copy fails the run. Sampling across all referenced files, not only
those copied this run, catches copies damaged or deleted later.

### Retention: mark and sweep

After `pruneBackups` (unchanged), the sweep:

1. reads `attachments.jsonl` of every retained, succeeded run at this
   destination and prefix **that copied files** (`copied_objects IS NOT NULL`),
   collecting referenced SHA-256s in a set (about 100 bytes per distinct file;
   a million files is about 100 MB, acceptable for a daily job; a database-side
   set is the upgrade path if that ever matters);
2. lists `objects/` (ListObjectsV2 with prefix, paginated) and deletes names
   that are a SHA-256, unreferenced, and last modified more than a day ago.

Safety: it runs inside `performBackup`, which always holds the `backups.run`
job lock (scheduled via the job runner, manual via `runExclusively`). The lock
is a PostgreSQL session lock that does not fence a backup whose connection
dropped, so the one-day grace keeps the sweep from deleting a copy whose
manifest is still being written (and makes S3 clock skew irrelevant). If any
retained manifest cannot be read, nothing is deleted. Only runs that copied
files count as references, so turning copying off lets copies age out. Two
instances sharing a prefix would delete each other's copies: documented as
unsupported. The sweep never fails a backup; it is retried after the next one,
and its count is stored on the run (`swept_objects`).

### Settings and defaults

`copyFiles` (boolean) and `verifyFiles` (`sample` | `all`) in the `backups`
setting. **On for a new configuration, off for an instance that saved backup
settings before v0.10** (detected by a non-empty stored setting without
`copyFiles`). Reason: the first copy can equal all attachment storage, doubled
in the attachment bucket with the default destination; it should be an
administrator's decision with the cost in front of them, not a side effect of
an upgrade. Existing instances get a clear notice on the Backups page while
copying is off, and the upgrade notes say how to turn it on. Saving settings
stores the value explicitly from then on.

### Data model and API

Migration `0035_backup_files`: nullable `copied_objects`, `copied_bytes`,
`skipped_objects`, `skipped_bytes`, `verified_objects`, `swept_objects` on
`backup_run` (NULL = the run did not copy files). `BackupRun.files` exposes
them; the history shows copied/already backed up (counts and bytes), read
back and swept. `manifest.json` gains
`files: { copied, folder: 'objects/', verification, copied/skipped counts }`.
The `backup.run` audit entry gains copied counts and bytes.

### Restore

`apps/api/src/services/backups/restore-files.ts` (covered by tests) with a thin
CLI, `src/scripts/restore-backup-files.ts` (`pnpm --filter @oci/api
backup:restore-files`, or `node dist/scripts/restore-backup-files.js` in the
image). It needs no database: it checks `attachments.jsonl` against
`manifest.json`, then streams each `objects/<sha>` to its key in local
(`--to-local`, new `LocalStorageDriver.putStream`: temp file + rename) or S3
(`--to-s3`) storage, verifying each checksum, skipping objects already present
unless `--overwrite`, with `--dry-run`. Credentials only from `BACKUP_S3_*` /
`TARGET_S3_*` environment variables. Exit 0, 1 (some failed), 2 (usage/setup).
The docs also give the equivalent `jq` + `aws s3 cp` loop.

### Deferred

- Server-side `CopyObject` when source and destination are the same bucket
  (the *Attachment storage bucket* destination): saves transfer, not storage.
- A database-side reference set for the sweep at very large file counts.
- Metrics for copied bytes (the run history and audit entry carry them).

## S3 suites in CI

### Server choice: VersityGW

| Option | Licence | Image | Fit |
| --- | --- | --- | --- |
| MinIO from pinned source | AGPL-3.0 | none published; build ~minutes | Works, but every run (or a separate GHCR publishing workflow with write permissions) pays for a Go build of a source-only, unmaintained community distribution. |
| SeaweedFS | Apache-2.0 | `chrislusf/seaweedfs`, ~180 MB | Full object store, but needs a command (`server -s3`) and an S3 config file, so cannot be a plain service container. |
| Garage | AGPL-3.0 | `dxflrs/garage` | Needs a layout and key created through its CLI before use. |
| **VersityGW** | **Apache-2.0** | **`versity/versitygw`, ~30 MB, multi-arch, maintained (v1.8.0, Sept 2026)** | **Configured entirely by environment, so it runs as a GitHub Actions service with a health check; starts in about a second.** |

Compatibility was verified, not assumed: the three S3 suites (storage driver,
backups including the new file tests, compliance export) ran against
`versitygw:v1.8.0` pinned by digest, posix backend on a tmpfs with sidecar
metadata (no dependency on the runner kernel's tmpfs xattr support), with
`CI=true`: 30 passed, 0 skipped. That covers multipart upload and abort,
ListObjectsV2 with prefix and continuation, HeadObject, CreateBucket,
path-style addressing and object-key validation. OCI does not use presigned
URLs or S3 checksum headers (it computes SHA-256 itself). One test asserted
MinIO's error name for a `..` key; it now asserts the HTTP 400 both servers
return. The suites still pass against the MinIO fixture.

### PostgreSQL 17 client tools

`postgresql-client-17` from apt.postgresql.org for noble, the key verified
against its published fingerprint before use, only that source list updated.
The major version is pinned and asserted (`pg_dump --version` 17.x) and passed
via `BACKUP_PG_BIN_DIR`. A minor pin was rejected: PGDG keeps only current
minors in the main repository, so it would break CI at each PostgreSQL release;
the archive repository has every version but resolves `libpq5` to betas.

### No silent skips

`OCI_COVERAGE_WITHOUT_S3` and the CI echo are gone; every floor applies in CI.
With `CI` set, `liveS3Available()` throws when S3 is unreachable, and the
backup suite always requires `pg_dump`, so a broken service fails the build
instead of quietly dropping coverage. New floors cover `backups/files.ts` and
`backups/restore-files.ts`.

### CI time

Measured locally: the S3 suites take about 6 s of test time; the service
image (30 MB) pulls in a few seconds alongside the others; the client-tools
step took 3 s in a clean `ubuntu:24.04` container (allow 20–30 s on a runner
for the key fetch and apt). Estimated addition: under a minute on a 22–26
minute job, well within the 45-minute limit; no parallelisation needed.
