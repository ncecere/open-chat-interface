# Design: make and operate (v0.9)

The design behind the v0.9 roadmap items, recorded before building so the code
can be checked against it and later work can change it deliberately. SCIM was
moved to "Under consideration" and is not part of v0.9.

The releases before this one are deployed: an upgrade from v0.8.0 must work as
a rolling upgrade (migrations first, then API replicas), so no migration may
break code from v0.8.

## Long conversations: compaction

Today, when a conversation outgrows the model's input budget, the oldest turns
are dropped silently (`selectContextSuffix` in `context-budget.ts`) and the
reply is marked context-limited. v0.9 summarises them instead. The approach
follows the [pi coding agent](https://pi.dev)'s compaction (its
`docs/compaction.md`), adapted to chat.

| Question | Decision |
| --- | --- |
| When | Before a turn, when the history that would be sent exceeds the input budget. Also on request ("Compact conversation", with optional instructions), and once after a provider reports the input was too long, followed by one retry. An instance switch turns automatic compaction off (on by default). |
| What is kept | The most recent turns, verbatim, up to half the input budget (pi keeps a fixed 20k tokens; a share of the budget scales with the model). |
| Where to cut | Only at the start of a user turn: never between a tool call and its result, never inside a reply. If the newest turn alone exceeds the share, everything before it is summarised and that turn is kept whole. |
| Repeated compaction | The next summary is made from the previous summary plus the turns between the previous cut and the new one, so information carries forward instead of being re-derived from scratch. |
| Summary format | Fixed sections adapted to conversations: Topic and goal; Facts, figures and decisions; The person's preferences and constraints; Open questions and next steps; Critical details (names, numbers, code, quotations to keep verbatim). |
| Input to the summariser | A plain transcript (`[User]: …`, `[Assistant]: …`, `[Tool step]: …`) so the model does not continue the conversation; reasoning is left out; tool results are cut to 2,000 characters. |
| Model | The conversation's own model, so no extra configuration; the call counts towards the person's usage like a reply. |
| Storage | A compaction record per thread: summary, first kept message, messages and tokens summarised, reason (automatic, manual, overflow), usage, model, time. Messages are never deleted or changed. |
| What people see | A divider above the first kept message: "Earlier messages were summarised to fit the model", expandable to the summary. The full history stays visible, searchable, exported and shared. |
| Interaction with other features | Forks copy the compaction when its cut lies within the copied messages. Retried replies and the reply switcher only touch the latest turn, after any cut. Temporary chats compact like any other. |

## Meaning-based search for project files

v0.8 indexes project-file passages for keyword search. v0.9 adds vector
embeddings and merges the two rankings.

| Question | Decision |
| --- | --- |
| When it is used | Only when an administrator has configured an embeddings model **and** the database has the pgvector extension enabled. Otherwise search stays keyword-only, exactly as in v0.8. |
| pgvector | Enabled once by the operator (`CREATE EXTENSION vector`). OCI never creates it: managed databases often restrict extensions, and the official images that ship it are Debian-based (see Operations below). OCI detects it and reports it on System health. |
| Embeddings model | Configured under Providers & Models: an existing provider and a model id. Dimensions are read from a test embedding. |
| Storage | One embedding per passage and model, in its own table, created when meaning-based search is first enabled (the column type needs the extension). Changing the model re-embeds in the background. |
| Ranking | Reciprocal rank fusion of the keyword and vector top results, so exact names and codes still win while paraphrases are found. Searches stay within one project, so an exact (unindexed) vector scan is fast enough; no approximate index. |
| Cost | Embedding calls are usage events: passages to the file's owner when indexed, queries to the person asking. |
| Operations | Moving an existing Alpine-based PostgreSQL to a Debian-based pgvector image must be a dump and restore, not a reused data directory (C library collation differences can corrupt text indexes). Alternatively build pgvector into the Alpine image. Both are documented. |

## Artifacts

As in the roadmap: inline first, versioned, then model-editable through tools.

| Question | Decision |
| --- | --- |
| What becomes an artifact | HTML and SVG code blocks, Mermaid diagrams of at least a few lines, and documents the model creates through the artifact tools. Ordinary code blocks stay code blocks. |
| Storage | `artifact` (thread, title, kind) and `artifact_version` (content, created by message or person, time). Counts towards storage; follows the conversation's retention, export and deletion. |
| Display | A card in the reply opens a side panel (full screen on phones) with preview, source, version history, copy and download. |
| Sandbox | HTML and SVG render in an `iframe` with `sandbox="allow-scripts"` and no `allow-same-origin` (an opaque, throwaway origin) and a Content-Security-Policy that blocks all network access. The few libraries offered (for charts and diagrams) are inlined into the frame by OCI, never fetched. The same sandbox renders artifacts on share links. |
| Editing | Documents (Markdown) can be edited directly, which makes a new version. HTML and SVG change through the model. |
| Tools | With tool-capable models, `create_artifact` and `update_artifact` (full replacement or find-and-replace edits) make new versions instead of re-sending whole documents. They change only OCI's own data, so they need no approval. |
| Diagrams | When artifacts are on, the system prompt asks for diagrams as SVG artifacts following the Diagram Design style guide (MIT, attributed), mapped to the instance's colours. An administrator switch turns that guidance off. |
| Governance | A per-role `artifacts` switch (on except for `restricted`). Model-calling artifacts are not planned. |

## File output

Export a reply or an artifact as a document, built on the stored content.

| Format | From |
| --- | --- |
| DOCX | A reply or a Markdown artifact: headings, lists, tables, code, links. |
| PDF | The same, laid out server-side without a browser. |
| XLSX | Tables in a reply or artifact, one sheet per table. |
| PPTX | A Markdown artifact or reply, one slide per top-level heading. |

Libraries must be MIT/Apache and pure JavaScript (no headless browser).
Generation is server-side, size-limited, and counts towards the export rate
limit.

## User memory

| Question | Decision |
| --- | --- |
| Availability | Instance switch (off by default), per-role switch, and each person's own opt-in in Settings (off by default). |
| How memories are made | With a tool-capable model, `remember` and `forget` tools; the reply shows "Memory updated" with undo. People can also add, edit and delete entries in Settings → Memory. |
| How they are used | Included in the system prompt, newest first, up to a fixed share of the input budget. Never used or written in temporary chats. |
| Data | Visible, editable, deletable, included in the full export, and subject to a retention setting. Audited as metadata only. |

## Compliance export and legal hold

| Question | Decision |
| --- | --- |
| What | Audit events, and optionally conversation content (off by default), written as JSON Lines to S3-compatible storage on a schedule. |
| Format | One object per period, with a checksum and a manifest; each run continues from the last exported event, so nothing is skipped or duplicated. |
| Legal hold | Administrators place named people on hold. While held, retention, trash purging and account deletion skip that person's data. Placing and lifting holds are audited. |

## Observability and events

| Question | Decision |
| --- | --- |
| Metrics | A Prometheus endpoint (`/metrics`), off unless a scrape token is configured, covering requests, replies, tool calls, jobs, queue depth and errors. |
| Traces | OpenTelemetry over OTLP when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; no content in spans. |
| Webhooks | Administrators register HTTPS endpoints for selected audit actions. Payloads are signed (HMAC-SHA256), retried with backoff, and delivered by the job runner; outbound requests use the same guard as connectors. |

## Automated backups

| Question | Decision |
| --- | --- |
| What | A scheduled `pg_dump` and a snapshot of attachment objects, written to S3-compatible storage. |
| Retention | Keep a configurable number of daily and weekly backups. |
| Restore check | Each backup is verified (archive readable, checksums, object counts) and the result shown on System health. A full restore into a scratch database is documented, not automated. |
| Where it runs | In the API's job runner, so no new service; the API image gains the PostgreSQL client tools. Deployments that already back up their own way can leave it off. |
