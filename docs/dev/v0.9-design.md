# Design: make and operate (v0.9)

The design behind the v0.9 roadmap items, recorded before building so the code
can be checked against it and later work can change it deliberately. SCIM was
moved to "Under consideration" and is not part of v0.9.

The releases before this one are deployed: an upgrade from v0.8.0 must work as
a rolling upgrade (migrations first, then API replicas), so no migration may
break code from v0.8.

## Long conversations: compaction

Today, when a conversation outgrows the model's input budget, the oldest turns
are dropped silently (`selectContextSuffix` in `context-budget.ts`) and the
reply is marked context-limited. v0.9 summarises them instead. The approach
follows the [pi coding agent](https://pi.dev)'s compaction (its
`docs/compaction.md`), adapted to chat.

| Question | Decision |
| --- | --- |
| When | Before a turn, when the history that would be sent exceeds the input budget. Also on request ("Compact conversation", with optional instructions), and once after a provider reports the input was too long, followed by one retry. An instance switch turns automatic compaction off (on by default). |
| What is kept | The most recent turns, verbatim, up to half the input budget (pi keeps a fixed 20k tokens; a share of the budget scales with the model). |
| Where to cut | Only at the start of a user turn: never between a tool call and its result, never inside a reply. If the newest turn alone exceeds the share, everything before it is summarised and that turn is kept whole. |
| Repeated compaction | The next summary is made from the previous summary plus the turns between the previous cut and the new one, so information carries forward instead of being re-derived from scratch. |
| Summary format | Fixed sections adapted to conversations: Topic and goal; Facts, figures and decisions; The person's preferences and constraints; Open questions and next steps; Critical details (names, numbers, code, quotations to keep verbatim). |
| Input to the summariser | A plain transcript (`[User]: …`, `[Assistant]: …`, `[Tool step]: …`) so the model does not continue the conversation; reasoning is left out; tool results are cut to 2,000 characters. |
| Model | The conversation's own model, so no extra configuration; the call counts towards the person's usage like a reply. |
| Storage | A compaction record per thread: summary, first kept message, messages and tokens summarised, reason (automatic, manual, overflow), usage, model, time. Messages are never deleted or changed. |
| What people see | A divider above the first kept message: "Earlier messages were summarised to fit the model", expandable to the summary. The full history stays visible, searchable, exported and shared. |
| Interaction with other features | Forks copy the compaction when its cut lies within the copied messages. Retried replies and the reply switcher only touch the latest turn, after any cut. Temporary chats compact like any other. |

As built (deviations and details decided during implementation):

- **Where the summary goes.** A delimited `<conversation-summary>` section at
  the end of the system prompt, not a leading user message as in pi: the first
  kept message is always a user message, and a summary message before it would
  put two user messages in a row, which some providers refuse.
- **What is kept.** Recent turns up to half the input budget, or less when the
  system prompt, project files, the new message and room for the summary leave
  less. Overflow recovery and manual compaction also keep at most half of the
  history since the previous cut, so a request always summarises something
  once there are two turns (otherwise a short conversation could never be
  compacted by hand). A turn here is a user message and every reply to it;
  tool steps live inside replies, so cutting at user messages never separates
  a call from its result. pi's split-turn summary is not needed: the newest
  turn is always kept whole, as decided.
- **Trigger.** Compaction runs in turn preparation, under the reply's durable
  claim, whenever history would otherwise be trimmed (budget, the 128
  message / 512 KiB history ceilings, or the per-turn file ceiling). The
  approval continuation prepares its context the same way, so it compacts too.
  It is best effort: if the summary call fails the reply goes ahead with the
  oldest turns left out, as in v0.8.
- **Overflow.** Recognised conservatively: an `APICallError` (also inside a
  `RetryError` or `cause`) with status 400/413/422 or none, whose message or
  body matches known context-length phrases; rate limits are never matched.
  Only an error before any output is recovered: the stream is peeked from a
  copy, the turn is rebuilt from storage as a retry of the stored prompt
  (reusing its web search), compacted keeping at most half of the history, and
  streamed once more. The instance switch covers this recovery too. A reply
  continued after approvals first reports its approved or denied tool steps,
  so it is not retried (an approved write is never run twice); its context is
  still compacted before the call like any other.
- **Usage.** Each compaction's summary call is its own usage event (id = the
  compaction's id, `messageCount` 0, the conversation's model and prices), not
  part of the reply's: a manual compaction has no reply, so one mechanism
  covers all three triggers, and a reply's recorded tokens stay its own. A
  manual compaction is admitted against the person's allowance (refused when
  spent); one made during a reply belongs to a turn already admitted and is
  recorded without a second check, so the last allowed message can still be
  summarised.
- **Long backlogs.** The summariser's input is bounded by the model's budget:
  a larger backlog is summarised in up to four successive calls, each carrying
  the summary so far; turns beyond that (only on a first compaction of a very
  long, e.g. imported, conversation) are left out, oldest first. At most 2,000
  messages / 8 MiB are read per compaction. Attachments appear in the
  transcript by name only.
- **Storage.** `conversation_compaction` (migration 0028). "Tokens summarised"
  is an estimate (input units / 4); the summary call's measured tokens are
  stored beside it. The newest row is the one in use. A copied compaction in a
  fork carries no usage. The JSON export (per conversation) includes every
  compaction; Markdown exports and share links show only messages.
- **API and UI.** `GET /api/threads/:id/compaction`, and
  `POST /api/threads/:id/compact` `{ instructions?, modelSlug? }` (owner only,
  409 while a reply is generating, 422 with nothing to summarise, chat rate
  limit). The web client omits `modelSlug`, so the latest reply's model is
  used. "Compact conversation" is an icon button in the conversation's top-bar
  controls (there is no separate conversation menu).

## Meaning-based search for project files

v0.8 indexes project-file passages for keyword search. v0.9 adds vector
embeddings and merges the two rankings.

| Question | Decision |
| --- | --- |
| When it is used | Only when an administrator has configured an embeddings model **and** the database has the pgvector extension enabled. Otherwise search stays keyword-only, exactly as in v0.8. |
| pgvector | Enabled once by the operator (`CREATE EXTENSION vector`). OCI never creates it: managed databases often restrict extensions, and the official images that ship it are Debian-based (see Operations below). OCI detects it and reports it on System health. |
| Embeddings model | Configured under Providers & Models: an existing provider and a model id. Dimensions are read from a test embedding. |
| Storage | One embedding per passage and model, in its own table, created when meaning-based search is first enabled (the column type needs the extension). Changing the model re-embeds in the background. |
| Ranking | Reciprocal rank fusion of the keyword and vector top results, so exact names and codes still win while paraphrases are found. Searches stay within one project, so an exact (unindexed) vector scan is fast enough; no approximate index. |
| Cost | Embedding calls are usage events: passages to the file's owner when indexed, queries to the person asking. |
| Operations | Moving an existing Alpine-based PostgreSQL to a Debian-based pgvector image must be a dump and restore, not a reused data directory (C library collation differences can corrupt text indexes). Alternatively build pgvector into the Alpine image. Both are documented. |

As built (deviations and details decided during implementation):

- **Setting.** The `embeddings` instance setting holds provider id, model id,
  dimensions (measured by embedding a sample when the model is saved; a model
  that cannot embed cannot be switched on) and an optional input price. API:
  `GET/PUT /api/admin/embeddings` and `POST /api/admin/embeddings/test`, audited
  as `embeddings.update` and `embeddings.test`. The admin test embedding is not
  recorded as usage.
- **Storage.** One table, `project_file_embedding (attachment_id, ordinal,
  model_key, embedding vector(n))`, keyed by passage (cascading from
  `project_file_chunk`) rather than by passage *and* model: `model_key`
  (provider/model/dimensions) marks which model made each vector, searches only
  use the current model's, and re-embedding replaces vectors in place. A change
  of dimensions drops and re-creates the table. Creation and re-creation run
  under a transaction-scoped advisory lock, from the admin save and from the
  job (which reads the setting uncached so a lagging replica cannot recreate
  the previous size); the reply path never creates it.
- **Migration 0029** holds only `project_file_embedding_failure`, which needs no
  extension: files whose embedding failed are backed off (5 minutes, doubling,
  at most 6 hours) so they cannot block the job; a model change gives them a
  fresh start. A run stops after three files fail in a row.
- **Job and uploads.** `projects.embed-passages` (every 5 minutes) embeds at
  most 512 passages per run, in per-file requests of at most 64, each batch
  written as it completes. An upload embeds its first 128 passages itself.
- **Ranking.** Reciprocal rank fusion (k = 60) of the keyword top 20 and the
  vector top 20 comes first, followed by the fusion of the full lists to fill
  the budget. Fusing whole lists would bury the paraphrase: the vector list
  contains every passage, so anything sharing a common word with the message
  would appear in both lists and outrank it. A message with no searchable word
  is not embedded. The question's embedding has an 8-second timeout and no
  retry; any failure falls back to keyword ranking and is logged.
- **Reply note.** `data-project-search` gains an optional `ranking` field
  (`hybrid` or `keyword`) next to the existing `mode` (`search` or `opening`),
  rather than new `mode` values, so replies stored by v0.8 still parse.
- **Usage.** Events use the model name `embedding:<model id>` with no message
  counted; cost is zero unless a price is set.

### Optional reranking

A third, optional stage after keyword and vector search: a reranking model (a
cross-encoder) reads the question together with each candidate passage and
scores how well it answers it, which picks the best few passages far more
accurately than either ranking alone.

| Question | Decision |
| --- | --- |
| When it is used | Only when an administrator configures a reranking model. Off by default. It also works without pgvector, reranking keyword results. |
| API | The Cohere-compatible `POST …/rerank` endpoint (query, documents, top N → index and relevance score), served by LiteLLM gateways, vLLM, Hugging Face TEI, Jina and Cohere, called on an existing provider's address and key. No new dependency. |
| What is reranked | The top 40 candidates after rank fusion; passages are then packed into the context in reranked order. |
| Failure | A timeout (5 s) or error falls back to the fused order, logged, never failing the reply. |
| Cost | A usage event per reranked message, charged to the person asking; zero cost unless a price is set. |
| Display | The reply's project-search note says whether results were reranked. |

As built (deviations and details decided during implementation):

- **Setting and API.** A separate `reranking` instance setting (enabled,
  provider id, model id, optional price) with its own `GET/PUT
  /api/admin/reranking` and `POST /api/admin/reranking/test`, audited as
  `reranking.update` and `reranking.test`, rather than fields on the
  embeddings setting: reranking is independent of embeddings and pgvector. The
  section sits on the Embeddings tab. Switching it on (or changing its model
  while on) reranks a three-sentence sample first, as saving an embeddings
  model embeds one; the test reports latency and the resolved endpoint.
- **Which providers.** The endpoint is always `<base URL>/rerank`, so only
  providers with a base URL qualify: OpenAI-compatible providers, and OpenAI
  providers pointed at a gateway. OpenAI's own API, Anthropic and Google
  (whose Vertex AI ranking API has another shape and authentication) have no
  Cohere-compatible endpoint and are not offered.
- **Client.** Request `{model, query, documents, top_n}` with the provider key
  as a bearer token; responses accepted as `results[].relevance_score` (Cohere
  v1 and v2, Jina, vLLM, LiteLLM) or TEI's bare `[{index, score}]`; 5 s timeout
  including the body, 2 MB response limit, errors named by provider. Hugging
  Face TEI's own `/rerank` takes `texts`, not `documents`, so TEI is reached
  through LiteLLM rather than directly (deviation from the table above).
- **What is reranked.** Only search results (`mode: search`), not the opening
  passages used when nothing matched. The top 40 are reordered by score;
  candidates the model did not score follow them, then the rest of the list.
- **Reply note.** `data-project-search` gains an optional `reranked` boolean,
  present only when reranking is configured: `true` when it was used, `false`
  when it fell back. Replies stored before it still parse.
- **Cost.** Priced per 1,000 searches (one search = one reranked message, as
  Cohere bills) rather than per token, since most rerankers report no tokens.
  Events use `rerank:<model id>`, count no message, record reported tokens,
  and are recorded even without tokens.

## Artifacts

As in the roadmap: inline first, versioned, then model-editable through tools.

| Question | Decision |
| --- | --- |
| What becomes an artifact | HTML and SVG code blocks, Mermaid diagrams of at least a few lines, and documents the model creates through the artifact tools. Ordinary code blocks stay code blocks. |
| Storage | `artifact` (thread, title, kind) and `artifact_version` (content, created by message or person, time). Counts towards storage; follows the conversation's retention, export and deletion. |
| Display | A card in the reply opens a side panel (full screen on phones) with preview, source, version history, copy and download. |
| Sandbox | HTML and SVG render in an `iframe` with `sandbox="allow-scripts"` and no `allow-same-origin` (an opaque, throwaway origin) and a Content-Security-Policy that blocks all network access. The few libraries offered (for charts and diagrams) are inlined into the frame by OCI, never fetched. The same sandbox renders artifacts on share links. |
| Editing | Documents (Markdown) can be edited directly, which makes a new version. HTML and SVG change through the model. |
| Tools | With tool-capable models, `create_artifact` and `update_artifact` (full replacement or find-and-replace edits) make new versions instead of re-sending whole documents. They change only OCI's own data, so they need no approval. |
| Diagrams | When artifacts are on, the system prompt asks for diagrams as SVG artifacts following the Diagram Design style guide (MIT, attributed), mapped to the instance's colours. An administrator switch turns that guidance off. |
| Governance | A per-role `artifacts` switch (on except for `restricted`). Model-calling artifacts are not planned. |

## File output

Export a reply or an artifact as a document, built on the stored content.

| Format | From |
| --- | --- |
| DOCX | A reply or a Markdown artifact: headings, lists, tables, code, links. |
| PDF | The same, laid out server-side without a browser. |
| XLSX | Tables in a reply or artifact, one sheet per table. |
| PPTX | A Markdown artifact or reply, one slide per top-level heading. |

Libraries must be MIT/Apache and pure JavaScript (no headless browser).
Generation is server-side, size-limited, and counts towards the export rate
limit.

## User memory

| Question | Decision |
| --- | --- |
| Availability | Instance switch (off by default), per-role switch, and each person's own opt-in in Settings (off by default). |
| How memories are made | With a tool-capable model, `remember` and `forget` tools; the reply shows "Memory updated" with undo. People can also add, edit and delete entries in Settings → Memory. |
| How they are used | Included in the system prompt, newest first, up to a fixed share of the input budget. Never used or written in temporary chats. |
| Data | Visible, editable, deletable, included in the full export, and subject to a retention setting. Audited as metadata only. |

As built (deviations and details decided during implementation):

- **Storage.** `user_memory` (migration 0033): user, content (1-500
  characters, whitespace collapsed to one line), source (`tool` or `person`),
  the conversation and message a tool-made note came from (set to null when
  they are deleted, so a note outlives its chat), created and updated times.
  The person's opt-in is `user_preference.memory_enabled` (same migration),
  not a separate table. At most 200 notes per person, enforced under a
  per-person advisory lock; the same note (ignoring case and spacing) is never
  stored twice.
- **Switches.** The instance switch is `features.memory` (General settings,
  off; settings saved before v0.9 read as off). Because the features object
  is otherwise written whole, `memory` is optional in the PATCH so an older
  client cannot switch it off by leaving it out. The role switch is a new
  `memory` role feature (on except `restricted`), combined with the instance
  switch like the others. Reading and deleting notes always work (a person's
  data stays theirs to review and delete); adding, editing, switching on and
  restoring by undo need the instance and role to allow memory.
- **Tools.** `remember({content})` and `forget({id})` are built-in tools of
  kind `read` (no approval): they change only the person's own OCI data, the
  person opted in, and every change is shown with Undo, the same reasoning as
  the artifact tools. They are governed by the role's `memory` switch, so
  they are added by the registry beside the catalogue and are not listed (or
  separately switchable) under a role's tools. They are offered only when
  every switch allows memory and the chat is not temporary; each call checks
  again (switches and the thread's `temporary` flag) before writing.
  `forget` takes the 8-character id shown before each note in the prompt; a
  `remember` of an existing note returns `exists` and changes nothing.
- **Undo.** `POST /api/memory/undo {messageId, toolCallId}` reads the step's
  stored result from the person's own reply: an added note is deleted, a
  removed one restored under its old id. Repeating it changes nothing. The
  web client marks the note "Undone" locally; after a reload Undo is offered
  again and is harmless.
- **Prompt.** A `<user-memory>` section after the instance prompt,
  personalisation and project instructions, before any compaction summary,
  framed as notes about the person rather than instructions, one line per
  note with its id. Budget: 5% of the model's input budget, capped at 8 KiB
  (byte units). Notes are added newest (most recently updated) first and the
  first that does not fit ends the list. A note's text cannot open or close
  the section. Models without tool calling still get the section. Loading is
  best effort: a failure leaves memory out rather than failing the reply.
- **Retention.** `memoryRetentionDays` on the retention settings (null = off),
  applied by a daily `retention.memories` job by last update.
- **Audit.** `memory.add`, `memory.update`, `memory.delete` with count,
  source, `via` (`tool`, `settings`, `undo`, `retention`) and ids, never the
  text; `memory.settings.update` for the opt-in; one `memory.delete` per
  retention run with the count and number of people. Tool calls also produce
  the usual `tool.call` events.
- **Export.** `memory.json` in the full export (plus a count in the manifest
  and README), whatever the switches say.

## Compliance export and legal hold

| Question | Decision |
| --- | --- |
| What | Audit events, and optionally conversation content (off by default), written as JSON Lines to S3-compatible storage on a schedule. |
| Format | One object per period, with a checksum and a manifest; each run continues from the last exported event, so nothing is skipped or duplicated. |
| Legal hold | Administrators place named people on hold. While held, retention, trash purging and account deletion skip that person's data. Placing and lifting holds are audited. |

As built (deviations and details decided during implementation):

- **Cursor.** Timestamps and random UUIDs cannot order events exactly, so
  migration 0034 adds `audit_log.seq` (a sequence; existing entries numbered
  once in `(created_at, id)` order under the migration's exclusive lock) and
  `message.change_seq` (set by a trigger on insert and whenever parts,
  status, error or `superseded_at` change). Each stream's cursor is the last
  exported number (`compliance_export_cursor`). Sequence numbers alone allow
  a gap (a transaction draws 10, another draws 11 and commits first), so a
  run's upper bound is read under a brief `SHARE` lock, which waits for every
  transaction already writing to the table; the lock wait is bounded (2 s,
  three attempts), after which the run fails without moving the cursor.
- **Exactly once.** A run records its object keys before uploading, uploads,
  reads every object back (size, SHA-256, line count), writes the manifest
  last, then moves the cursors in the transaction that marks the run
  succeeded (conditional on the cursor not having moved). Failed runs delete
  their objects; runs a restart interrupted are found by their `running` row
  and cleaned up by the next run under the job lock. Audit retention keeps
  entries above the cursor while the export is on.
- **One object per stream per run** (`audit.jsonl`, `messages.jsonl`,
  `manifest.json` in a dated folder), not one per period; empty runs write
  nothing. Schedule: hourly or daily (a UTC hour).
- **Content (deviation: not retroactive).** Off by default. Turning it on
  starts the message stream from that moment; messages written before (and
  while it was off) are not exported, and existing messages are not numbered
  (no rewrite of `message`). Lines carry ids, roles, text, tool-step
  summaries (`summarizeToolPart`), file names and cited URLs; never reasoning,
  raw tool results, `data:` URLs or attachment bytes. A message still
  streaming is exported once it finishes; changes between runs collapse to
  the latest state. Deletions are not exported as content events.
- **Destination** reuses the backups destination code (now
  `destinationIssues`/`resolveDestination` in `services/backups/settings.ts`):
  the attachment bucket under `.oci-compliance/` (skipped by reconciliation)
  or a separate bucket with encrypted credentials. Exported objects are kept
  unless `keepDays` is set.
- **Audit.** `compliance.settings.update`, `compliance.hold.place` and
  `compliance.hold.lift` join the protected actions. `compliance.export.run`
  is recorded for manual runs and failures only: auditing every scheduled
  success would make every run export the previous run's entry.
- **Legal hold.** `legal_hold` rows (active while `lifted_at` is null; one
  active hold per person). Retention, trash purge (threads and attachments),
  temporary chat expiry and audit retention (entries by or about the person)
  skip held people; their own "delete forever" and "empty trash" are refused
  (moving to the trash still works); admin deletion is refused with a clear
  message, and a `BEFORE DELETE` trigger on `user` (SQLSTATE `OCLH1`) refuses
  it on every other path, including Better Auth's admin endpoints. Not
  covered: project deletion (its files are deleted at once) and usage-event
  pruning.

## Observability and events

| Question | Decision |
| --- | --- |
| Metrics | A Prometheus endpoint (`/metrics`), off unless a scrape token is configured, covering requests, replies, tool calls, jobs, queue depth and errors. |
| Traces | OpenTelemetry over OTLP when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; no content in spans. |
| Webhooks | Administrators register HTTPS endpoints for selected audit actions. Payloads are signed (HMAC-SHA256), retried with backoff, and delivered by the job runner; outbound requests use the same guard as connectors. |

As built (details decided during implementation):

- **Metrics.** A hand-written exposition (counters, histograms, gauges read at
  scrape time) rather than `prom-client`: OCI needs nothing else, and it adds
  no dependency. Served at the API root (`/metrics`, not `/api/metrics`), so
  the bundled Caddy does not forward it; scrape replicas directly. Without
  `METRICS_TOKEN` it answers 404; the token is compared as a SHA-256 digest in
  constant time. Labels are route templates, configured tool ids, job names
  and fixed vocabularies; never ids or raw paths. Queue depth is the webhook
  queue and the storage deletion queue; "errors" are `oci_errors_total`
  (unexpected server errors) plus 5xx statuses in the request counter. Reply
  metrics hook into the end of generation (`stream-response.ts`, one line),
  tool calls into `recordToolCall`, jobs into the job runner.
- **Traces.** The OpenTelemetry SDK (`sdk-trace-node`, OTLP/HTTP JSON exporter)
  is loaded with dynamic imports only when the endpoint is set. Spans for HTTP
  requests (named by route template, honouring an incoming `traceparent`),
  replies and tool calls (recorded after the fact with their measured start),
  jobs, backups and webhook deliveries. Errors set a status with a class name
  or HTTP status, never a message. No auto-instrumentation of outgoing calls.
- **Webhooks.** Configuration stays in the UI (endpoints) while metrics and
  traces are environment-only, shown read-only on System health. Actions are
  exact names or `prefix.*`, or all. The queue (`webhook_delivery`, migration
  0030) is filled by `recordAudit` itself (the audit id is generated in the
  application so the payload can carry it; the payload's `createdAt` is the
  application's clock); endpoints are cached for 15 s per process. Delivery is
  at least once: rows are leased (`FOR UPDATE SKIP LOCKED`, five minutes)
  before sending. Signature: `OCI-Webhook-Signature: v1=<hex HMAC-SHA256 of
  "<timestamp>.<body>">` with `OCI-Webhook-Timestamp`; the body is stored, so
  retries send identical bytes, re-signed. Retries: 8 attempts, 1 minute
  doubling to a 1-hour cap; refused addresses, schemes and redirects fail at
  once. Endpoints have the connectors' *Allow private network* switch (plain
  HTTP and private addresses; metadata addresses never). The payload is the
  audit entry without its IP address. The secret is shown once, on creation
  and rotation; rotation takes effect immediately (no overlap window).
  Webhook changes and `backup.settings.update` join the audit actions kept
  regardless of retention.

## Automated backups

| Question | Decision |
| --- | --- |
| What | A scheduled `pg_dump` and a snapshot of attachment objects, written to S3-compatible storage. |
| Retention | Keep a configurable number of daily and weekly backups. |
| Restore check | Each backup is verified (archive readable, checksums, object counts) and the result shown on System health. A full restore into a scratch database is documented, not automated. |
| Where it runs | In the API's job runner, so no new service; the API image gains the PostgreSQL client tools. Deployments that already back up their own way can leave it off. |

As built (deviations and details decided during implementation):

- **Attachments: a manifest, not a copy (deviation).** Each backup writes
  `attachments.jsonl` (key, size, SHA-256 of every file and thumbnail object;
  no names) instead of copying objects. Copying every object daily would make
  backups proportional to all uploads ever made; objects are immutable, so the
  manifest plus bucket versioning (or volume snapshots for local storage)
  gives the same restore guarantee. Checksums are cached in
  `backup_object_checksum`, so each object is read once. Incremental copying
  to the backup bucket is a possible later addition.
- **Destination.** Either the attachment bucket under the reserved
  `.oci-backups/` prefix (which storage reconciliation skips) or a separate
  bucket with its own encrypted credentials and prefix, recommended so one
  leaked or lost credential does not take the backups with the data. The
  separate option refuses the attachment bucket itself. Settings live in the
  `backups` instance setting; turning backups on is refused while the
  destination is incomplete or `pg_dump` is missing.
- **Schedule.** A daily hour (UTC); the `backups.run` job ticks every ten
  minutes and runs when today's slot has no scheduled attempt and no
  successful manual backup, so a missed slot is caught up. Manual runs share
  the job lock and run in the background.
- **Streaming.** `pg_dump --format=custom` streams into an S3 multipart upload
  (16 MiB parts, `S3StorageDriver.putStream`); the upload completes only if
  `pg_dump` exits 0. The password goes into a 0600 `.pgpass` in a private
  temporary directory, never into arguments or `PGPASSWORD`; the child gets a
  minimal environment, and output is scrubbed of the password.
- **Verification.** The stored archive is read back: size and SHA-256 must
  match, and `pg_restore --list` (fed from the stream) must list tables; the
  manifest's size, checksum and line count must match. A run failing any step
  is recorded as failed and its objects are deleted. Missing attachment
  objects do not fail a run; they are counted and warned about on System
  health. Archives written to a stream carry no data offsets, so restores are
  serial (no `pg_restore --jobs`).
- **Retention.** The newest backup of each of the last *n* days that have one,
  plus the newest of each of the last *m* ISO weeks (UTC); defaults 7 and 4.
  Only runs at the current destination are pruned; run rows stay as history.
- **History.** `backup_run` (migration 0030) rather than `job_run.details`, so
  object keys, sizes and checksums are queryable. Each run is audited as
  `backup.run` (actor for manual runs), so webhooks can alert on failures.
