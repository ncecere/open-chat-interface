# Design: make and operate (v0.9)

The design behind the v0.9 roadmap items, recorded before building so the code
can be checked against it and later work can change it deliberately. SCIM was
moved to "Under consideration" and is not part of v0.9.

The releases before this one are deployed: an upgrade from v0.8.0 must work as
a rolling upgrade (migrations first, then API replicas), so no migration may
break code from v0.8.

## Long conversations: compaction

Today, when a conversation outgrows the model's input budget, the oldest turns
are dropped silently (`selectContextSuffix` in `context-budget.ts`) and the
reply is marked context-limited. v0.9 summarises them instead. The approach
follows the [pi coding agent](https://pi.dev)'s compaction (its
`docs/compaction.md`), adapted to chat.

| Question | Decision |
| --- | --- |
| When | In the background, never in a reply's path (redesigned; see below): after a reply finishes, when the history the next turn would send passes a soft threshold (75% of the input budget), or when a turn already had to leave turns out. Also on request ("Summarise earlier messages now", with optional instructions). An instance switch turns automatic compaction off (on by default). |
| What is kept | The most recent turns, verbatim, up to half the input budget (pi keeps a fixed 20k tokens; a share of the budget scales with the model). |
| Where to cut | Only at the start of a user turn: never between a tool call and its result, never inside a reply. If the newest turn alone exceeds the share, everything before it is summarised and that turn is kept whole. |
| Repeated compaction | The next summary is made from the previous summary plus the turns between the previous cut and the new one, so information carries forward instead of being re-derived from scratch. |
| Summary format | Fixed sections adapted to conversations: Topic and goal; Facts, figures and decisions; The person's preferences and constraints; Open questions and next steps; Critical details (names, numbers, code, quotations to keep verbatim). |
| Input to the summariser | A plain transcript (`[User]: …`, `[Assistant]: …`, `[Tool step]: …`) so the model does not continue the conversation; reasoning is left out; tool results are cut to 2,000 characters. |
| Model | The conversation's own model, so no extra configuration; the call counts towards the person's usage like a reply. |
| Storage | A compaction record per thread: summary, first kept message, messages and tokens summarised, reason (automatic, manual), usage, model, time. Messages are never deleted or changed. |
| What people see | A quiet line above the first kept message: "Earlier messages are summarised for the model", expandable to the summary. The full history above it stays visible and unchanged, searchable, exported and shared. |
| Interaction with other features | Forks copy the compaction when its cut lies within the copied messages. Retried replies and the reply switcher only touch the latest turn, after any cut. Temporary chats compact like any other. |

As built (deviations and details decided during implementation):

- **Redesign: background compaction.** As first built, compaction ran in turn
  preparation under the reply's durable claim: a reply waited (up to minutes)
  for its summary, and a manual compaction was refused (409) while a reply was
  generating. People asked for it to happen in the background, never to stop
  them talking, and never to delete history. So summaries are now made only by
  a queue (`compaction-queue.ts`):
  - *Trigger.* After a reply completes, the history the next turn would send
    (the summary in use, every turn since its cut with files, the prompt and
    the reply, estimated as model context does) is compared with
    `SOFT_COMPACTION_RATIO` = 0.75 of that model's input budget
    (`compactionDue` in `compaction-plan.ts`). Three quarters leaves room for
    a few more turns while the summary is made, and compacting keeps at most
    half the budget, so the next check is comfortably below it. A turn that
    already had to leave turns out also queues one. The worker checks the
    threshold again (also counting three quarters of the 128-message and
    512 KiB history ceilings as due), so a stale or repeated automatic
    request is a no-op.
  - *Turns never wait.* A turn uses the latest recorded compaction. If its
    history still exceeds the budget it falls back to v0.8 for that turn only
    (oldest turns left out, reply marked context-limited) and queues a
    compaction.
  - *Queue.* `conversation_compaction_job`, one row per thread (idempotent).
    The `chat.compact-conversations` job runs every minute, and each request
    also starts a pass in-process at once. Workers claim a row with
    `for update skip locked` and a 15-minute lease (longer than the slowest
    summary, four 120 s calls), so several replicas or passes never summarise
    one thread twice and a restart's leftovers are taken over when the lease
    runs out. A manual request upgrades a waiting automatic one (instructions,
    run now); a repeat while one is waiting or running is the same request;
    an automatic request while one runs asks for one more (threshold-checked)
    run afterwards, because turns were added since it was planned. Failures
    retry after 1, 5 and 30 minutes, then drop; a refusal (model gone or too
    small) drops at once.
  - *No conversation locks.* The worker reads only the active path; the newest
    turn, possibly still generating, is always kept whole, so it never takes
    the reply claim and never causes a 409 for sending, retrying, switching
    replies or approving. Committing takes the thread row lock for a moment
    (as any write does) to order concurrent commits: the newest cut wins (a
    compaction is kept only if it reaches further than one recorded
    meanwhile; its summary carries everything before its own cut forward), and
    one whose input changed (a summarised message or its first kept message
    gone or off the active path, or the thread trashed or expired) is
    discarded. Trashing a thread deletes its queued request.
  - *Usage.* Every summary is admitted against the person's allowance; while
    it is spent the request waits (checked every 15 minutes, without
    recording quota denials, for a day). Manual requests check it up front
    (429), as well as "nothing to summarise" and "model too small" (422), so
    those answer at once; everything else completes in the background.
  - *Overflow.* A provider "too long" before any output is retried once with
    at most half of the history that was sent (oldest turns left out, marked
    context-limited) instead of compact-and-retry: it is error recovery while
    the person waits for the reply to start, and a summary call there (up to
    minutes) is exactly the wait this redesign removes. The retry needs no
    summary or new lock, so it is safe, and does not depend on the instance
    switch (it is not compaction); a compaction is queued as for any limited
    turn. The `overflow` compaction reason is gone.
  - *Migration.* Migration 0028 was edited in place (v0.9 had not shipped):
    it now also creates the queue table and allows only `automatic` and
    `manual` reasons. A development database migrated with an earlier v0.9
    build needs recreating.
  - *UI.* The action is "Summarise earlier messages now"; it returns 202 and
    the dialog closes at once. `GET /compaction` reports `pending` (running,
    or due now); the client checks every 3 s while pending, for at most two
    minutes, and reads it again after each reply. The divider is a quiet line,
    "Earlier messages are summarised for the model".
- **Where the summary goes.** A delimited `<conversation-summary>` section at
  the end of the system prompt, not a leading user message as in pi: the first
  kept message is always a user message, and a summary message before it would
  put two user messages in a row, which some providers refuse.
- **What is kept.** Recent turns up to half the input budget, or less when the
  system prompt, project files, the new message and room for the summary leave
  less (as first built; the background worker keeps up to half the budget).
  Manual compaction also keeps at most half of the history since the
  previous cut, so a request always summarises something
  once there are two turns (otherwise a short conversation could never be
  compacted by hand). A turn here is a user message and every reply to it;
  tool steps live inside replies, so cutting at user messages never separates
  a call from its result. pi's split-turn summary is not needed: the newest
  turn is always kept whole, as decided.
- **Trigger (superseded by the redesign above).** A turn queues a compaction
  whenever its history had to be trimmed (budget, the 128 message / 512 KiB
  history ceilings, or the per-turn file ceiling), and a finished reply queues
  one past the soft threshold. The approval continuation prepares its context
  the same way and is checked after it finishes like any reply.
- **Overflow.** Recognised conservatively: an `APICallError` (also inside a
  `RetryError` or `cause`) with status 400/413/422 or none, whose message or
  body matches known context-length phrases; rate limits are never matched.
  Only an error before any output is recovered: the stream is peeked from a
  copy, the turn is rebuilt from storage as a retry of the stored prompt
  (reusing its web search) with at most half of the history it sent, and
  streamed once more. A continued reply is rebuilt the same way, the reply
  being continued still last.
- **Usage.** Each compaction's summary call is its own usage event (id = the
  compaction's id, `messageCount` 0, the conversation's model and prices), not
  part of any reply's, so a reply's recorded tokens stay its own. It is
  admitted against the person's allowance (see the redesign above).
- **Long backlogs.** The summariser's input is bounded by the model's budget:
  a larger backlog is summarised in up to four successive calls, each carrying
  the summary so far; turns beyond that (only on a first compaction of a very
  long, e.g. imported, conversation) are left out, oldest first. At most 2,000
  messages / 8 MiB are read per compaction. Attachments appear in the
  transcript by name only.
- **Storage.** `conversation_compaction` (migration 0028). "Tokens summarised"
  is an estimate (input units / 4); the summary call's measured tokens are
  stored beside it. The newest row is the one in use. A copied compaction in a
  fork carries no usage. The JSON export (per conversation) includes every
  compaction; Markdown exports and share links show only messages.
- **API and UI.** `GET /api/threads/:id/compaction` → `{ compaction, pending }`,
  and `POST /api/threads/:id/compact` `{ instructions?, modelSlug? }` → 202
  with the same body (owner only, never 409, 422 with nothing to summarise or
  a model too small, 429 with the allowance spent, chat rate limit). The web
  client omits `modelSlug`, so the latest reply's model is used. "Summarise
  earlier messages now" is an icon button in the conversation's top-bar
  controls (there is no separate conversation menu).

## Meaning-based search for project files

v0.8 indexes project-file passages for keyword search. v0.9 adds vector
embeddings and merges the two rankings.

| Question | Decision |
| --- | --- |
| When it is used | Only when an administrator has configured an embeddings model **and** the database has the pgvector extension enabled. Otherwise search stays keyword-only, exactly as in v0.8. |
| pgvector | Enabled once by the operator (`CREATE EXTENSION vector`). OCI never creates it: managed databases often restrict extensions, and the official images that ship it are Debian-based (see Operations below). OCI detects it and reports it on System health. |
| Embeddings model | Configured under Providers & Models: an existing provider and a model id. Dimensions are read from a test embedding. |
| Storage | One embedding per passage and model, in its own table, created when meaning-based search is first enabled (the column type needs the extension). Changing the model re-embeds in the background. |
| Ranking | Reciprocal rank fusion of the keyword and vector top results, so exact names and codes still win while paraphrases are found. Searches stay within one project, so an exact (unindexed) vector scan is fast enough; no approximate index. |
| Cost | Embedding calls are usage events: passages to the file's owner when indexed, queries to the person asking. |
| Operations | Moving an existing Alpine-based PostgreSQL to a Debian-based pgvector image must be a dump and restore, not a reused data directory (C library collation differences can corrupt text indexes). Alternatively build pgvector into the Alpine image. Both are documented. |

As built (deviations and details decided during implementation):

- **Setting.** The `embeddings` instance setting holds provider id, model id,
  dimensions (measured by embedding a sample when the model is saved; a model
  that cannot embed cannot be switched on) and an optional input price. API:
  `GET/PUT /api/admin/embeddings` and `POST /api/admin/embeddings/test`, audited
  as `embeddings.update` and `embeddings.test`. The admin test embedding is not
  recorded as usage.
- **Storage.** One table, `project_file_embedding (attachment_id, ordinal,
  model_key, embedding vector(n))`, keyed by passage (cascading from
  `project_file_chunk`) rather than by passage *and* model: `model_key`
  (provider/model/dimensions) marks which model made each vector, searches only
  use the current model's, and re-embedding replaces vectors in place. A change
  of dimensions drops and re-creates the table. Creation and re-creation run
  under a transaction-scoped advisory lock, from the admin save and from the
  job (which reads the setting uncached so a lagging replica cannot recreate
  the previous size); the reply path never creates it.
- **Migration 0029** holds only `project_file_embedding_failure`, which needs no
  extension: files whose embedding failed are backed off (5 minutes, doubling,
  at most 6 hours) so they cannot block the job; a model change gives them a
  fresh start. A run stops after three files fail in a row.
- **Job and uploads.** `projects.embed-passages` (every 5 minutes) embeds at
  most 512 passages per run, in per-file requests of at most 64, each batch
  written as it completes. An upload embeds its first 128 passages itself.
- **Ranking.** Reciprocal rank fusion (k = 60) of the keyword top 20 and the
  vector top 20 comes first, followed by the fusion of the full lists to fill
  the budget. Fusing whole lists would bury the paraphrase: the vector list
  contains every passage, so anything sharing a common word with the message
  would appear in both lists and outrank it. A message with no searchable word
  is not embedded. The question's embedding has an 8-second timeout and no
  retry; any failure falls back to keyword ranking and is logged.
- **Reply note.** `data-project-search` gains an optional `ranking` field
  (`hybrid` or `keyword`) next to the existing `mode` (`search` or `opening`),
  rather than new `mode` values, so replies stored by v0.8 still parse. (Since
  the relevance floors below, new replies are always `search`.)
- **Usage.** Events use the model name `embedding:<model id>` with no message
  counted; cost is zero unless a price is set.

### Optional reranking

A third, optional stage after keyword and vector search: a reranking model (a
cross-encoder) reads the question together with each candidate passage and
scores how well it answers it, which picks the best few passages far more
accurately than either ranking alone.

| Question | Decision |
| --- | --- |
| When it is used | Only when an administrator configures a reranking model. Off by default. It also works without pgvector, reranking keyword results. |
| API | The Cohere-compatible `POST …/rerank` endpoint (query, documents, top N → index and relevance score), served by LiteLLM gateways, vLLM, Hugging Face TEI, Jina and Cohere, called on an existing provider's address and key. No new dependency. |
| What is reranked | The top 40 candidates after rank fusion; passages are then packed into the context in reranked order. |
| Failure | A timeout (5 s) or error falls back to the fused order, logged, never failing the reply. |
| Cost | A usage event per reranked message, charged to the person asking; zero cost unless a price is set. |
| Display | The reply's project-search note says whether results were reranked. |

As built (deviations and details decided during implementation):

- **Setting and API.** A separate `reranking` instance setting (enabled,
  provider id, model id, optional price) with its own `GET/PUT
  /api/admin/reranking` and `POST /api/admin/reranking/test`, audited as
  `reranking.update` and `reranking.test`, rather than fields on the
  embeddings setting: reranking is independent of embeddings and pgvector. The
  section sits on the Embeddings tab. Switching it on (or changing its model
  while on) reranks a three-sentence sample first, as saving an embeddings
  model embeds one; the test reports latency and the resolved endpoint.
- **Which providers.** The endpoint is always `<base URL>/rerank`, so only
  providers with a base URL qualify: OpenAI-compatible providers, and OpenAI
  providers pointed at a gateway. OpenAI's own API, Anthropic and Google
  (whose Vertex AI ranking API has another shape and authentication) have no
  Cohere-compatible endpoint and are not offered.
- **Client.** Request `{model, query, documents, top_n}` with the provider key
  as a bearer token; responses accepted as `results[].relevance_score` (Cohere
  v1 and v2, Jina, vLLM, LiteLLM) or TEI's bare `[{index, score}]`; 5 s timeout
  including the body, 2 MB response limit, errors named by provider. Hugging
  Face TEI's own `/rerank` takes `texts`, not `documents`, so TEI is reached
  through LiteLLM rather than directly (deviation from the table above).
- **What is reranked.** Only search results. The top 40 are reordered by
  score; candidates the model did not score follow them, then the rest of the
  list (unless the relevance floor below cuts the list first).
- **Reply note.** `data-project-search` gains an optional `reranked` boolean,
  present only when reranking is configured: `true` when it was used, `false`
  when it fell back. Replies stored before it still parse.
- **Cost.** Priced per 1,000 searches (one search = one reranked message, as
  Cohere bills) rather than per token, since most rerankers report no tokens.
  Events use `rerank:<model id>`, count no message, record reported tokens,
  and are recorded even without tokens.

### Relevance floors

Reported with real files: in a project holding a large staff handbook (200,000
characters after extraction, 255 chunks) and a research guide (41 chunks),
"write b tree in rust, go, zig" was answered with "Used passages from
northbrook-research-guide.md (1 passage), northbrook-staff-handbook.txt (54
passages)". Keyword search let any shared word match, and the passages filled
the whole share (half the input budget) whatever their score: here the only
word in common was "in", found in 54% of the chunks. Meaning-based search
likewise always returned its top results, and reranking only reordered. That
wasted cost and context, could distract the model, and the note suggested a
relevance that was not there. Each stage now keeps only candidates that are
plausibly about the message. The constants, with their reasoning, are in
`apps/api/src/services/project-search/relevance.ts`.

| Stage | Floor | Value |
| --- | --- | --- |
| Keyword: which chunks qualify | A chunk must contain at least one *distinctive* word of the message: one found in at most a quarter of the project's chunks (or in at most three, however few there are) and not an English stop word. Common words still add to a qualifying chunk's score but never bring one in alone. | `KEYWORD_DISTINCTIVE_MAX_SHARE = 0.25`, `KEYWORD_DISTINCTIVE_MIN_CHUNKS = 3` |
| Keyword: how far down | Qualifying chunks scoring below a fraction of the best chunk's score are dropped, so one strong match does not bring a long tail of chunks sharing one weaker word. | `KEYWORD_RELATIVE_FLOOR = 0.35` |
| Meaning-based | Chunks with a cosine similarity to the question below the floor are not candidates (before fusion). Since v0.11.1 (#65), neither are chunks below a fraction of the best chunk's similarity: text on the same topic as the question scores well above the absolute floor. | `SEMANTIC_MIN_SIMILARITY = 0.2`, `SEMANTIC_RELATIVE_FLOOR = 0.7` |
| Reranking | When every returned score lies within 0–1, the reranked list ends before the first candidate scored below the floor; the unscored candidates and the rest of the list go with it. Scores outside 0–1 (raw logits) only order, as before. | `RERANK_MIN_SCORE = 0.05` |

Decisions:

- **Relative, not absolute, keyword thresholds.** A BM25-style score grows
  with the corpus (inverse document frequency is a logarithm of the chunk
  count), so an absolute floor would mean different things in a small and a
  large project. Both keyword floors are ratios: of the project's own chunks,
  and of the best chunk's score.
- **Distinctive words rather than a score normalised by the query's attainable
  maximum.** Normalising by the sum of the query's word weights (times the
  saturation ceiling) was considered and rejected: counting only words present
  in the files, a chunk matching only common words still covers most of the
  query's present weight (the B-tree question's only present word is "in", so
  every chunk scores near the maximum); counting absent words too punishes
  ordinary questions, whose wording ("summarise", "policy", "how") is often
  not in the files, and cuts each topic of a two-topic question. The
  distinctive-word rule rejects exactly the failing case: no word in common
  that is specific to a part of the files.
- **Stop words.** PostgreSQL's own English stop-word list
  (`ts_lexize('english_stem', word)` is empty) marks "what", "about", "is" and
  the like: in some files even these are rare, and "what is 2+2" must not match
  the one passage that says "whatever". Other languages rely on the share rule
  alone, which catches their function words in any file of some length. The
  index itself is unchanged (`simple` configuration).
- **0.25 and 0.35, from the handbook.** Topic words sit at 3–13% of the
  chunks ("conference" 4%, "leave" 6%, "data" 13%) and the commonest words at
  54–100% ("in", "for", "are", "the"). Relative to the best chunk, partial
  matches that should go score 26–31% (every "data protection" chunk for "a
  data management plan"; every "meeting room" for "the Harlow Room's key"),
  while ones that should stay score 41–46% (a chunk mentioning the topic
  once; the weaker topic of "parking permits and annual leave").
- **Meaning-based floor is low on purpose.** Where "unrelated" falls depends on
  the embeddings model: OpenAI text-embedding-3 and Cohere embed-v3 put
  unrelated text at about 0–0.2, while nomic-embed-text, bge-m3 or ada-002
  put even unrelated text at 0.3–0.8, where 0.2 removes nothing. Dropping
  the passage that answers a question is worse than including one that does
  not, so the default only removes what is unrelated for any common model. A
  per-model setting is deferred.
- **Reranking floor only on the 0–1 scale.** Cohere, Jina and bge rerankers
  (as served by vLLM, LiteLLM and TEI) return sigmoid scores, with unrelated
  text close to 0. A server returning raw logits cannot be thresholded on the
  same scale, so its scores only order. Candidates past a below-floor score
  are dropped too, because they rank after one the model judged unrelated.
- **Nothing relevant: no passages, no note on the reply.** The reply shows
  nothing about project search. The model gets one line instead of passages:
  the files' names, that they are too long to include in full, that nothing
  matched closely enough, and that the person can ask about a specific topic,
  name or term. It goes where the passages header goes (a model-only text part
  before the first user message), is costed like it, and is left out if even
  it does not fit. File names are clipped to 120 characters; a project has at
  most 32 files in context.
- **The opening-passages fallback is gone.** Until now, when nothing matched
  (or the message had no searchable word), each file's opening passages filled
  the share. That was the same problem in another form: an unrelated question
  got the first pages of every file. Since the index uses the `simple`
  configuration, which keeps stop words, "no searchable word" means no word at
  all (punctuation, an emoji, a lone letter, an image with no text), which
  says nothing about the files; the file names serve the model better and cost
  almost nothing. `mode: opening` stays in the schema so stored replies parse
  and show their note as before; new replies always use `mode: search`.
- **Small projects are unchanged.** When every file fits whole, nothing is
  searched and every file is included, as in v0.7.

Tuned and proved on the two files that showed the problem
(`apps/api/test/fixtures/project-search/`, synthetic, 268 KB), keyword search
only, with a 128,000-unit input budget (`project-search-relevance.live.test.ts`).
Passages are counted in chunks, as the note counts them:

| Message | Before | After |
| --- | --- | --- |
| write b tree in rust, go, zig | 56 (1 guide + 55 handbook) | 0, no note |
| write a poem about the sea | 51 | 0, no note |
| what is 2+2 | 52 | 0, no note |
| What is AMBER-42? | 52 | 2, both with the answer (section 97) |
| Where is the key for the Harlow Room kept? | 56 | 2, both with the answer (section 97) |
| What are the rules for visitor badges? | 55 | 18, all about visitor badges |
| What goes in a data management plan? | 61 (13 + 48) | 12, guide only, all about data management plans |
| How do I get a parking permit? | 15 | 15 (only distinctive words already) |
| Who approves conference funding? | 11 | 11 (likewise) |
| summarise the leave policy | 54 | 18, all about annual leave |

The best-ranked chunk is in the section that answers each specific question.

Known limitation: keyword search cannot tell what a shared distinctive word
means. "Can you help me plan a trip to Rome?" still matches the research
guide's "data management plans" (12 chunks), because "plan" is specific to
them. Reranking (whose floor drops such passages) and, to a lesser degree,
meaning-based search are the remedy; keyword results are fused in unchanged so
that exact names and codes that embeddings miss are still found. Conversely, a
question whose only content words are everywhere in the files ("Who is the
health and safety officer?" in a handbook that names that officer in most
sentences) gets no passages: no part of the files is more about it than
another. Deferred: per-model or administrator-tunable floors.

## Artifacts

As in the roadmap: inline first, versioned, then model-editable through tools.

| Question | Decision |
| --- | --- |
| What becomes an artifact | HTML and SVG code blocks, Mermaid diagrams of at least a few lines, and documents the model creates through the artifact tools. Ordinary code blocks stay code blocks. |
| Storage | `artifact` (thread, title, kind) and `artifact_version` (content, created by message or person, time). Counts towards storage; follows the conversation's retention, export and deletion. |
| Display | A card in the reply opens a side panel (full screen on phones) with preview, source, version history, copy and download. |
| Sandbox | HTML and SVG render in an `iframe` with `sandbox="allow-scripts"` and no `allow-same-origin` (an opaque, throwaway origin) and a Content-Security-Policy that blocks all network access. The few libraries offered (for charts and diagrams) are inlined into the frame by OCI, never fetched. The same sandbox renders artifacts on share links. |
| Editing | Documents (Markdown) can be edited directly, which makes a new version. HTML and SVG change through the model. |
| Tools | With tool-capable models, `create_artifact` and `update_artifact` (full replacement or find-and-replace edits) make new versions instead of re-sending whole documents. They change only OCI's own data, so they need no approval. |
| Diagrams | When artifacts are on, the system prompt asks for diagrams as SVG artifacts following the Diagram Design style guide (MIT, attributed), mapped to the instance's colours. An administrator switch turns that guidance off. |
| Governance | A per-role `artifacts` switch (on except for `restricted`). Model-calling artifacts are not planned. |

As built (deviations and details decided during implementation):

- **Storage.** Migration 0032: `artifact (user_id, thread_id, message_id,
  source_key, title, kind, current_version)` and `artifact_version
  (artifact_id, version, content, size_bytes, source reply|person, message_id)`.
  An artifact cascades with its thread, owner and the reply that created it; a
  version's message is set null if that message is ever deleted. `source_key`
  is `block:<n>` (the n-th fenced block of the reply, counting every fence) or
  `tool:<call id>`, unique per message, which makes detection and tool calls
  idempotent. Limits: 512 KiB per version (also a check constraint), 100
  versions per artifact, 200 artifacts per conversation.
- **Storage accounting.** Version bytes are summed from the rows (artifacts of
  conversations not in the trash) rather than kept in `storage_usage`, so
  cascading deletes can never leave a counter stale. They count towards total
  bytes, not the file count, in upload, import and restore admission and in
  the usage shown to people and administrators. A new artifact or version is
  admitted under the same per-person lock (thread first, then the usage row);
  detected blocks that do not fit stay code blocks.
- **Detection.** Shared code (`@oci/shared` `detectArtifactBlocks`) so the
  server and every renderer agree on which blocks are artifacts: closed
  top-level fences; `html` that is a whole document or at least 10 lines;
  any complete SVG (`svg`, or `html`/`xml`/untagged whose content is one
  `<svg>`); `mermaid` of at least 3 lines. Run when a reply is stored as
  complete (also after an approval continuation), best effort. A retried reply
  is a new message with its own artifacts; replaying a stream stores nothing.
  Markdown documents come only from the tools.
- **Tools.** `create_artifact` and `update_artifact` (full `content` or up to
  20 find-and-replace `edits`, each matching exactly once) are built-in tools
  of kind `read`: they change only OCI's own data in the current conversation,
  so no approval. They are not in the per-role tool list; the role's
  `artifacts` switch offers them to every tool-capable model. Updates are
  limited to the conversation's own artifacts. The system prompt lists the
  conversation's artifacts (id, title, kind, version; up to 20, from replies
  on the active path) so the model can address them.
- **Sandbox host page (deviation).** The frame is not an `srcdoc` frame: an
  `srcdoc` document inherits the embedding page's Content-Security-Policy, and
  the application's own policy (`script-src 'self'` in the bundled Caddy
  configuration) would block every inline script. Instead the frame loads a
  static host page, `/artifact-frame.html`, with `sandbox="allow-scripts"`
  only (opaque origin), served with its own policy `default-src 'none';
  script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:;
  font-src data:; base-uri 'none'; form-action 'none'` (header in Caddy and a
  meta element in the file). It accepts one document by `postMessage` from its
  parent and writes it; the document starts with the same policy as a meta
  element and a guard that keeps link clicks inside the frame. Caddy serves
  that path with `frame-ancestors 'self'` and without `X-Frame-Options`;
  everything else is unchanged. Residual risk: a script can still navigate
  its own frame (no browser enforces a navigation policy), which can only
  carry the artifact's own content; automatic refresh tags are removed.
- **Libraries.** D3 7.9.0 (ISC) only, inlined from OCI's bundle in place of
  `<script data-oci-library="d3"></script>`, loaded lazily the first time an
  artifact asks for it.
- **Display.** HTML and SVG blocks are replaced by their card; a Mermaid
  diagram keeps its inline drawing with the card below it; a block without a
  saved artifact stays a code block. The panel has Preview, Source and
  Versions, Copy and Download. From 1024px wide it is docked beside the
  conversation (`aside`, named by its title; about 45% wide, at least 22rem):
  non-modal, no focus trap, Escape inside it or Close closes it and focus
  returns to the card or the composer. Narrower, and always on share links, it
  is a modal dialog (right side, full screen on phones); Escape leaves an edit
  first, then closes, and focus returns to the card. Close sits in its own
  header column, never over the actions. Mermaid and Markdown previews use the
  conversation's renderer (Mermaid in strict mode), not the frame; Source is
  highlighted by the same Streamdown code plugin (plain text above 50,000
  characters; at most every 400 ms while written).
- **Live artifacts.** An artifact tool call is shown as its card at its place
  in the reply (no separate tool step): while its input streams
  (`input-streaming`, partial input parsed by the SDK) the card reads
  "Preparing…" (with the seconds waited after 3 s), then "Writing *title*…"
  with line and character counts and the last three lines; "Details" shows a
  readable summary (never the raw JSON). The panel can show the source as it
  arrives (`aria-busy`, polite announcements at start and finish only) and
  switches to the saved artifact's preview once the list (read again when a
  call's output arrives) has it, unless the person opened something else.
  On wide screens and unless the person turned off "Open artifacts
  automatically" (a browser preference), the panel opens by itself, without
  moving focus, for the first artifact a reply written in this tab starts
  writing, or for the first block artifact once such a reply has finished;
  never for history, reloads, share links, or after the person closed the
  panel or opened something during that reply.
- **Reply order.** A reply's reasoning, tool calls and text are shown in the
  order of its parts, each run of one kind as one group, so multi-step replies
  read reasoning, tool call, reasoning, …, text. Share pages and Markdown
  exports interleave tool-step summaries and text the same way.
- **Editing.** A person's edit of a Markdown document (`POST
  /api/artifacts/:id/versions` with `baseVersion`, 409 when stale) makes a
  `person` version. Reading stays possible when the role switch is off.
- **API.** `GET /api/artifacts?threadId=`, `GET /api/artifacts/:id`,
  `GET /api/artifacts/:id/versions/:n`; owner only, 404 otherwise and for
  conversations in the trash.
- **Shares and exports.** A share includes artifacts created by its replies,
  each at the newest version made by a shared reply or by the owner (for a
  snapshot, edits made before the link was created), redacted like message
  text. The JSON export carries every version; Markdown names them
  ("Artifact “Title” (HTML, version 2)"). Forks and edits copy the
  artifacts of copied replies with the versions made on the copied path,
  renumbered.
- **Diagram guidance.** A short paragraph adapted from the Diagram Design
  skill (MIT, Cathryn Lavery) using the branding accent colour; the
  `diagramGuidance` chat setting (on by default) turns it off.

## File output

Export a reply or an artifact as a document, built on the stored content.

| Format | From |
| --- | --- |
| DOCX | A reply or a Markdown artifact: headings, lists, tables, code, links. |
| PDF | The same, laid out server-side without a browser. |
| XLSX | Tables in a reply or artifact, one sheet per table. |
| PPTX | A Markdown artifact or reply, one slide per top-level heading. |

Libraries must be MIT/Apache and pure JavaScript (no headless browser).
Generation is server-side, size-limited, and counts towards the export rate
limit.

As built (deviations and details decided during implementation):

- **API.** `GET /api/threads/:id/messages/:messageId/export?format=` for an
  assistant reply on the active path and `GET
  /api/artifacts/:id/export?format=[&version=]` for a Markdown artifact
  (current version by default). Owner only; 404 for anyone else, for
  conversations in the trash, user messages and superseded replies; 409 while
  the reply is still streaming. HTML, SVG and Mermaid artifacts are refused
  (422): they download as they are. No new tables, no migration. Formats,
  labels, MIME types and limits are shared (`@oci/shared` `documents.ts`).
- **Parsing.** markdown-it 15 (MIT; CommonMark, GFM tables and
  strikethrough, linkify, raw HTML off, nesting capped at 100) into one small
  document model that every generator reads. micromark was rejected: its GFM
  table and emphasis handling is quadratic (a 40,000-row table took over a
  minute). Images become "[Image: alt]" and are never fetched; math stays as
  written; raw HTML stays literal text; only absolute http, https and mailto
  links (up to 2,048 characters) stay links; characters XML cannot carry are
  removed.
- **Generators.** DOCX with `docx` 9.7.2 (A4, Title and Heading styles, real
  Word numbering per list, repeating shaded table header). PDF with `pdfkit`
  0.20.2 (A4, standard Helvetica/Courier, not embedded). XLSX written directly
  as SpreadsheetML and zipped with `fflate` (deviation from "a library": exceljs
  pulls in archiver, unzipper, tmp and a dozen deprecated packages; it is a dev
  dependency only, to read files back in tests): one sheet per table named after
  the heading above it, header bold and frozen, plain numbers and percentages
  as numbers, everything else shared-string text, so nothing is a formula.
  PPTX with `pptxgenjs` 4.0.1 (16:9; title slide, then a slide per top-level
  heading, or per second-level heading when there is a single top-level one;
  overflow continues on "(continued)" slides; table rows spread over slides
  repeating the header; cells cut to 500 characters; at most 250 slides). Its
  output is post-processed to drop the repeated `a:pPr` it writes before every
  run, which PowerPoint otherwise offers to repair.
- **PDF fonts (limitation).** The standard fonts cover Windows-1252 only:
  other accented Latin letters lose the accent, a few symbols get ASCII
  stand-ins ("→" to "->"), everything else prints as "?". Embedding a Unicode
  font was rejected: fonts covering those scripts are OFL rather than
  MIT/Apache and add megabytes per script. DOCX keeps every character; the
  user guide says so.
- **Isolation.** Each document is generated in a fresh `worker_threads`
  worker (512 MB old-generation heap, 60 s); exhausting either is a 422 "too
  long or complex", other failures a 500. A replica generates at most two at
  once and one per person (in-process; 429 with `Retry-After: 5` otherwise).
  The API process never loads the generators. The API thread makes only the
  cheap checks (text present, 512 KB of UTF-8 at most and, for XLSX, the
  shared `markdownHasTable` line scan) and leaves parsing to the worker: a
  dense 512 KB input takes markdown-it about half a second, which must not
  block the event loop for a request that is refused without using the
  allowance. The worker's parser has the last word on tables. Output is
  capped at 20 MB.
- **Rate limit.** One hourly allowance per person, 60, bucket `export:file`,
  shared with `GET /api/threads/:id/export` (Markdown), which had no limit
  before; the full archive keeps its own. Refusals (no text, too large, no
  table, not found) are decided before the allowance is used; the generation
  slot is taken before it, so "already being prepared" costs nothing.
- **Audit.** `message.export` (format, threadId, sizeBytes) and
  `artifact.export` (format, version, threadId, sizeBytes); never content or
  titles.
- **Filenames.** `<title-slug>-reply-<YYYY-MM-DD>.<ext>` for a reply,
  `<title-slug>-v<n>.<ext>` for an artifact, ASCII only (the conversation
  Markdown export's slug), in `Content-Disposition: attachment; filename="…"`,
  with `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.
- **Web.** "Export as…" is a Radix dropdown menu button (icon in a reply's
  actions, labelled in the artifact panel for Markdown documents, owner mode
  only, so never on share pages; not offered while a reply streams or for
  replies without text). It lists DOCX, PDF, PPTX and, when `markdownHasTable`
  finds a table, XLSX, evaluated only when the menu opens. That is the same
  check the API makes before generating, so the option appears exactly when
  the API would accept it; a reply the line scan misjudges still gets the
  API's 422 message. The file is fetched (`api.download`), saved through an
  object URL under the `Content-Disposition` name, and any failure shows the
  API's message inline (`role="alert"`, dismissible). Temporary chats can
  export, like their Markdown download.
- **Licences.** The new dependency trees add BlueOak-1.0.0 (sax),
  `(MIT AND Zlib)` (pako), `(MIT OR GPL-3.0-or-later)` (jszip, used under MIT)
  and PSF-2.0 (argparse, markdown-it's CLI only) to the allowed list.

## User memory

| Question | Decision |
| --- | --- |
| Availability | Instance switch (off by default), per-role switch, and each person's own opt-in in Settings (off by default). |
| How memories are made | With a tool-capable model, `remember` and `forget` tools; the reply shows "Memory updated" with undo. People can also add, edit and delete entries in Settings → Memory. |
| How they are used | Included in the system prompt, newest first, up to a fixed share of the input budget. Never used or written in temporary chats. |
| Data | Visible, editable, deletable, included in the full export, and subject to a retention setting. Audited as metadata only. |

As built (deviations and details decided during implementation):

- **Storage.** `user_memory` (migration 0033): user, content (1-500
  characters, whitespace collapsed to one line), source (`tool` or `person`),
  the conversation and message a tool-made note came from (set to null when
  they are deleted, so a note outlives its chat), created and updated times.
  The person's opt-in is `user_preference.memory_enabled` (same migration),
  not a separate table. At most 200 notes per person, enforced under a
  per-person advisory lock; the same note (ignoring case and spacing) is never
  stored twice.
- **Switches.** The instance switch is `features.memory` (General settings,
  off; settings saved before v0.9 read as off). Because the features object
  is otherwise written whole, `memory` is optional in the PATCH so an older
  client cannot switch it off by leaving it out. The role switch is a new
  `memory` role feature (on except `restricted`), combined with the instance
  switch like the others. Reading and deleting notes always work (a person's
  data stays theirs to review and delete); adding, editing, switching on and
  restoring by undo need the instance and role to allow memory.
- **Tools.** `remember({content})` and `forget({id})` are built-in tools of
  kind `read` (no approval): they change only the person's own OCI data, the
  person opted in, and every change is shown with Undo, the same reasoning as
  the artifact tools. They are governed by the role's `memory` switch, so
  they are added by the registry beside the catalogue and are not listed (or
  separately switchable) under a role's tools. They are offered only when
  every switch allows memory and the chat is not temporary; each call checks
  again (switches and the thread's `temporary` flag) before writing.
  `forget` takes the 8-character id shown before each note in the prompt; a
  `remember` of an existing note returns `exists` and changes nothing.
- **Undo.** `POST /api/memory/undo {messageId, toolCallId}` reads the step's
  stored result from the person's own reply: an added note is deleted, a
  removed one restored under its old id. Repeating it changes nothing. The
  web client marks the note "Undone" locally; after a reload Undo is offered
  again and is harmless.
- **Prompt.** A `<user-memory>` section after the instance prompt,
  personalisation and project instructions, before any compaction summary,
  framed as notes about the person rather than instructions, one line per
  note with its id. Budget: 5% of the model's input budget, capped at 8 KiB
  (byte units). Notes are added newest (most recently updated) first and the
  first that does not fit ends the list. A note's text cannot open or close
  the section. Models without tool calling still get the section. Loading is
  best effort: a failure leaves memory out rather than failing the reply.
- **Retention.** `memoryRetentionDays` on the retention settings (null = off),
  applied by a daily `retention.memories` job by last update.
- **Audit.** `memory.add`, `memory.update`, `memory.delete` with count,
  source, `via` (`tool`, `settings`, `undo`, `retention`) and ids, never the
  text; `memory.settings.update` for the opt-in; one `memory.delete` per
  retention run with the count and number of people (one per note since
  v0.10, as a deletion event). Tool calls also produce
  the usual `tool.call` events.
- **Export.** `memory.json` in the full export (plus a count in the manifest
  and README), whatever the switches say.

## Compliance export and legal hold

| Question | Decision |
| --- | --- |
| What | Audit events, and optionally conversation content (off by default), written as JSON Lines to S3-compatible storage on a schedule. |
| Format | One object per period, with a checksum and a manifest; each run continues from the last exported event, so nothing is skipped or duplicated. |
| Legal hold | Administrators place named people on hold. While held, retention, trash purging and account deletion skip that person's data. Placing and lifting holds are audited. |

As built (deviations and details decided during implementation):

- **Cursor.** Timestamps and random UUIDs cannot order events exactly, so
  migration 0034 adds `audit_log.seq` (a sequence; existing entries numbered
  once in `(created_at, id)` order under the migration's exclusive lock) and
  `message.change_seq` (set by a trigger on insert and whenever parts,
  status, error or `superseded_at` change). Each stream's cursor is the last
  exported number (`compliance_export_cursor`). Sequence numbers alone allow
  a gap (a transaction draws 10, another draws 11 and commits first), so a
  run's upper bound is read under a brief `SHARE` lock, which waits for every
  transaction already writing to the table; the lock wait is bounded (2 s,
  three attempts), after which the run fails without moving the cursor.
- **Exactly once.** A run records its object keys before uploading, uploads,
  reads every object back (size, SHA-256, line count), writes the manifest
  last, then moves the cursors in the transaction that marks the run
  succeeded (conditional on the cursor not having moved). Failed runs delete
  their objects; runs a restart interrupted are found by their `running` row
  and cleaned up by the next run under the job lock. Audit retention keeps
  entries above the cursor while the export is on.
- **One object per stream per run** (`audit.jsonl`, `messages.jsonl`,
  `manifest.json` in a dated folder), not one per period; empty runs write
  nothing. Schedule: hourly or daily (a UTC hour).
- **Content (deviation: not retroactive).** Off by default. Turning it on
  starts the message stream from that moment; messages written before (and
  while it was off) are not exported, and existing messages are not numbered
  (no rewrite of `message`). Lines carry ids, roles, text, tool-step
  summaries (`summarizeToolPart`), file names and cited URLs; never reasoning,
  raw tool results, `data:` URLs or attachment bytes. A message still
  streaming is exported once it finishes; changes between runs collapse to
  the latest state. Deletions are not exported as content events.
- **Destination** reuses the backups destination code (now
  `destinationIssues`/`resolveDestination` in `services/backups/settings.ts`):
  the attachment bucket under `.oci-compliance/` (skipped by reconciliation)
  or a separate bucket with encrypted credentials. Exported objects are kept
  unless `keepDays` is set.
- **Audit.** `compliance.settings.update`, `compliance.hold.place` and
  `compliance.hold.lift` join the protected actions. `compliance.export.run`
  is recorded for manual runs and failures only: auditing every scheduled
  success would make every run export the previous run's entry.
- **Legal hold.** `legal_hold` rows (active while `lifted_at` is null; one
  active hold per person). Retention, trash purge (threads and attachments),
  temporary chat expiry and audit retention (entries by or about the person)
  skip held people; their own "delete forever" and "empty trash" are refused
  (moving to the trash still works); admin deletion is refused with a clear
  message, and a `BEFORE DELETE` trigger on `user` (SQLSTATE `OCLH1`) refuses
  it on every other path, including Better Auth's admin endpoints. Not
  covered: project deletion (its files are deleted at once) and usage-event
  pruning (both covered in v0.10, with every other deletion path; see
  `v0.10-design.md`).

## Observability and events

| Question | Decision |
| --- | --- |
| Metrics | A Prometheus endpoint (`/metrics`), off unless a scrape token is configured, covering requests, replies, tool calls, jobs, queue depth and errors. |
| Traces | OpenTelemetry over OTLP when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; no content in spans. |
| Webhooks | Administrators register HTTPS endpoints for selected audit actions. Payloads are signed (HMAC-SHA256), retried with backoff, and delivered by the job runner; outbound requests use the same guard as connectors. |

As built (details decided during implementation):

- **Metrics.** A hand-written exposition (counters, histograms, gauges read at
  scrape time) rather than `prom-client`: OCI needs nothing else, and it adds
  no dependency. Served at the API root (`/metrics`, not `/api/metrics`), so
  the bundled Caddy does not forward it; scrape replicas directly. Without
  `METRICS_TOKEN` it answers 404; the token is compared as a SHA-256 digest in
  constant time. Labels are route templates, configured tool ids, job names
  and fixed vocabularies; never ids or raw paths. Queue depth is the webhook
  queue and the storage deletion queue; "errors" are `oci_errors_total`
  (unexpected server errors) plus 5xx statuses in the request counter. Reply
  metrics hook into the end of generation (`stream-response.ts`, one line),
  tool calls into `recordToolCall`, jobs into the job runner.
- **Traces.** The OpenTelemetry SDK (`sdk-trace-node`, OTLP/HTTP JSON exporter)
  is loaded with dynamic imports only when the endpoint is set. Spans for HTTP
  requests (named by route template, honouring an incoming `traceparent`),
  replies and tool calls (recorded after the fact with their measured start),
  jobs, backups and webhook deliveries. Errors set a status with a class name
  or HTTP status, never a message. No auto-instrumentation of outgoing calls.
- **Webhooks.** Configuration stays in the UI (endpoints) while metrics and
  traces are environment-only, shown read-only on System health. Actions are
  exact names or `prefix.*`, or all. The queue (`webhook_delivery`, migration
  0030) is filled by `recordAudit` itself (the audit id is generated in the
  application so the payload can carry it; the payload's `createdAt` is the
  application's clock); endpoints are cached for 15 s per process. Delivery is
  at least once: rows are leased (`FOR UPDATE SKIP LOCKED`, five minutes)
  before sending. Signature: `OCI-Webhook-Signature: v1=<hex HMAC-SHA256 of
  "<timestamp>.<body>">` with `OCI-Webhook-Timestamp`; the body is stored, so
  retries send identical bytes, re-signed. Retries: 8 attempts, 1 minute
  doubling to a 1-hour cap; refused addresses, schemes and redirects fail at
  once. Endpoints have the connectors' *Allow private network* switch (plain
  HTTP and private addresses; metadata addresses never). The payload is the
  audit entry without its IP address. The secret is shown once, on creation
  and rotation; rotation takes effect immediately (no overlap window).
  Webhook changes and `backup.settings.update` join the audit actions kept
  regardless of retention.

## Automated backups

| Question | Decision |
| --- | --- |
| What | A scheduled `pg_dump` and a snapshot of attachment objects, written to S3-compatible storage. |
| Retention | Keep a configurable number of daily and weekly backups. |
| Restore check | Each backup is verified (archive readable, checksums, object counts) and the result shown on System health. A full restore into a scratch database is documented, not automated. |
| Where it runs | In the API's job runner, so no new service; the API image gains the PostgreSQL client tools. Deployments that already back up their own way can leave it off. |

As built (deviations and details decided during implementation):

- **Attachments: a manifest, not a copy (deviation).** Each backup writes
  `attachments.jsonl` (key, size, SHA-256 of every file and thumbnail object;
  no names) instead of copying objects. Copying every object daily would make
  backups proportional to all uploads ever made; objects are immutable, so the
  manifest plus bucket versioning (or volume snapshots for local storage)
  gives the same restore guarantee. Checksums are cached in
  `backup_object_checksum`, so each object is read once. Incremental copying
  to the backup bucket is a possible later addition.
- **Destination.** Either the attachment bucket under the reserved
  `.oci-backups/` prefix (which storage reconciliation skips) or a separate
  bucket with its own encrypted credentials and prefix, recommended so one
  leaked or lost credential does not take the backups with the data. The
  separate option refuses the attachment bucket itself. Settings live in the
  `backups` instance setting; turning backups on is refused while the
  destination is incomplete or `pg_dump` is missing.
- **Schedule.** A daily hour (UTC); the `backups.run` job ticks every ten
  minutes and runs when today's slot has no scheduled attempt and no
  successful manual backup, so a missed slot is caught up. Manual runs share
  the job lock and run in the background.
- **Streaming.** `pg_dump --format=custom` streams into an S3 multipart upload
  (16 MiB parts, `S3StorageDriver.putStream`); the upload completes only if
  `pg_dump` exits 0. The password goes into a 0600 `.pgpass` in a private
  temporary directory, never into arguments or `PGPASSWORD`; the child gets a
  minimal environment, and output is scrubbed of the password.
- **Verification.** The stored archive is read back: size and SHA-256 must
  match, and `pg_restore --list` (fed from the stream) must list tables; the
  manifest's size, checksum and line count must match. A run failing any step
  is recorded as failed and its objects are deleted. Missing attachment
  objects do not fail a run; they are counted and warned about on System
  health. Archives written to a stream carry no data offsets, so restores are
  serial (no `pg_restore --jobs`).
- **Retention.** The newest backup of each of the last *n* days that have one,
  plus the newest of each of the last *m* ISO weeks (UTC); defaults 7 and 4.
  Only runs at the current destination are pruned; run rows stay as history.
- **History.** `backup_run` (migration 0030) rather than `job_run.details`, so
  object keys, sizes and checksums are queryable. Each run is audited as
  `backup.run` (actor for manual runs), so webhooks can alert on failures.
